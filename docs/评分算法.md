# 评分算法

> **v0.2，2026-10-24：已在 `gildedrose-lab/scorer/` 实现**（判定在 `judge.py`，汇总与比较在 `aggregate.py`）；单元测试与宿主机集成测试已通过，Docker 容器中的完整校准待执行，见[评分器运行说明](评分器运行说明.md)。 本文把[评测规格](评测规格.md) v0.3 的指标定义写成可以直接实现的计算步骤：单个测试怎么判状态，一份产物怎么算指标，多次运行和多道题怎么汇总，两个 Agent 版本怎么比较并下结论。各评分步骤怎样执行、输入输出是什么格式，见[评分器与校准样本设计](评分器与校准样本设计.md)。

## 1. 先说清楚：没有单一总分

评分结果是一张**成绩单**加一个**比较结论**，不把各项指标加权合成一个总分。原因：

- 权重怎么定都带主观性，换个权重排名就变；
- 合成之后，“检出率升了、误报率也升了”这种取舍就看不出来了。

比较两个版本时，按第 6 节的规则给出四种结论之一：更好、更差、无法区分、主指标提升但有代价。这个结论就是“评分”的最终输出。

## 2. 计算的层级

```text
测试（一个 TEST）
  └─ 产物（一次运行冻结的一组测试文件；每次运行有“首次”和“修复后”两份）
       └─ 运行（同一道题跑 K 次）
            └─ 题目
                 └─ 题库（开发集、验收集分开，永不合并）
```

- **每次运行评两份产物**：首次生成的产物和预算内修复后的产物，各自独立走一遍全部评分步骤。比较版本时用“修复后”，“首次”单独报告。
- **只存计数，不存比率**：每份产物的 `result.json` 保存原始计数（杀死几个、分母多少），比率在汇总时才计算，避免四舍五入误差累积。

## 3. 单个测试的状态判定

对步骤 2 发现的每个测试，按下面的顺序判定，**命中第一条即停**：

| 顺序 | 条件 | 状态 |
|---|---|---|
| 1 | JSON 中 `status` 不是 `RUN` | `disabled` |
| 2 | JSON 中 `result` 是 `SKIPPED` | `skipped` |
| 3 | 单独重跑时没有拿到该测试的结果（被信号终止、异常退出或提前退出，没有写出 JSON） | `crashed` |
| 4 | 单独重跑时超过 `test_timeout_seconds` | `timed_out` |
| 5 | JSON 中 `failures` 非空 | `failed_on_target` |
| 6 | 步骤 4 的任意一次运行结果与步骤 3 不同（变成失败、崩溃、超时或跳过） | `flaky` |
| 7 | 以上都不满足 | `valid` |

- 整体运行“可信”指：写出了 JSON、未超时、退出码为 0 或 1（GoogleTest 有断言失败时退出码为 1）。整体运行可信时，第 3、4 条不会出现，直接取整体运行的结果；否则对每个测试单独重跑一次，按单独重跑的结果判定。
- 整体运行的超时为 `test_timeout_seconds × 测试数`，限制在 20–600 秒。
- 步骤 4 的一次运行拿不到 JSON 时，从标准输出恢复：已结束的测试取其结果；崩溃或超时时正在运行的那个测试计为失败；因此没有运行到的测试，这一次不计入。
- 状态 1–5 合称**无效测试**；`flaky` 单独计数；只有 `valid` 的测试（称为**稳定有效测试**）进入覆盖率、变异和替换版本步骤。

## 4. 一份产物的判定与指标

### 4.1 产物状态

按顺序判定，命中即停：

| 顺序 | 条件 | 状态 | 原因 |
|---|---|---|---|
| 1 | 任一步骤出现基础设施错误（工具链、Docker、评分器、题目材料出错） | `infra_error` | 具体错误 |
| 2 | 产物哈希不符，或含不允许的文件 | `invalid` | `artifact_rejected` |
| 3 | 编译或链接失败 | `invalid` | `build_failed` |
| 4 | 列出测试时就拿不到结果（没有写出列表 JSON，例如自带 `main` 不运行测试、静态初始化中退出） | `invalid` | `no_result` |
| 5 | 发现的测试数为 0 | `invalid` | `zero_tests` |
| 6 | 整体运行可信，但结果中的测试集合与发现清单不一致 | `invalid` | `protocol_mismatch` |
| 7 | 整体运行不可信，且每个测试单独重跑都拿不到结果（全部崩溃或超时） | `invalid` | `no_result` |
| 8 | 没有状态为 `valid` 或 `flaky` 的测试 | `invalid` | `no_valid_tests` |
| 9 | 有 `flaky`，但没有 `valid` | `invalid` | `all_flaky` |
| 10 | 以上都不满足 | `scored` | — |

### 4.2 每份产物保存的计数

| 计数 | 含义 |
|---|---|
| `built` | 步骤 1 通过为 1，否则为 0 |
| `n_discovered` | 发现的测试数；构建失败时不存在 |
| `n_invalid` | 状态 1–5 的测试数 |
| `n_passed_1_3` | 状态为 `valid` 或 `flaky` 的测试数，即通过步骤 1–3 的测试 |
| `n_flaky`、`n_valid` | 不稳定测试数、稳定有效测试数 |
| `flaky_failures` | 每个不稳定测试在 N 次重复运行中的失败次数 |
| `mut_killed`、`mut_survived`、`mut_not_covered`、`mut_timeout`、`mut_other` | 步骤 6 的变异计数，已剔除冻结时判定的等价变异和不稳定变异 |
| `mut_total` | 冻结的变异分母，即全部变异减去等价变异和不稳定变异 |
| 覆盖计数 | 每个被测文件的已执行行数与可执行行数、已执行分支数与总分支数、已调用函数数与函数总数 |
| `variants` | 步骤 7 中每个替换版本的结果；等价版本另存失败的测试名单 |
| 成本 | token、耗时、模型调用次数、修复轮次，原样取自生成记录 |

### 4.3 由计数算指标

记号：`⊥` 表示“不适用”，在汇总时跳过，不是 0。

| 指标 | 一份产物上的计算 | `invalid` 时 |
|---|---|---|
| V1 | `built` | 照常计算 |
| V2 | 产物状态为 `scored`，或原因为 `all_flaky`，记 1；否则记 0 | 照常计算 |
| V3 | `n_invalid ÷ n_discovered` | `n_discovered` 不存在时为 ⊥ |
| S1 | `n_flaky ÷ n_passed_1_3` | `n_passed_1_3 = 0` 时为 ⊥ |
| S2 | 每个不稳定测试：`失败次数 ÷ N` | 没有不稳定测试时为 ⊥ |
| M1（端到端） | `mut_killed ÷ (mut_total − mut_timeout)`；`mut_other` 留在分母中 | **记 0** |
| M1（仅有效） | 同上 | ⊥ |
| M2 | 检出的手写变异数 ÷ 手写变异总数（版本编译失败的不计入分子分母，单列） | ⊥ |
| M4 | 每个真实缺陷版本：检出记 1，未检出记 0，版本编译失败记 ⊥ 并单列；一份产物上取各版本的平均 | ⊥ |
| F1 | 在至少一个等价版本上失败或超时的稳定有效测试数 ÷ `n_valid` | ⊥ |
| C1–C3 | 所有被测文件的计数先求和，再相除 | ⊥ |
| K1 | 原样保留 | 照常保留 |

`infra_error` 的产物不算任何指标，见第 5.1 节的重跑规则。

> 设计说明：
> - V2 的定义是“通过步骤 1–3”，所以全部不稳定（`all_flaky`）的产物也算有效运行；但没有稳定测试可用，端到端 M1 仍记 0。
> - 端到端 M1 把无效产物记 0，生产中“生成了但不能用”的情况就会反映在主指标里。

## 5. 汇总

### 5.1 基础设施错误的重跑

- 产物为 `infra_error` 时，修复问题后重新评分同一份冻结产物，不需要重新生成，最多重试 2 次。
- 重试后仍是 `infra_error` 的，这次运行在该版本下标记为缺失，汇总时跳过，并在报告中写明缺失的题目和次数。
- 比较两个版本时，只用两者都有结果的题目（第 6.1 节）。

### 5.2 按题汇总（同一题、同一版本、同一阶段）

对该题的 K 次运行：

- 比率类指标（V1、V2、V3、S1、M1、M2、M4、F1、C1–C3）：取各次运行值的**算术平均**，跳过 ⊥。全部是 ⊥ 时，该题这一项为 ⊥。
- S2：把所有不稳定测试的值合在一起，取中位数。
- K1：报告每项成本的平均值和中位数。

### 5.3 跨题汇总

- 每道题**权重相同**，取各题值的算术平均，跳过该项为 ⊥ 的题，并写明参与的题数。不按变异数或测试数加权，避免大题主导结果。
- 开发集和验收集分别汇总，永不合并。

### 5.4 噪声估计

**前提**：测噪声之前，评分器必须已通过校准（[评分器与校准样本设计](评分器与校准样本设计.md)第 11 节），其中包括“同一样本评两次，结果除耗时字段外完全一致”。这保证评分器自身的噪声为 0，测出的波动全部来自 Agent 的生成过程。评分器修改后要重新校准；如果评分器版本变了，噪声也要重测。

顺序为：实现评分器 → 校准（含重复评分一致）→ 用基线版本测噪声 → 根据噪声定 δ 和各容忍值，冻结评测规格 v1 → 比较版本。δ 只在比较版本时使用，前面几步都不依赖它。

同一个 Agent 版本、同一批题，独立评测两轮（每轮每题 K 次），按第 6.2 节把这两轮当作两个版本比较。得到的 M1 差值置信区间半宽，就是**噪声幅度**。“最小有意义差异” δ 不能小于噪声幅度。

## 6. 比较两个版本

### 6.1 配对的题集

只用两个版本都有非缺失结果的题目，记为集合 T，题数为 n。n 小于 10 时，结论标注“题数不足，仅供参考”。

### 6.2 主指标的差值与置信区间（两层配对 bootstrap）

对每道题 t，A、B 两个版本各有 K 个“修复后”阶段的端到端 M1 值：

1. 点估计：`d_t = mean(B 在 t 上的 K 个值) − mean(A 在 t 上的 K 个值)`，`Δ = mean(d_t)`，对 t ∈ T 求平均。
2. 置信区间：固定随机种子，重复 B = 10000 次：
   1. 从 T 中有放回地抽 n 道题（按题聚类）；
   2. 对每道抽中的题，分别从 A 的 K 个值、B 的 K 个值中有放回地各抽 K 个，算出这道题的 `d_t*`；
   3. 对抽中的题求 `Δ* = mean(d_t*)`。
3. 取这 10000 个 `Δ*` 的 2.5% 和 97.5% 分位数，作为 95% 置信区间 `[L, U]`。

第一层抽题，反映“换一批题结果会怎样”；第二层抽运行，反映同一道题上每次运行的波动。随机种子写入结果文件，保证可复现。

### 6.3 守护指标

对每个已接入的守护指标 g（V2、S1、K1；有数据时还包括 M2、M4、F1），用同样的方法算差值 `Δ_g` 和区间。先统一方向：

- V2、M2、M4 越高越好，`worse_g = −Δ_g`；
- S1、F1、K1 越低越好，`worse_g = Δ_g`。

`worse_g ≤ ε_g` 即为通过。各指标的容忍值 `ε_g` 在正式比较前写定（评测规格第 7 节的待定事项）。

### 6.4 结论

依次判断，命中即停：

| 结论 | 条件 |
|---|---|
| **更好** | `Δ ≥ δ`，`L > 0`，且所有守护指标通过 |
| **主指标提升但有代价** | `Δ ≥ δ`，`L > 0`，但至少一个守护指标不通过；列出不通过的项 |
| **更差** | `Δ ≤ −δ`，且 `U < 0` |
| **无法区分** | 以上都不满足 |

二值结果（例如每次运行的 M4）也用同一个 bootstrap 计算。题数多时，可以另用 McNemar 检验作补充，但结论以本节规则为准。

## 7. 算例

假设开发题“甲”的冻结分母为：Mull 共生成 40 个变异，冻结时判定 3 个等价，`mut_total = 37`。

**一份产物**：稳定有效测试跑 Mull，杀死 28 个，超时 2 个，其余幸存或未覆盖。

```text
M1 = 28 ÷ (37 − 2) = 28 ÷ 35 = 0.800
```

**一道题的 5 次运行（修复后阶段）**：

| 运行 | 产物状态 | M1（端到端） | M1（仅有效） |
|---|---|---|---|
| 1 | scored | 0.800 | 0.800 |
| 2 | invalid（build_failed） | 0 | ⊥ |
| 3 | scored | 0.743 | 0.743 |
| 4 | scored | 0.771 | 0.771 |
| 5 | scored | 0.829 | 0.829 |

```text
M1 端到端 = (0.800 + 0 + 0.743 + 0.771 + 0.829) ÷ 5 = 0.629
M1 仅有效 = (0.800 + 0.743 + 0.771 + 0.829) ÷ 4 = 0.786
V2 = 4 ÷ 5 = 0.8
```

仅看有效运行，测试质量不错；端到端分数被一次编译失败拉低。这说明该改进的方向是“生成的测试能否编译”，而不是“断言写得好不好”。

**两个版本的比较**：三道题上，B 相对 A 的差值为 `d = (+0.10, +0.05, +0.12)`，`Δ = 0.090`。假设 bootstrap 区间为 `[0.05, 0.12]`，预先写定 δ = 0.05：主指标满足 `Δ ≥ δ` 且 `L > 0`。如果 B 的 V2 下降 0.02、容忍值为 0.05，守护通过，结论为**更好**；但题数只有 3，结论要标注“题数不足，仅供参考”。

## 8. 实现要点

- 汇总器只读取各产物的 `result.json` 计数，不重新执行任何测试。
- bootstrap 的次数、随机种子、δ 和各 ε 都写入 `summary.json`，结论连同这些参数一起保存。
- 每个比率都同时输出分子、分母和参与的数量（题数、运行数），便于人工复核。
- 汇总器自身也需要校准：已用手工构造的结果（差值为 0、+0.1、−0.1，守护指标越界，题数不足，重复结果）验证点估计、区间和结论判定，见 `gildedrose-lab/scorer/tests/test_aggregate.py`，不需要 Docker。
