# 测试评测实现与校准样本

> **assessment 0.2.1 已通过 Linux ARM64 Docker 完整校准，GildedRose 16 个样本各两次，与 0.2.0 判定、指标及成本一致。** 两处材料变化失效门禁回归通过，100 道题已按当前 D015/D016 签署准入，见[题库验证说明](题库验证说明.md)第 13 节。本文说明评测模块的职责、运行位置、执行流程、校准样本和当前限制。
>
> 本文描述当前实现；版本迁移过程与具体检查数量见运行说明。文档修订不改变校准样本、阈值或冻结分母。

## 1. 范围与设计原则

评测实验先从 benchmark 题目中提取被测源码和公开任务，交给生成产品。生成结束后，评测模块分别接收首次、最终测试快照，沿用该题源码，并读取题目中的评测参数和隐藏材料，输出结构化评分结果。它不调用模型，不修改被测代码，也不读取 Agent 的推理过程，只读取生成阶段留下的成本记录。

设计原则：

1. **只认执行结果**：是否有效、是否杀死变异，都以容器内实际编译、运行的结果为准。
2. **按结果文件判定，不按退出码判定**：GoogleTest 断言失败也会返回非零退出码，所以有效性以 JSON 结果为准，退出码只用来发现崩溃和超时。
3. **评测模块问题和测试问题分开**：工具链、Docker、评测模块自身或题目材料出错时，这次评分记为“基础设施错误”，修复后重评，不能记成 0 分。
4. **构建由评测模块掌控**：CMake 文件、编译选项、链接方式都由评测模块提供，Agent 只提交测试源文件，不能改构建、排除测试或替换被测代码。
5. **同一输入，同一输出**：同一份测试快照重复评分，除耗时、路径、时间戳外结果必须完全一致。
6. **容器内执行，宿主机复核**：容器只执行并留下原始记录；宿主机按原始记录重新判定一遍测试状态，与容器内的判定不一致即视为评测模块故障。

## 2. 总体结构

| 文件 | 运行位置 | 职责 |
|---|---|---|
| `evaluate.py` | 宿主机 | 评分入口：评一份测试快照，或用当前评测模块补评一次历史运行 |
| `pipeline.py` | 宿主机 | 对一份产物依次执行步骤 1–8：校验产物，启动各阶段容器，复核原始记录，写 `result.json` |
| `docker_runner.py` | 宿主机 | 在固定版本的镜像里启动阶段容器，核对隔离参数和挂载的读写属性 |
| `container_steps.py` | 容器内 | 执行构建、测试运行（发现、整体运行、单独重跑、稳定性、覆盖率）和 Mull，写原始记录 `step.json` |
| `judge.py` | 容器内外共用 | 测试状态、产物状态、计数、指标、变异与替换版本的判定，全部为纯函数 |
| `gtest_results.py` | 容器内外共用 | 解析 GoogleTest 的列表 JSON、运行 JSON 和标准输出 |
| `common.py` | 宿主机 | 路径、哈希、题目包与产物校验、Mull 配置生成、评测模块指纹与校准状态 |
| `calibrate.py` | 宿主机 | 校准器：样本各评两次，核对期望和一致性，写校准报告和校准状态 |
| `prepare_task.py` | 宿主机 | 题目准备：标定变异分母、准入检查 |
| `aggregate.py` | 宿主机 | 汇总器：按题、跨题汇总，两个版本的配对比较 |
| `freeze_product.py` | 宿主机 | 为外部准备的测试记录文件清单与哈希：写 `manifest.json` |
| `cmake/` | 容器内 | 评测模块提供的构建模板和 C++11 断言头文件 |
| `VERSION`、`tests/` | — | 评测模块版本号；单元测试、宿主机集成测试与固定数据 |

共用 `evaluator/common/audit.py` 记录命令，`evaluator/common/coverage.py` 解析多文件 gcov 与函数覆盖；镜像标签取自 `evaluator/toolchains/toolchains.py`。评测容器由 `docker_runner.py` 创建，各阶段隔离参数见第 8 节。

## 3. 输入：题目包

```text
benchmark/<task-id>/
  task.json                           # 题目卡的机器可读版
  source/                             # 被测源码；生成阶段提供可见部分，评测阶段沿用该题源码
  hidden/
    reference_tests/*.cc              # 参考强测试集
    equivalence_probe/tests/*.cc      # 有界穷举探针（只用于标定变异分母）
    equivalence_probe/generate_probe.cc   # 探针生成器
    mutation_baseline.json            # 变异分母，由 prepare_task.py 生成，人工复核
    variants/<variant-id>/<源文件相对路径>   # 替换版本：只放被替换的源文件
```

`task.json` 的主要字段（GildedRose 开发题见 `benchmark/gildedrose-update-quality/task.json`）：

| 字段 | 含义 |
|---|---|
| `id`、`set` | 题目 ID；`dev` 或 `acceptance` |
| `source` | 仓库、提交、源码根目录（相对仓库根目录）、被测文件的 SHA-256 |
| `target_sources`、`include_dirs` | 被测源文件（编进测试程序、统计覆盖、加 Mull 插件）和头文件目录 |
| `visible` | 给 Agent 的材料清单；生成产品投影这些可见文件，评测容器只读挂载所需源码 |
| `allowed_test_files` | 产物中允许的文件，例如 `tests/*.cc`、`tests/*.h` |
| `existing_tests` | 目标仓库自带测试的情况；GildedRose 自带的只有 fixme 占位断言，不能作人类基线 |
| `scoring_domain` | 评分输入域 |
| `params` | 稳定性重复次数 N、乱序种子、单测超时、Mull 最短超时、参考强测试集强度阈值 |
| `mull` | Mull 算子（GildedRose 为 `cxx_all`）；评测模块据此生成实际配置，`includePaths` 只包含被测源文件 |
| `hidden` | 隐藏材料的位置 |
| `variants` | 替换版本列表，始终存在，可以为空；每项有 `id`、`kind`（`real_bug`、`equivalent`、`handwritten`）、`expect`（`fail` 或 `pass`）、文件哈希 |

当前接入约束：

- Mull 算子写在 `task.json` 里，不再单独放 `hidden/mull.yml`。实际配置由评测模块生成并记录哈希，避免手写路径和算子不一致。
- 替换版本当前只支持替换被测源文件，不支持替换头文件：未被替换的源文件仍会包含原头文件。

## 4. 输入：运行产物

生成产品在每次编译前保存本轮测试快照；首次快照同时保存在 `first/`，生成结束时另存最终快照到 `final/`。评测分别读取这两份快照及其文件哈希，不直接使用仍可编辑的工作区测试。外部准备的测试需先整理到独立产物目录，再用 `freeze_product.py` 记录清单；这个辅助脚本只生成清单，不负责复制测试。

```text
<产物目录>/
  manifest.json      # 每个文件的 SHA-256 与保存时间；时间字段沿用 frozen_at
  tests/*.cc         # 测试文件；tests/ 同时作为头文件目录
```

评分开始前核对：`manifest.json` 存在且格式正确；实际文件与清单一一对应、哈希一致；每个文件都匹配 `allowed_test_files`；没有符号链接。任何一条不满足，判为 `artifact_rejected`。成本记录 `cost.json` 单独传入，格式包含 `tokens.input/output/cache_read/cache_write`、`seconds`、`model_calls`、`repair_rounds`、`usd` 和成本抽取版本；首次/最终成本分别传入，见[生成入口运行说明](生成入口运行说明.md)。

## 5. 评分步骤的实现

每个阶段在全新的容器中执行，只挂载这个阶段需要的材料：

| 阶段 | 镜像 | 挂载（除 `/assessment`、`/common` 只读和 `/out` 可写外） | 对应步骤 |
|---|---|---|---|
| `gcc-build` | GCC | `/repo` 源码只读、`/product` 产物只读、`/build` 可写 | 1 |
| `gcc-run` | GCC | `/repo` 只读（gcov 读源码）、`/build` 只读 | 2–5 |
| `clang-build` | Clang | `/repo`、`/product`、`/config` 只读，`/build` 可写；`MULL_CONFIG=/config/mull.yml` | 6 的构建 |
| `mull` | Clang | `/repo`、`/build`、`/config` 只读；`MULL_CONFIG` 同上 | 6 |
| `vNN-build` | GCC | `/repo`、`/product`、`/variant` 只读，`/build` 可写 | 7 的构建 |
| `vNN-run` | GCC | `/build` 只读 | 7 的运行 |

阶段按“构建 / 运行”划分：运行阶段不单独挂入 benchmark 的隐藏目录、产物源码和可写的构建目录；替换版本只在构建阶段进入容器，挂载点和目录名都是中性的（`/variant`、`v01`），避免通过显式目录名泄露版本类型；这不构成对恶意测试完全隐藏评测材料的保证，具体限制见第 8 节。

### 5.1 步骤 1：构建

- 用 `cmake/CMakeLists.txt` 构建：`-std=c++11`（关闭扩展），强制包含 `cxx11_guard.h`，`-O0 -g`。
- 被测源文件直接编进测试可执行文件 `scored_tests`，不打包成静态库：测试里重新定义被测函数会出现重复定义的链接错误。
- 链接 `GTest::gmock` 和 `GTest::gtest_main`。
- 三种模式：`coverage`（GCC 14.2.0，只给被测源文件加 `--coverage -fprofile-abs-path`）、`mull`（Clang 19.1.7，只给被测源文件加载 Mull 插件）、`plain`（不插桩，用于替换版本）。
- 核对 `compile_commands.json`：每个编译单元都带 `-std=c++11`，被测源文件和测试文件都在其中；不满足视为评测模块故障。
- CMake 配置失败视为评测模块故障（配置阶段不编译测试）；编译或链接失败判为 `build_failed`，保存含 error、undefined reference、multiple definition、duplicate symbol 的诊断行。

### 5.2 步骤 2–3：发现、整体运行、单独重跑

1. 发现：`--gtest_list_tests --gtest_output=json:<file>`。没有写出列表 JSON 判为 `no_result`；列表为空判为 `zero_tests`。GoogleTest 1.12.1 的列表包含禁用的测试。
2. 整体运行：`--gtest_output=json:<file>`，超时为单测超时 × 测试数（20–600 秒）。结果可信的条件是写出了 JSON、未超时、退出码为 0 或 1；可信时结果中的测试集合必须与发现清单一致，否则判为 `protocol_mismatch`。
3. 整体运行不可信时，逐个单独重跑（`--gtest_filter=<名称>`，各自一份 JSON、各自计时）。
4. 字段取值（已在 GoogleTest 1.12.1 上实测）：通过为 `status=RUN, result=COMPLETED`；失败另带 `failures`；跳过为 `RUN/SKIPPED`；禁用（测试名或套件名带 `DISABLED_` 前缀）为 `NOTRUN/SUPPRESSED`。
5. 测试状态的判定顺序见评分算法第 3 节。

### 5.3 步骤 4：稳定性

对步骤 3 通过的测试：

1. 重复运行 N 次，每次一个独立进程、一份 JSON；
2. 对每个乱序种子运行一次（`--gtest_shuffle --gtest_random_seed=<种子>`）；
3. 每个测试单独运行一次；步骤 3 已单独跑过的复用结果。

所有运行使用同一个工作目录。某次运行拿不到 JSON 时，从标准输出恢复已结束测试的结果（只认带 `(N ms)` 的结束行，不认汇总段的重复行），把崩溃或超时时正在运行的测试计为失败。

### 5.4 步骤 5：覆盖率

- 构建目录在运行阶段只读，所以所有运行都用 `GCOV_PREFIX`（`GCOV_PREFIX_STRIP=0`）把 `.gcda` 重定向到输出目录。前面各次运行写到废弃目录；覆盖率单独用一个干净目录，只运行一次稳定有效测试。
- 采集时把 `.gcno` 从构建目录复制到 `.gcda` 旁边，用 `gcov-14 -b -c -p` 分别生成文本和 JSON，按文本头部的 `Source:` 行对应源文件，只统计 `target_sources`；文本与 JSON 的行、分支计数必须一致。函数覆盖取自 gcov JSON 的 `functions`（`execution_count > 0`）。
- 同一源码行或同一函数可能对应多个符号（如构造、析构函数的 C1/C2、D0/D2 版本）：JSON 的行记录按行号合并，任一记录执行过即算覆盖；函数按名称与起始行合并；文本报告只取合并后的那一行，不取其后按符号分节的重复行（0.1.6 起）。
- 被测源文件编译了却没有任何可执行代码（例如只有 `#include`）时，没有 `.gcda`，只有 `.gcno`；按 0/0 计入并标记 `no_executable_code`，不再使整题覆盖率不可用（0.1.6 起）。
- 覆盖率是诊断指标：采集失败只记一条警告，C1–C3 为“不适用”，不影响其他步骤。C4（增量覆盖）需要可用的已有测试，GildedRose 题目不适用，第一版未实现。

### 5.5 步骤 6：变异测试

- 实际 Mull 配置由 `task.json` 生成（算子 + 只包含被测源文件的 `includePaths`），写入 `/config/mull.yml` 并记录 SHA-256，必须与变异分母中记录的一致。
- 运行 `mull-runner-19 --allow-surviving --include-not-covered --workers=2 --ld-search-path=<多架构库目录> --minimum-timeout=<毫秒> --reporters=Elements ... scored_tests -- --gtest_filter=<稳定有效测试>`。只运行有效测试，靠的是 mull-runner 的用法 `[OPTIONS] <EXECUTABLE> [RUNNER_ARGS]...`：跟在可执行文件后面的参数原样传给测试程序。即使 `--` 被原样转给测试程序也不影响：已实测 GoogleTest 会忽略它，后面的过滤条件照常生效。这样就不需要依赖环境变量。
- 变异以报告中的 `id` 标识，形如 `cxx_sub_to_add:/repo/cpp/src/GildedRose.cc:51:47:51:48`，包含算子和位置。变异集合与冻结的分母不一致视为评测模块故障；分母中标为等价或不稳定的变异剔除；状态映射为 `Killed`→杀死，`Survived`→幸存，`NoCoverage`→未覆盖，`Timeout`→超时，其余→其他。
- Clang 下构建失败（同一份测试在 GCC 下能编译）记为评测模块故障 `clang_build_failed`，需要人工排查工具链差异。

### 5.6 步骤 7：替换版本执行

对 `variants` 中的每个版本（按 ID 排序，阶段目录命名为 `v01`、`v02`……）：

1. 构建：被替换的源文件取自 `/variant/<相对路径>`，其余源文件、头文件目录和测试文件不变，`plain` 模式；
2. 运行：只运行稳定有效测试；整体运行不可信时逐个单独重跑定位；
3. 判定：

| 版本期望 | 结果 | 记为 |
|---|---|---|
| `fail` | 至少一个有效测试断言失败或崩溃 | `detected` |
| `fail` | 只有超时，没有失败或崩溃 | `timeout` |
| `fail` | 全部通过 | `not_detected` |
| `fail` | 版本上编译失败 | `build_failed`，单列，不算检出 |
| `pass` | 全部通过 | `clean` |
| `pass` | 有测试失败、崩溃或超时 | `false_alarm`，列出这些测试 |
| `pass` | 版本上编译失败 | 题目问题，记为评测模块故障，修题目 |

### 5.7 步骤 8：成本

原样读取传入的 `cost.json`；没有传入时记一条 `cost_missing` 警告，不估算。实现上在产物校验和构建之前读取，确保无效产物提前返回时也保留成本。成本提取由生成产品负责，assessment 不重新读取模型会话。

## 6. 状态与指标

测试级、产物级、变异级状态的判定顺序，以及由计数算指标、汇总和比较的方法，都见[评分算法](评分算法.md)第 3–6 节；实现在 `judge.py` 和 `aggregate.py`。

## 7. 输出：结果文件

每份产物输出一个 `result.json`。按 D014，源码使用 assessment 命名；schema 1 的 `scorer` 等字段、`mode: score` 和 `score/<版本>/` 目录保留兼容，不表示仍有旧 scorer 模块。主要字段：

| 字段 | 内容 |
|---|---|
| `scorer` | 评测模块版本、代码指纹、评分时的校准状态 |
| `task`、`product`、`meta` | 题目 ID 与集合、`task.json` 哈希；产物路径与 `manifest.json` 哈希；Agent 版本、第几次运行、首次或修复后 |
| `mode`、`executor`、`images` | `score` 或 `prep`；`docker` 或宿主机辅助检查的 `local`；两个镜像的 ID |
| `status`、`invalid_reason`、`infra_detail` | 产物状态、无效原因、评测模块故障详情 |
| `build`、`tests` | 构建结果与诊断；每个测试的最终状态 |
| `counts` | 测试计数、变异计数、覆盖计数（评分算法第 4.2 节） |
| `mutants`、`variants` | 每个变异的状态；每个替换版本的结果与失败的测试 |
| `metrics` | 由计数算出的单份产物指标（评分算法第 4.3 节） |
| `cost`、`steps`、`warnings` | 成本记录；各阶段的状态与目录；警告（例如变异分母尚未复核） |

目录：`runs/<run-id>/` 下每份产物一个目录，包含各阶段目录（`gcc-build/`、`gcc-run/`、`clang-build/`、`mull/`、`vNN-build/`、`vNN-run/`，各有 `job.json`、`step.json`、命令日志）、宿主机命令日志和 `result.json`。宿主机侧的 Docker 证据（镜像记录、容器创建与检查）写在 `runs/<run-id>/evidence/`。

## 8. 隔离、防作弊与版本

**隔离**：所有容器禁网、只读根文件系统、2 CPU / 2 GiB / 256 进程、非 root、丢弃全部 capabilities；启动前核对每个挂载的读写属性与预期一致，不一致就中止并删除容器。

**已考虑的规避方式与对策**

| 规避方式 | 对策 | 校准样本 |
|---|---|---|
| 改构建文件、排除测试 | 只接受 `allowed_test_files`，构建模板由评测模块提供 | 单元测试 |
| 没有任何测试 | 判 `zero_tests` | CAL-01 |
| 全部跳过或禁用 | 记为 `skipped`/`disabled`，不算有效 | CAL-02、CAL-03 |
| 自带 `main`，不运行测试直接返回 0 | 以 JSON 为准，列表都拿不到判 `no_result` | CAL-04 |
| 静态初始化里调用 `exit(0)` | 同上 | CAL-05 |
| 在测试文件里重新定义被测函数 | 被测源文件直接编进可执行文件，重复定义导致链接失败 | CAL-06 |
| 把断言宏定义为空、只调用不检查 | 测试仍然有效，但变异检出接近 0，主指标会反映出来 | CAL-12、CAL-13 |
| 运行时读取隐藏材料 | 运行阶段不单独挂入 benchmark 的隐藏目录，替换阶段使用中性路径名 | 接线测试 |
| 篡改测试快照 | 评分前核对 `manifest.json` 哈希，拒绝符号链接 | 单元测试 |

评测模块针对常见规避写法，不防专门针对评测系统的恶意代码。当前 `/assessment` 只读挂载整个模块，含校准材料；测试进程也可以改写自己的输出目录。它不构成隐藏材料完全不可读或原始报告不可篡改的强保证。

**版本与补评**

- `assessment/VERSION` 使用 `主版本.次版本.修订号`：改变任何判定或指标口径，升次版本；只修实现错误、不改口径，升修订号；指标集合整体重构，升主版本。
- 校准状态记录在 `evaluator/assessment/calibration-status.json`，包含评测模块版本、**代码指纹**（`assessment/` 下全部代码、构建模板、版本号以及共用脚本的哈希）、**样本指纹**（全部校准样本及期望）、**校准题目指纹**和两个镜像的 ID。评测版本、代码、样本、镜像或任何一道校准题的材料变化，都会使所有题目的校准状态过期（`stale`）。校准默认覆盖 `calibration/` 下所有带样本的题目，并逐题记录指纹；只校准部分题目或样本时不更新状态（D016）。
- **准入（R-08，D016）**：`benchmark/admission.json` 登记已准入题目及其指纹，由 `benchmark/tools/admit.py` 在复核人签署分母后写入。每份结果记录评分时的题目指纹（`task.sha256`），也记录校准状态；汇总器默认拒绝比较未通过校准、来自不同版本评测模块的结果；也拒绝题目当前未准入或准入已失效（当前指纹与登记不一致）、或结果评分时的指纹与登记不一致的结果。runner 批量选题时跳过未准入的题，点名时报错；冒烟与新题试跑加 `--allow-unadmitted`，其结果不能用于正式比较。
- 补评：`evaluate.py --rescore <旧 run-id>` 读取旧运行中每份结果对应的测试快照，核对 `manifest.json` 哈希未变后，用当前评测模块重新评分，写入原 run 的各 trial/score/<新版本>/，旧版本原样保留；同版本已有且指纹匹配的有效结果跳过；失效或不完整结果移入 incomplete/ 后重评，汇总用 --assessment-version 选择版本。

## 9. 题目准备：变异分母的标定

`prepare_task.py baseline` 在 Docker 中执行：

1. 用参考强测试集和有界穷举探针各评分 `--repeats` 次（默认 2 次），准备模式只记录 Mull 原始结果；
2. 各次运行的变异集合必须完全一致；
3. 任何一个测试集在各次之间结果不同的变异，列为**不稳定变异**，从分母中剔除（例如引入了未定义行为、偶然崩溃的变异）；参考测试检出而探针（包含全部参考测试）未检出的变异，结果只能来自二进制差异，同样列为不稳定（D015）；
4. 探针也区分不出（幸存或未覆盖）的变异，列为**等价变异候选**，从分母中剔除；探针超时或其他状态的变异保留在分母中，列入“需复核”；
5. 用剩余分母算参考强测试集的 M1，与 `reference_min_m1`（初始 0.8）比较；
6. 准入检查：参考强测试集和探针都应检出“应失败”的版本、在等价版本上无误报；
7. 草稿写到运行目录；加 `--write` 写入题目包的 `hidden/mutation_baseline.json`，复核状态为 `pending`。**人工逐个复核等价候选后**，把 `review.status` 改为 `reviewed`；复核之前，每份评分结果都会带一条警告。

题库题目用 `benchmark/tools/prepare_new_tasks.py` 批量标定：它调用本工具但不让其直接写入，先落实 `benchmark/tools/mutant_review/<题目 ID>/confirmed.json` 的复核结论（真实 Mull 反例已检出的移回分母；只在未定义行为下不同的列为不稳定，D015），重算参考 M1 后再写入。复核签署与准入由 `benchmark/tools/admit.py` 完成，要求每个等价候选都在同目录的 `equivalent.json` 中有结论（D016）。

GildedRose 的有界穷举探针由 `generate_probe.cc` 在评分输入域内逐点运行原始代码生成：8 个商品名（含 3 个近似名），sellIn −20 至 20，质量 0–50（Sulfuras 为 80），共 14,678 个单商品用例，外加 28 组多商品库存。宿主机检查结果：探针在原代码和当时的等价版本 eq-01（已按 D011 删除）上通过，在 hw-01 上失败。

## 10. 校准样本

校准样本是**评测模块的验收标准**：用好坏已知的测试，检验评测模块的每个判定是否正确。它们是开发材料，由人手写，任何时候都不提供给被评测的生成 Agent。

每个样本的形式和 Agent 的运行产物相同，评测模块走的是同一条路径：

```text
calibration/<task-id>/<sample-id>/
  final/tests/*.cc
  final/manifest.json
  generation/cost.json      # 固定的假数据
  expected.json             # 期望结果
```

`expected.json` 包括：

- **硬性期望** `hard`：产物状态、无效原因、指定测试的状态、其余测试的默认状态、替换版本结果，以及在某个版本上失败的测试清单；
- **相对期望** `relations`：指标的范围或样本之间的大小关系，例如“M1 不超过 CAL-15 的 20%”；
- `reference_copy`：样本中参考测试副本的路径。校准时核对它与隐藏的参考强测试集逐字节相同。

校准还统一核对每轮输出的 `cost`、`metrics.K1` 与样本的 `generation/cost.json` 完全一致，无效样本同样检查。

样本由 `calibration/gildedrose-update-quality/build_samples.py` 生成：CAL-12、CAL-13、CAL-14 由参考强测试集机械改写，CAL-07、08、10、11、15、16 含参考测试的原样副本。修改参考强测试集后要重新运行这个脚本，并升评测模块版本。

当前样本（GildedRose 开发题，替换版本为 eq-02 和 hw-01，所以每个有效样本都同时检查替换版本）。“容器检查”列对应 0.1.5 的完整校准，见[入库报告](../evaluator/assessment/calibration_report.md)和 `runs/calibration-assessment-rename-20261026-02/`：

- **CAL-09** 改为只放两个测试：整体运行的超时随测试数增长，放入整套参考测试会让每次评分多等几分钟。
- **CAL-11** 不用随机数，改用工作目录中的计数文件确定性地模拟：第 1 次通过，之后偶数次失败。真随机会让“同一样本评两次结果一致”无法成立；评测模块按固定顺序运行，所以失败次数是确定的（10 次重复中 5 次失败）。
- **CAL-17**（手写变异）并入各样本的替换版本期望：hw-01 在 CAL-15 上检出、在 CAL-12/13/14 上未检出。
- **CAL-16** 提前启用，用来验证误报这条判定路径。2026-10-25 按 [D011](决策记录.md) 重做：旧的 eq-01 把质量截断到 0–50，只在评分输入域内与原代码一致，会把断言域外真实行为的正确测试判为误报；新的 eq-02 在全部无未定义行为的输入上与原代码一致，只有依赖未定义行为的测试才会在它上面失败。

CAL-12、CAL-15 的数值阈值已随校准样本固定；首次校准时允许的一次调整窗口已经结束。后续修改须记录理由、升评测模块版本并重新校准，不能为使结果通过而临时调整。

## 11. 通过标准与运行时机

**通过标准**（全部满足才算校准通过）：

1. 所有样本的硬性期望完全一致；
2. 所有相对期望成立，特别是 M1 的顺序：CAL-12、CAL-13 < CAL-14 < CAL-15；
3. 每个样本评分两次，结果除耗时、路径、时间戳外完全一致；
4. 样本中的参考测试副本与隐藏的参考强测试集一致；
5. 每轮结果的成本记录与 K1 均完整保留输入成本，包括无效样本；
6. 全部在 Docker 容器内执行，日志和结果保存在独立的运行目录。

只校准部分题目或部分样本时（`--task`、`--samples`），报告照常写出，但不更新校准状态。

**运行时机**：评测代码、校准样本、校准题目材料或镜像变化后重新完整校准。每轮正式评测开始前检查校准状态与指纹，并核对所用题目已准入、指纹与准入登记一致；对应条件未变且状态为 passed 时，复用已有校准，不要求每轮重跑。纯文档变化不改变评测代码指纹；准入清单与题库数据不属于评测代码，变化后不需要重新校准。

**维护**：每新增一个评分步骤，同时补充覆盖该步骤的样本；样本文件冻结并记录哈希。修改样本等同于修改评测模块的验收标准，要升评测模块版本。
