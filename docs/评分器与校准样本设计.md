# 评分器与校准样本设计

> **v0.1 设计草案，2026-10-23，全部待实现。** 对应[评测规格](评测规格.md) v0.3：规格规定“评什么”，[评分算法](评分算法.md)规定“怎么算”，本文规定评分器“怎么做”，以及用什么样本证明它判得对。实现基于现有的 [C++11 固定工具链](C++11固定工具链.md)。文中的文件路径和字段名是建议，实现时可以调整，但调整后要同步本文。

## 1. 范围与设计原则

评分器的输入是一道题的题目包和 Agent 的一次运行产物，输出是这次运行的结构化评分结果。它不调用模型，不修改被测代码，也不读取 Agent 的推理过程，只读取生成阶段留下的成本记录。

设计原则：

1. **只认执行结果**：是否有效、是否杀死变异，都以容器内实际编译、运行的结果为准。
2. **按结果文件判定，不按退出码判定**：GoogleTest 断言失败也会返回非零退出码，所以有效性以 JSON 结果为准，退出码只用来发现崩溃和超时。
3. **评分器问题和测试问题分开**：工具链、Docker、评分器自身出错时，这次运行记为“基础设施错误”，重跑，不能记成 0 分。
4. **构建由评分器掌控**：CMake 文件、编译选项、链接方式都由评分器提供，Agent 只提交测试源文件，不能改构建、排除测试或替换被测代码。
5. **同一输入，同一输出**：同一份冻结产物重复评分，除耗时字段外结果必须完全一致。

## 2. 总体结构

| 模块 | 运行位置 | 职责 |
|---|---|---|
| 调度器 | 宿主机 Python | 校验题目包和产物的哈希；按步骤启动容器；汇总各步骤输出，写结果文件 |
| 容器内执行器 | GCC 镜像、Clang 镜像 | 执行编译、运行测试、gcov、Mull、替换版本；每个步骤输出原始日志和一份步骤结果 |
| 汇总器 | 宿主机 Python | 把多次运行的结果按题、按版本汇总，计算区间和配对比较 |
| 校准器 | 宿主机 Python | 对校准样本逐个评分，与期望比对，输出校准报告 |

复用现有代码：

- `scripts/audit.py`：命令审计，保持不变；
- `scripts/coverage.py`：gcov 解析，扩展为支持多个被测源文件和函数覆盖；
- `toolchains.py` 里的容器隔离参数（禁网、只读根文件系统、资源限制、非 root），抽成公共的 Docker 运行模块；
- `scripts/check_toolchain.py` 里的测试发现、JSON 核对和 Mull 调用，作为步骤 1–3 和步骤 6 的起点。

建议的新文件：

```text
gildedrose-lab/
  scorer/
    score.py              # 调度器入口：--task --artifact --run-id
    container_steps.py    # 容器内执行器：按 --step 执行单个步骤
    aggregate.py          # 汇总器
    calibrate.py          # 校准器
    cmake/CMakeLists.txt  # 评分器提供的构建模板
    VERSION               # 评分器版本号
  tasks/<task-id>/        # 题目包，见第 3 节
  calibration/<task-id>/<sample-id>/   # 校准样本，见第 9 节
```

## 3. 输入：题目包

```text
tasks/<task-id>/
  task.json                 # 题目卡的机器可读版
  visible/                  # 给 Agent 的材料清单（源码本身通过只读挂载引用，不复制）
  hidden/
    mull.yml                # 冻结的 Mull 配置：算子、被测源文件路径
    mutation_baseline.json  # 变异分母：变异清单、已判定的等价变异
    reference_tests/        # 参考强测试集
    human_baseline.json     # 人类基线 H1 的评分结果
    variants/<variant-id>/  # 替换版本：只放被替换的源文件
```

`task.json` 的主要字段：

```json
{
  "id": "gildedrose-update-quality",
  "set": "dev",
  "source": {"repo": "...", "commit": "...", "files": {"cpp/src/GildedRose.cc": "<sha256>"}},
  "target_sources": ["cpp/src/GildedRose.cc"],
  "build": {"include_dirs": ["cpp/src"], "link_libraries": []},
  "allowed_test_files": ["tests/*.cc"],
  "existing_tests": {"path": "...", "visible_to_agent": false},
  "budget": {"tokens": 0, "seconds": 0, "repair_rounds": 0},
  "scoring_domain": "quality 0–50；Sulfuras 为 80",
  "params": {"stability_repeats": 10, "shuffle_seeds": [1, 2, 3], "test_timeout_seconds": 10},
  "variants": [
    {"id": "fix-123-before", "kind": "real_bug", "expect": "fail", "files": {"cpp/src/GildedRose.cc": "<sha256>"}}
  ]
}
```

`variants` 始终存在，第一版为空数组。`kind` 取 `real_bug`、`equivalent`、`handwritten` 之一；`expect` 取 `fail` 或 `pass`。

## 4. 输入：运行产物

生成阶段（规格第 3.3 节）为每次运行留下：

```text
trial-<k>/
  generation/        # 首次产物、每轮修复的产物、每轮的编译运行记录
  final/tests/*.cc   # 冻结的最终测试文件
  final/manifest.json   # 文件清单与 SHA-256、冻结时间
  generation/cost.json  # token、耗时、模型调用次数、修复轮次
```

评分器开始前先核对 `manifest.json` 中的哈希。不一致，或出现 `allowed_test_files` 以外的文件，这次运行判为无效，原因记为 `artifact_rejected`。

## 5. 评分步骤详细设计

每个步骤在全新的容器里执行，并写出 `scoring/step-<n>/` 下的原始日志和 `step.json`。测试名一律用 `Suite.Name` 形式。

### 5.1 步骤 1：构建（GCC 镜像）

- 用评分器的 `cmake/CMakeLists.txt` 构建，参数为被测源文件、头文件目录和测试文件；`-std=c++11`，并强制包含 C++11 断言头文件（同工具链验收）。
- **被测源文件直接编进测试可执行文件**（或者用 CMake 的 OBJECT library），不打包成静态库。这样测试文件里如果重新定义了被测函数，会出现重复定义的链接错误，而不是悄悄用假实现替换真代码。
- 测试可执行文件链接 `GTest::gtest_main` 和 `GTest::gmock`。
- 从 `compile_commands.json` 核对：每个编译单元都使用 `-std=c++11`，被测源文件是题目包里哈希一致的那一份。
- 编译或链接失败：运行判为无效，原因 `build_failed`，保存编译器诊断。

### 5.2 步骤 2：发现与执行核对

1. 运行 `--gtest_list_tests` 得到发现的测试清单。
2. 运行 `--gtest_output=json:<file>`。
3. 判定：
   - 没有 JSON 文件：可能是崩溃、自带 `main` 没有调用 `RUN_ALL_TESTS`，或者提前 `exit`。先用 5.3 的单独重跑定位；所有测试都拿不到结果的，运行判为无效，原因 `no_result`。
   - JSON 中的测试集合要和发现清单一致；多出或缺少，判为 `protocol_mismatch`。
   - 发现数为 0，运行判为无效，原因 `zero_tests`。
   - 测试的 `status` 不是 `RUN`，记为 `disabled`；`result` 为 `SKIPPED`，记为 `skipped`。这两类测试都无效，但不影响其他测试。

### 5.3 步骤 3：被测代码上通过

- JSON 中有 `failures` 的测试记为 `failed_on_target`，判为无效（D001：测试写错）。
- 整个进程崩溃或超时时，对每个测试单独运行一次（`--gtest_filter=Suite.Name`，各自一份 JSON、各自计时），据此给出 `crashed`、`timed_out` 或通过。单个测试超时以 `params.test_timeout_seconds` 为准。
- 有效测试 = 已执行、未跳过、通过、未崩溃、未超时的测试。没有有效测试的运行判为无效，原因 `no_valid_tests`。

### 5.4 步骤 4：稳定性

只针对有效测试，全部通过 `--gtest_filter` 限定范围：

1. 重复运行 N 次：启动 N 个独立进程，各自输出 JSON，不使用一次进程内的 `--gtest_repeat`，避免多轮结果混在一个文件里。
2. 乱序运行：对 `shuffle_seeds` 中的每个种子运行一次，参数为 `--gtest_shuffle --gtest_random_seed=<seed>`。
3. 单独运行：每个测试单独运行一次；步骤 3 已经单独跑过的，复用结果。

任何一次结果与步骤 3 不一致的测试记为 `flaky`，从后续步骤中排除，并记录失败次数（S2）。

### 5.5 步骤 5：覆盖率（GCC 镜像）

- 删除全部 `.gcda` 后，只运行稳定的有效测试，然后执行 gcov 文本和 JSON 两种输出。
- 只统计 `target_sources` 中的文件，按文件和合计分别给出行、分支、函数（C1–C3）。函数覆盖从 gcov JSON 的 `functions` 字段读取。
- 题目有已有测试时，另外分别统计“已有测试单独”和“二者合并”的覆盖，算出 C4。

### 5.6 步骤 6：变异测试（Clang 镜像）

- 按工具链说明构建：只给被测源文件加载 Mull 插件，使用题目包里冻结的 `mull.yml`。
- 运行 `mull-runner-19 --allow-surviving --include-not-covered`，输出 Elements 格式的 JSON 报告。
- 只用稳定的有效测试：通过 `GTEST_FILTER` 环境变量限定。**mull-runner 是否把环境变量传给测试进程，实现时要先验证**；不行就改用 Mull 提供的测试程序参数机制。
- 用（算子、文件、行、列）作为变异的标识，与 `mutation_baseline.json` 比对：
  - 变异集合与冻结的分母不一致，说明配置或工具变了，记为基础设施错误；
  - 冻结时已判定为等价的变异，剔除；
  - `Killed` 计入分子；`Survived` 和 `NoCoverage` 只进分母；`Timeout` 单列，不进分子分母；其他状态单列并检查。

### 5.7 步骤 7：替换版本执行（GCC 镜像）

对 `variants` 中的每个版本：

1. 在临时目录中复制被测源码树，用版本文件覆盖对应文件，并核对哈希；
2. 用同一份测试文件、同一个构建模板重新构建；
3. 只运行稳定的有效测试，输出 JSON；
4. 判定：

| 版本期望 | 结果 | 记为 |
|---|---|---|
| `fail` | 至少一个有效测试失败（断言失败或崩溃） | `detected` |
| `fail` | 全部通过 | `not_detected` |
| `fail` | 版本上编译失败 | `build_failed`，单列，不算检出。测试用了修复后才有的接口时会出现这种情况 |
| `pass` | 全部通过 | `clean` |
| `pass` | 有测试失败 | `false_alarm`，并列出失败的测试 |
| `pass` | 版本上编译失败 | 题目问题，记为基础设施错误，修题目 |

列表为空时，步骤 7 直接输出“跳过”，不报错。

### 5.8 步骤 8：成本

读取 `generation/cost.json`，原样写入结果，缺字段时标为缺失，不估算。

## 6. 状态分类

状态的精确判定顺序、由计数算指标和汇总的方法，见[评分算法](评分算法.md)第 3–5 节。

**运行级**

| 状态 | 含义 | 是否计分 |
|---|---|---|
| `scored` | 至少有一个稳定的有效测试，完成了全部适用步骤 | 计分 |
| `invalid` | 产物被拒、构建失败、零测试、无有效测试等 | 计分：端到端 M1 记 0 |
| `infra_error` | 工具链、Docker、评分器自身或题目材料出错 | 不计分，修复后重跑，报告中写明次数 |

**测试级**：`valid`、`disabled`、`skipped`、`failed_on_target`、`crashed`、`timed_out`、`flaky`。只有 `valid` 且不是 `flaky` 的测试进入步骤 5–7。

**变异级**：`killed`、`survived`、`not_covered`、`timeout`、`equivalent`（冻结时剔除）、`other`。

**替换版本级**：见 5.7 的表。

## 7. 输出：结果文件

每次运行输出 `result.json`，主要结构：

```json
{
  "scorer_version": "0.1.0",
  "calibration_report": "<哈希或路径>",
  "task": {"id": "...", "hash": "..."},
  "trial": {"agent_version": "...", "k": 1, "artifact_manifest_sha256": "..."},
  "images": {"gcc": "<image id>", "clang": "<image id>"},
  "status": "scored",
  "invalid_reason": null,
  "tests": [{"name": "Suite.Name", "status": "valid", "flaky": false, "stability_failures": 0}],
  "steps": {"1": {"status": "passed", "log": "scoring/step-1/"}},
  "metrics": {"V3": 0.0, "S1": 0.0, "M1": 0.0, "C1": 0.0, "C2": 0.0, "C3": 0.0, "K1": {}},
  "mutants": {"killed": 0, "survived": 0, "not_covered": 0, "timeout": 0, "equivalent": 0},
  "variants": [{"id": "...", "kind": "real_bug", "expect": "fail", "outcome": "detected", "failed_tests": []}]
}
```

目录沿用规格第 5 节：`runs/<run-id>/tasks/<task-id>/trial-<k>/scoring/` 存放各步骤原始输出，`result.json` 与之并列；`runs/<run-id>/summary.json` 由汇总器生成。

## 8. 隔离、防作弊与版本

**隔离**

- 所有容器沿用工具链验收的隔离参数：禁网、只读根文件系统、资源限制、非 root、丢弃全部 capabilities。
- 源码、测试产物只读挂载；每个步骤只有自己的输出目录可写。
- **运行测试的容器不挂载任何隐藏材料。** 替换版本只在构建时进入容器；变异分母、等价判定、人类基线只在宿主机汇总时使用。这样测试代码在运行时读不到评分答案。

**已考虑的作弊方式与对策**

| 作弊方式 | 对策 |
|---|---|
| 改构建文件、排除测试 | 只接受 `allowed_test_files`，构建模板由评分器提供 |
| 自带 `main`，不运行测试直接返回 0 | 以 JSON 结果为准，没有结果判 `no_result` |
| 静态初始化里调用 `exit(0)` | 同上 |
| 全部跳过或禁用 | 记为 `skipped`/`disabled`，不算有效 |
| 在测试文件里重新定义被测函数 | 被测源文件直接编进可执行文件，重复定义导致链接失败 |
| 把断言宏定义为空、只调用不检查 | 测试仍然有效，但变异检出接近 0，主指标会反映出来 |
| 运行时读取隐藏材料 | 运行容器不挂载隐藏材料 |

**版本与补评**

- `scorer/VERSION` 使用 `主版本.次版本.修订号`：改变任何判定或指标口径，升次版本；只修实现错误、不改口径，升修订号；指标集合整体重构，升主版本。
- 版本号一变，就重跑全部校准样本；校准报告与版本号一起写入每份结果。
- 补评命令（建议）：`score.py --rescore runs/<run-id>`，读取已冻结的产物，用当前版本评分器重新评分，结果写入新的运行目录，不覆盖旧结果。

## 9. 校准样本：目的与形式

校准样本是**评分器的验收标准**：用好坏已知的测试，检验评分器的每个判定是否正确。它们是开发材料，由人手写，任何时候都不提供给被评测的生成 Agent。

每个样本的形式和 Agent 的运行产物完全相同，这样评分器走的是同一条路径：

```text
calibration/<task-id>/<sample-id>/
  final/tests/*.cc
  final/manifest.json
  generation/cost.json      # 填固定的假数据
  expected.json             # 期望结果
```

`expected.json` 分两部分：

- **硬性期望**：必须完全一致的判定，例如运行状态、无效原因、某个测试的测试级状态；
- **相对期望**：指标之间的大小关系或范围，例如“M1 低于参考强测试集的 20%”。

第一批样本都挂在 GildedRose 开发题上。

## 10. 第一版样本清单

| 编号 | 样本内容 | 期望 | 何时启用 |
|---|---|---|---|
| CAL-01 | 测试文件里没有任何 `TEST` | 运行 `invalid`，原因 `zero_tests` | 步骤 1–3 |
| CAL-02 | 所有测试都调用 `GTEST_SKIP()` | 全部 `skipped`；运行 `invalid`，原因 `no_valid_tests` | 步骤 1–3 |
| CAL-03 | 所有测试名带 `DISABLED_` 前缀 | 全部 `disabled`；运行 `invalid` | 步骤 1–3 |
| CAL-04 | 自带 `main`，直接 `return 0` | 运行 `invalid`，原因 `no_result` | 步骤 1–3 |
| CAL-05 | 在静态初始化中调用 `std::exit(0)` | 运行 `invalid`，原因 `no_result` | 步骤 1–3 |
| CAL-06 | 在测试文件里重新定义 `GildedRose::updateQuality()` | 运行 `invalid`，原因 `build_failed`（重复定义） | 步骤 1–3 |
| CAL-07 | 参考强测试集，其中一个断言值故意写错 | 该测试 `failed_on_target`，其余 `valid`；运行 `scored` | 步骤 1–3 |
| CAL-08 | 参考强测试集，加一个空指针解引用的测试 | 该测试 `crashed`（单独重跑定位），其余 `valid` | 步骤 1–3 |
| CAL-09 | 参考强测试集，加一个死循环的测试 | 该测试 `timed_out`，其余 `valid` | 步骤 1–3 |
| CAL-10 | 两个测试共享一个全局变量，后一个依赖前一个先运行 | 依赖的那个测试 `flaky`；S1 > 0 | 步骤 4 |
| CAL-11 | 一个测试按随机数决定成败，失败概率约 50% | 该测试 `flaky`；S2 在 0.2–0.8 之间 | 步骤 4 |
| CAL-12 | 只调用 `updateQuality()`，不写断言 | 运行 `scored`；C1 与参考强测试集接近；M1 低于参考强测试集的 20% | 步骤 5–6 |
| CAL-13 | 断言写法正常，但把 `EXPECT_EQ` 宏定义为空 | 同 CAL-12 | 步骤 6 |
| CAL-14 | 只断言 `sellIn`，不检查 `quality` | M1 高于 CAL-12、低于 CAL-15 | 步骤 6 |
| CAL-15 | 参考强测试集 | 全部 `valid`、无 `flaky`；M1 达到强度阈值 | 步骤 1–6 |
| CAL-16 | 参考强测试集，加一个断言输入域外行为的测试（如 Aged Brie 质量 60 保持 60） | 在“输入域内等价、域外把质量截断到 50”的等价版本上，该测试 `false_alarm`；其余测试 `clean` | 步骤 7 接入等价版本后 |
| CAL-17 | 参考强测试集，在一个手写变异版本上运行 | 版本 `detected` | 步骤 7 接口完成后 |
| CAL-18 | 参考强测试集，在真实缺陷的修复前版本上运行 | 版本 `detected` | 有真实缺陷题后 |

CAL-12、CAL-15 中的数值阈值是初始值：第一次校准后，可以根据参考强测试集的实际分数调整一次，并在校准报告里写明调整前后的值和理由。之后再调整，要升评分器版本。

## 11. 通过标准与运行时机

**通过标准**（全部满足才算校准通过）：

1. 所有已启用样本的硬性期望完全一致；
2. 所有相对期望成立，特别是 M1 的顺序：CAL-12、CAL-13 < CAL-14 < CAL-15；
3. 每个样本评分两次，结果除耗时字段外完全一致；
4. 全部在 Docker 容器内执行，日志和结果保存在独立的运行目录。

**运行时机**：

- 评分器每次修改后、合并之前；
- 每轮正式评测开始前；
- 工具链镜像变化之后。

校准报告列出每个样本的期望、实际结果和是否一致，与评分器版本号一起保存；正式评分结果引用这份报告。

**维护**：每新增一个评分步骤，同时补充覆盖该步骤的样本；样本文件冻结并记录哈希。修改样本等同于修改评分器的验收标准，要升评分器版本。
