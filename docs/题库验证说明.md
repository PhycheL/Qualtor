## 2. 在 Docker 机器上验证

所有命令都从仓库根目录执行。

**第 1 步：确认环境与校准状态**

```bash
python3 evaluator/toolchains/toolchains.py --skip-build
python3 -B -m unittest discover -s evaluator/runner/tests -p "test_review_regressions.py"
```

第二条命令应全部通过，其中包括新增的 `TaskSelectionTest`。

**第 2 步：批量标定变异分母**

```bash
python3 benchmark/tools/prepare_new_tasks.py --write --jobs 2 --run-id bank-prepare-<日期>-01
```

- 脚本找出所有还没有 `hidden/mutation_baseline.json` 的题，逐题调用 `prepare_task.py baseline`。每道题有各自的 run，名称为 `<run-id>-<题目 ID>`。
- 每道题要用参考测试和探针各跑两遍完整评分（含 Mull），全量耗时较长，建议放在后台运行。
- 写入前应用 `benchmark/tools/mutant_review/<题目 ID>/confirmed.json`：已确认不等价、却仍被探针判为等价候选的变异移回分母，并重算参考 M1（第 8 节）。
- 只有全部检查都通过、移回后参考 M1 仍达标的题才会写入 `mutation_baseline.json`；没通过的题留在“未标定”状态，runner 会自动跳过。
- 结果汇总在 `runs/<run-id>/summary.md` 和 `summary.json`。

补强后的 40 道题及后续补写测试的 6 道题均已完成重标定（第 9、11 节），当前默认命令没有待标定题可选。修改已有题目材料后，用 `--tasks <题目 ID> --write --force` 指定重标定；单题准备入口 `prepare_task.py` 不读取 `mutant_review/`，题库题目应使用本脚本。使用新的 run 保留历史证据。历史分母不能仅因文件存在就认定适用于新材料。

**第 3 步：按汇总处理问题**

| 现象 | 常见原因 | 处理 |
|---|---|---|
| 参考测试或探针的某些测试 `failed_on_target` | 生成型断言在 Linux 上的结果与 macOS 不同，多见于浮点数学函数 | HumanEval-X、Tennis、Parrot：在本机重跑生成脚本，或删去这些断言；手写题按 Linux 上的实际输出改断言（D001） |
| 生成型探针题的参考 M1 低于 0.8 | 参考测试只取了每个函数的前 12 个输入 | 补充参考测试后重新标定 |
| `reference_copy` 题的原始检出率低于 0.8 | 上游测试或手写测试较弱 | 题目照常写入分母，但要列入待补强清单，优先补强后再用于正式比较 |
| `clang_build_failed` 或其他基础设施错误 | GCC 与 Clang 的差异 | 人工排查，必要时把题目移出本批 |
| 等价候选或不稳定变异较多 | 探针不是穷举，或变异引入了未定义行为 | 第 4 步人工复核 |

**第 4 步：人工复核等价候选**

按[评测运行说明](评测运行说明.md)第 3 节逐题复核，整题结论充分、分母及参考强度一致后再把 `review.status` 改为 `reviewed`。当前逐项证据与修订草稿见第 7 节。题目较多时建议按以下顺序：
1. 生成型探针的题：候选少，复核快；
2. 中等层的题；
3. `reference_copy` 的题：复核时把不等价的变异移回分母。

**第 5 步：端到端冒烟**

挑几道不同类型的题，用当前模型配置各跑一次：

```bash
python3 evaluator/run.py --config default \
  --tasks humaneval-x-cpp-01 exercism-clock tennis-refactoring-4 racing-car-tire-pressure theatrical-players-statement \
  --trials 1 --jobs 2 --run-id eval-bank-smoke-<日期>-01
```

这一步确认新题能走通“生成 → 编译反馈 → 独立评测”。其中：
- `racing-car-tire-pressure` 只编译 `Alarm.cpp`，Agent 需要自己在测试里提供 `Sensor` 替身；
- `theatrical-players-statement` 的可见文件含约 900 KB 的 `json.hpp`。

**需要带回的结果**：第 2 步的 `summary.md` 与 `summary.json`，第 5 步的 `summary.json`，以及第 3 步中改动过的题目清单。

## 4. 重建题目

以下命令在装有 Apple clang（或其他支持 ASan/UBSan 的 clang）、GCC 14 和用 GCC 14 构建的 GoogleTest 1.12.1 的机器上执行。

- 提交号固定为：

| zai-org/CodeGeeX（HumanEval-X 数据，SHA-256 `dcf2e280…6dbb0`） | `2838420b7b4492cf3d16bce5320e26e65960c9e2` |

| Parrot | `28fe97be…` |
| Racing-Car | `6584af9b…` |

kata 的完整提交号见各题 `source/SOURCE.json`。

```bash
export QUALTOR_HOST_CMAKE=<cmake> QUALTOR_HOST_NINJA=<ninja> QUALTOR_HOST_GTEST=<GCC 版 GoogleTest 前缀> QUALTOR_HOST_CXX=g++-14
python3 benchmark/tools/import_exercism.py --source <exercism/cpp 解压目录> --commit <提交号> --force
```

- 生成型探针用固定种子（20261027）和自带的伪随机数生成器，同一平台上重跑结果一致。
- 重建时，材料与原来完全相同的题会保留已有的 `mutation_baseline.json`；材料有变化的题，分母作废，脚本会提示“需重新标定”。此后用 `prepare_new_tasks.py --write` 补标定：默认选择所有没有分母的题。

## 6. 第二轮处理（2026-10-27）

针对第 5 节发现的问题：

| 问题 | 处理 | 结果 |
|---|---|---|
| `humaneval-x-cpp-17` 的 `minPath` 崩溃 | 原生成器两遍填充都让未初始化的 `x`、`y` 取 0 或负值，恰好不越界。改为带 ASan 与不带 ASan 两种构建、不同栈与堆填充共跑 4 遍，只保留每遍都正常结束且结果相同的输入；全部生成型题按新规则重建 | 第 17 组网格不含 1 的输入全部被过滤。第 15 组 `maximum` 的 50 个越界输入（`k` 大于数组长度）、第 02 组 `string_sequence` 的 1 个输入一并去掉：首轮在 Linux 上碰巧没有崩溃 |
| hello-world、reverse-string 没有变异；linked-list 的 `.cpp` 是空壳 | 三题移出题库；导入脚本写明排除原因，并检测没有函数实现的 `.cpp` | 零变异题的口径作为 R-06 的一部分提出（[题库构建方案](题库构建方案.md)第 2 节） |
| SupermarketReceipt、Tennis 4 覆盖率不可用 | 评测模块升为 0.1.6：gcov JSON 同一行的多条记录按行合并，函数按名称与起始行合并，文本只取合并行；只有 `.gcno` 没有 `.gcda` 的被测源文件按 0/0 计入（[评测运行说明](评测运行说明.md)第 12 节） | 单元测试通过，其中新增的 `CoverageMergeTest` 用首轮 tennis4 的真实 gcov 输出作夹具；尚未在 Docker 中校准 |

1. **Telemetry 固定随机种子并不使分支变异都等价。** 长调用序列检出了 8 个候选中的 7 个。剩下 `disconnect` 的一项在实际 IR 中为 `store i8 42`，读取时 `trunc i8 to i1` 得到 false；这是该 IR 的效果，不是标准 C++ 中 `bool = 42` 的语义。
2. **第 11 组 grade 的 24 个阈值比较等号不可达。** IR 将 float 提升为 double，而 12 个 double 十进制阈值均不能由 binary32 精确表示。因此严格/非严格比较相同，不能把这些候选都归因为随机输入遗漏阈值。其他函数仍可受益于边界种子。
3. **源码的“删除调用”可能没有删除表面看到的函数。** 同位置的多个内部变异可能共用 Mull ID，实际选中的是其中一个。Secret Handshake、Tennis 4、grade 的相关项删除了空 allocator 析构，原调用仍执行；删除实际 string/map 析构则可能影响资源释放，需要另行核验。已保存 IR，并修正 `mutant_report.py` 的提示和“源码示意”表头。
