# Qualtor 项目执行细则

适用于本仓库内的实施与验证。项目目标、技术路线、当前起点和按任务阅读的入口由根目录 [AGENTS.md](../AGENTS.md) 维护；本文件维护具体执行要求。用户在当前任务中的明确要求优先。

## 沟通与任务范围

- 代码标识符、命令及原始日志保留原文，进度说明、结论和交付说明使用中文。
- 先用大白话说明结果，再提供必要的技术细节和证据。默认简洁；只有用户要求时才生成详尽报告或附件。
- 用户要求讨论、解释或“不改任何东西”时，只做必要的只读核查，不修改文件、不运行会产生实验产物的命令。

## 文档与源码

- 根目录 `README.md` 保留文档导航，`AGENTS.md` 维护项目目标、技术路线和协作入口；详细规则、说明、规划和报告统一维护在 `docs/`，并更新 [文档索引](README.md)。上游源码说明和冻结评测输入保持原位。
- 实现生成入口、测试框架接入或新评测能力后，同步更新实现状态和运行说明；以实现和本轮原始结果为准，区分已实现、已验证和待实现。
- 搜索代码时优先限定 `gildedrose-lab/scripts/`、`gildedrose-lab/toolchains/` 和目标源码，避免把运行产物、日志和生成报告当作实现代码。

## C++ 与 Docker 边界

- 当前上游范围是 `external/GildedRose-Refactoring-Kata/cpp/`，路径相对 `gildedrose-lab/`。保留整个 `cpp/` 所需源码、头文件和构建配置；`.cc` 也是 C++，不要仅按 `.cpp` 后缀筛选或擅自改名。Python 是自动化调度语言。
- 仓库源码保存在宿主机，通过 bind mount 引入容器；Docker 镜像只安装工具链。保持构建上下文限定在 `gildedrose-lab/docker/`，不得用 `COPY`、`ADD` 把项目源码打包进镜像。
- 用 Docker 中的实际编译、测试和覆盖率结果证明闭环可用。宿主机检查可以辅助定位问题，但不能替代容器验收。保留评测执行容器的禁网、资源限制和只读源码挂载；首次构建下载依赖和生成器的模型 API 调用单独配置。
- 保持上游源码快照及其提交、文件哈希可追溯。测试生成和 Bug 注入使用独立工作目录、副本；不得通过改动原始业务代码、评分器或参考答案来抬高生成测试的成绩。

## 生成与评测规则

- 每项生成任务明确：目标代码、可见上下文、测试框架、允许修改的文件、生成及修复预算。沿用项目适用的框架；新增框架时同步接入构建和测试发现。
- 正式评测使用独立的生成上下文和受限工作区，只提供允许的源码、接口和构建材料。隐藏评分用的 Bug、参考答案、测试及历史评分输出；不要把整个 `/lab` 挂给生成 Agent。只读挂载不能防止答案泄漏。
- 上述隔离针对被评测的生成 Agent。维护系统的开发 Agent 可以读取评分实现和历史证据；已经用于调试的题目应归入开发集。
- 记录首次生成产物与每次修复，分别报告首次成绩和预算内修复后的成绩。进入隐藏评分前冻结产物和哈希；新的尝试使用独立记录。
- 确认生成测试实际被发现、执行并检查行为。零测试、跳过全部测试、空断言或仅“编译成功”不能判定为有效测试。
- 模型生成的测试独立评分，原有规则测试仅作对照。评价补充测试的增益时，分别运行原有测试、生成测试及二者组合，并清理或隔离覆盖率数据，避免把原有成绩计入生成测试。
- 覆盖率仅统计指定业务源码，并说明分母。区分用例记录数、互异输入数、测试函数数和评测任务数；覆盖率不是断言正确性或 Bug 检出能力的证明。
- 行为变异检出、编译/链接错误捕获、等价改动对照分别统计。有效变异未被覆盖仍属于未检出；无法构建、已确认等价、超时和基础设施错误单列说明。测试框架的断言失败可能返回非零退出码，应按实际结果分类，不能一律当作工具故障。
- 比较 Agent/skill 时固定任务集、模型配置和预算，记录源码、提示词、Agent、skill 与工具链版本；分开开发题和未参与调试的验收题，多次运行并按任务或项目汇总。
- 结果至少说明可用性、正确性、缺陷检出、覆盖范围、稳定性与成本。将失败归因到可改进的环节，避免只报总分或挑选最好的一次。

## 执行、证据与完成条件

- 从项目根目录使用 `python3 gildedrose-lab/toolchains.py` 构建并验收两套工具链；镜像已存在时可加 `--skip-build`。具体参数和前提见 [实验说明](实验运行说明.md)。
- 变异分母标定、评分器校准、评分和汇总按 [评分器运行说明](评分器运行说明.md) 执行。修改评分器、校准样本或题目材料后重新校准；正式比较只使用校准状态为 passed、同一评分器版本的结果。
- 每轮使用新的运行目录。保留历史成功和失败记录、冻结答案与原始日志，不覆盖旧结果来制造通过。当前结果位于 `gildedrose-lab/runs/<run-id>/summary.json`，对应证据位于 `gildedrose-lab/artifacts/toolchains/<run-id>/`；`artifacts/latest-run.txt` 仅定位旧实验记录。
- 实验命令沿用 `scripts/audit.py` 的记录机制，保存命令、时间、退出码、stdout、stderr 及必要输入；日志中不写入密钥。报告结论应能追溯到本轮容器、构建和测试证据。
- 修改编译、覆盖率或变异流程后，运行与改动相关的 Docker 验证；新增生成评测能力时，验证实际生成测试的接入与评分，不能只靠旧规则测试通过。纯文档改动核对内容和引用路径即可。
- 完成时说明改了什么、实际验证了什么、结果和证据位置，以及尚未验证的部分。Docker 不可用或检查未通过时如实说明，不能宣称已经跑通。
