## D001 断言以被测代码的实际运行结果为准

- **日期**：2026-10-22
- **决定**：Agent 全自动读取已有 C++ 代码并生成单元测试，断言的预期值以被测代码的实际运行结果为准。代码是否符合需求，由后续的功能测试负责，不属于本阶段。
- **理由**：
  - Agent 是全自动的，用在生产环境。
  - 需求文档难以维护，从需求文档自动拆解出断言效果不可靠。
  - 以实际行为为准时，测试在被测代码上失败就能直接判定为测试写错，评分可以全自动完成。
- **放弃的选项**：以需求文档为准生成断言，用来发现已有缺陷。
- **代价**：被测代码本身的缺陷会被测试一起锁定，留给后续功能测试发现。
- **前提（制定时待确认）**：生产环境里，Agent 能拿到目标项目的构建环境，在沙箱中编译、运行代码。
- **现状（2026-10-26）**：D013 产品已提供可独立交付的 GCC/Docker 编译反馈；任意项目的构建适配仍需按项目验证，当前支持范围见[产品 README](../agents/README.md)。

## D002 评分范围收窄，替换版本统一执行

> 第 2 条的规模由 D017 修订：开发集真实缺陷题至少 20 道、等价版本题至少 10 道；验收集真实缺陷 3–5 道保留。

- **日期**：2026-10-23
- **决定**：
  1. 不做 sanitizer、极端变异和静态扫描（断言密度、无断言测试、脆弱写法），对应指标 M3、F2、A1、A2 从评测规格中删除。
  2. 保留真实缺陷和等价版本，小规模实施：真实缺陷 3–5 道验收题，等价版本 2–3 道开发题。
  3. 优先级：先打通主链路（构建、执行核对、稳定性、gcov、Mull），然后是真实缺陷，最后是等价版本。
  4. 手写变异、真实缺陷、等价版本在评分器中统一为“替换版本执行”步骤，第一版就实现接口，题目格式始终保留替换版本列表，列表可以为空。
- **理由**：
  - 只调用不断言、断言无效的测试，Mull 的检出率本来就接近 0；断言密度和脆弱写法这些信号，变异测试和等价版本覆盖得更直接。
  - sanitizer 抓的测试自身未定义行为，在当前阶段意义很小，重复运行也能暴露其中一部分。
  - 真实缺陷是验证“变异检出率高等于测试有用”的唯一真实世界证据；等价版本是唯一检查误报的手段，防止评分被“写死实现细节”的测试钻空子。
  - 两者在评分器里是同一个动作，先留好接口，以后补的是题目数据，不需要改评分器。
- **放弃的选项**：把 sanitizer、极端变异、静态扫描排在后面实施；给每道题都配真实缺陷和等价版本。
- **代价**：测试自身的未定义行为（例如悬垂引用）不会被专门检查，可能出现“碰巧通过”的测试。
- **重新评估的条件**：错误分析中发现这类问题频繁出现，或者这类问题影响了版本比较的结论。

## D004 生成在容器中运行：只读挂载、无 bash、直接联网

> **部分已被 D013 替代。** 下文保留 2026-10-24 的决定；现行 pi 在宿主机运行，生成 C++ 在禁网 Docker 中编译执行。工具白名单和 Agent 驱动修复的约束仍保留。

- **日期**：2026-10-24
- **决定**：
  1. 生成 Agent 在 Docker 容器中运行；生成镜像以 `qualtor-gcc` 为基础加装 node 24，由 `toolchains.py` 构建。pi 目录只读挂载进容器。
  2. 只挂载本 trial 需要的材料；被测代码只读挂载、不复制；隐藏材料不进入生成容器。
  3. Agent 只有 `read`、`write`、`edit`、`grep`、`find`、`ls`、`build_and_test` 七个工具，不提供 bash。
  4. `build_and_test`、路径门卫、轮次计数与快照以框架自己的 pi 扩展实现，与被评测配置分开。
  5. 生成容器直接联网，API 地址和密钥由环境变量传入；评分容器保持禁网。测试进程暂不断网。
- **理由**：pi 自身不构成安全边界，隔离要靠容器；有 bash 就能绕过修复轮次计数；没有 bash，Agent 没有可联网的工具，不需要出口代理；API 地址会变化。
- **放弃的选项**：宿主机上靠权限配置运行；按域名白名单的出口代理；不限次数的探针工具。
- **代价**：Agent 了解代码实际行为只能通过 `build_and_test`，会消耗修复轮次；修复阶段可联网而评分阶段禁网，依赖真实网络的测试会在评分时失败。
- **重新评估的条件**：出现需要联网的被测代码（届时让测试进程断网运行）。

## D005 修复由 Agent 驱动，只限制修复轮次

- **日期**：2026-10-24
- **决定**：
  1. Agent 自己决定何时调用 `build_and_test`；它只返回编译错误和每个测试的通过/失败及失败信息，不返回覆盖率、变异结果，也不运行替换版本和参考测试。
  2. 修复包括编译失败和在被测代码上运行失败（按 D001 属于测试写错）。
  3. 首次产物为第一次调用 `build_and_test` 时的工作区，这次不算修复；之后每次调用算 1 轮；用满 N 轮后拒绝执行。N 写进 `task.json`，初始值 3。
  4. 预算只限制修复轮次，token 与时间只记录。另设无响应看门狗：pi 连续 15 分钟无任何事件即终止，记为 `generation_stalled`。
  5. trial 结束状态分为 `finished`、`budget_exhausted`、`never_built`、`generation_stalled`、`agent_error`；`agent_error` 用全新工作区重跑，最多 2 次。
- **实现细化（2026-10-26）**：首次产物在首次编译前保存为测试快照；看门狗默认 900 秒无进展，编译时暂停、心跳不算进展；新增用户取消状态 `cancelled`，清理并保留产物、不重试。详见[接口与运行边界](接口与运行边界.md#结束与重试)。
- **修订**：2026-10-25 的 [D012](#d012-基础设施重试耗尽即停止生成整轮修订-d005) 补充第 5 条：`agent_error` / `infra_error` 耗尽重试后，取消未开始的 trial，生成整轮记为 `failed`；替代此前“单个 trial 记缺失、其余继续”的处理口径。
- **理由**：修复策略由 Agent 决定，才能评出 Agent 与 skill 的差异；评分信息一旦反馈给 Agent，Agent 就会针对指标优化；大代码库所需时间无法事先确定，只能检测卡死。
- **放弃的选项**：编排器驱动的固定修复循环；token 和墙钟预算；60 分钟总时长上限。
- **代价**：Agent 若一直读文件不结束，看门狗抓不到；暂不设模型调用次数上限，出现后再加。

## D006 run 是一次执行，补评写进原 run

- **日期**：2026-10-24
- **决定**：
  1. run 是一次实际执行的记录。同一配置执行两次就是两个 run，互不干扰。一个 run 包含所选题目的 K 个 trial（K = 5）。
  2. 一个 run 的全部内容（配置快照、工作区、每轮快照、冻结产物、日志、成本、评分）放在同一个 run 目录。
  3. 评分器升级后的补评写进原 run，按评分器版本分子目录，旧结果原样保留、不覆盖；汇总时指定评分器版本。
  4. 生成入口一条命令完成“生成 → 修复 → 冻结 → 评分 → 汇总”；评分器校准状态不是 passed 时拒绝运行。
- **理由**：一次执行的证据集中一处，便于追溯；补评属于原执行，按版本分目录同样满足“不覆盖旧结果”。
- **放弃的选项**：run 等同于一份配置；补评另开 run。
- **代价**：评分器版本多了以后，run 目录里会积累多份评分结果。

## D011 等价版本必须在全部输入上等价

- **日期**：2026-10-25
- **决定**：
  1. 等价版本须在被测代码**全部无未定义行为的输入**上与被测代码行为一致，不再以评分输入域为界。评分输入域只约束参考强测试集和有界穷举探针。
  2. 删除 GildedRose 的 eq-01（把质量截断到 0–50），新增 eq-02：按商品种类拆成独立函数的重构，只在 `sellIn == INT_MIN` 时与原代码不同；原代码在该输入上执行 `sellIn - 1` 会发生有符号溢出，属于未定义行为。等价性用 `hidden/variants/differential_check.cc` 在大范围输入网格上与原代码逐一比对确认。
  3. 断言评分输入域之外真实行为的测试（例如质量 60 的商品）按正常测试计分，不算误报。CAL-16 改为同时包含一条这样的测试和一条依赖有符号溢出的测试：前者在 eq-02 上必须通过，只有后者应判为误报。
  4. 评分器升为 0.1.3，在 Docker 中重新校准；已有的真实运行结果在原 run 中按 0.1.3 补评。
- **理由**：
  - 按 D001，被测代码的实际运行结果就是标准答案。质量 60 时给出 59 还是 50 是一处真实的行为差异，eq-01 实际上是一个在边界外改了行为的变异，不是等价版本。
  - 评分输入域对 Agent 不可见，代码本身也不检查输入范围。Agent 照实际行为写出的正确测试被判为误报，F1 量到的是“测了多少域外输入”，而不是测试是否脆弱。2026-10-24 的真实 K=5 运行中，12 份产物在 eq-01 上全部判为误报，原因都是这一点。
  - 等价版本真正等价后，测试在它上面失败只可能是因为锁死了实现细节或依赖未定义行为，这才是 F1 要抓的脆弱测试。
- **放弃的选项**：
  - 把输入域写进 `TASK.md`：生产环境里没有人告诉 Agent 输入范围，评测会比实际使用偏好。
  - 只用评分域内的测试计算 F1：评分器要先自动提取每条测试的输入，对任意 C++ 测试难以做到可靠，会引入新的噪声。
- **代价**：GildedRose 这类纯计算代码很难写出既真等价、又能让“只断言输出”的测试失败的改写，F1 在这道题上大概会接近 0，区分度要靠以后更复杂的题目。CAL-16 依赖 `-O0` 下有符号溢出按补码回绕的固定行为，换编译器或优化级别时要重新确认。
- **修订**：CAL-16 原先“断言输入域外行为应判误报”的设计意图（见[评测实现与校准样本](评测模块与校准样本设计.md)第 10 节）作废。

## D015 只在未定义行为或资源耗尽时才不同的变异不计入分母

- **日期**：2026-10-28
- **状态**：由开发 Agent 按“能定的直接定”提出并实施，用户可推翻；推翻时只需改 `confirmed.json` 的判定并重新落实，评测代码不受影响。
- **决定**：
  1. 变异与原代码的差异只在未定义行为（越界访问、整数除零、有符号溢出、无效迭代器等）下出现时，复核判定为 `undefined_only`，列为不稳定变异，不计入 M1 分母。原先“sanitizer 证实 UB 即移回分母”的 10 项一并改判。
  2. 差异只在资源耗尽时出现（分配失败、超过 `max_size`、泄漏）的变异，按等价处理，在 `equivalent.json` 写明理由。
  3. 准备工具发现参考测试检出、而包含全部参考测试的探针未检出时，不再列为等价候选，改列为不稳定：探针含有全部参考测试，两者结果不同只能来自二进制差异，多为未定义行为。
  4. 只在部分输入上越界、在其他有定义输入上有确定差异的变异（如把 `length()` 换成 42，长度超过 42 时会截断），仍按普通变异处理，应补测试检出。
- **理由**：
  - 评测不带 sanitizer（D002），同一个 UB 变异在不同二进制、不同执行条件下可能幸存或崩溃。实测中，第 18 组 `cpp_141.cc:27` 被参考测试两轮检出、探针两轮幸存；Rail Fence 第 14 行在正式 Mull 中幸存，单独回放时崩溃；第 16 组两项在一轮中归为不稳定，下一轮又成了等价候选。把这类变异放进分母，被评测测试能否“检出”取决于内存布局，是噪声而不是测试质量。
  - D011 已规定等价版本只在无未定义行为的输入上要求一致，依赖未定义行为的测试被视为脆弱测试；分母口径与此保持一致。
- **代价**：越界、除零这类真实缺陷不进入 M1；如以后评测引入 sanitizer 运行，需要重新讨论。资源类差异（如 `reserve` 参数变化）不计入，测不出内存效率问题。
- **版本**：第 3 点改变了 `prepare_task.py` 的分类，随 R-08 一起把评测模块升为 0.2.0，需在 Docker 中重新校准；第 1、2 点只改题库数据（`benchmark/tools/mutant_review/`）。

**D018-2 头文件覆盖率**
- 插桩范围：有 `target_headers` 的题，覆盖率构建要给全部编译单元插桩（测试、依赖源文件和被测源文件），原因有两个：
  - 头文件里的代码在测试单元中实例化；
  - 内联函数和模板实例是 COMDAT。链接器如果保留了未插桩单元里的那份副本，计数会丢失，覆盖率就会取决于链接顺序。
- 统计范围：只统计被测头文件，依赖文件自身的行仍不计入。Mull 插件仍只加在被测源文件上。
- 冻结分母：
  - 行按行号跨编译单元合并；
  - 函数按 `(start_line, start_column)` 合并各实例，任一实例执行过即算覆盖；
  - 分母来自参考测试的覆盖率运行，写入 `hidden/coverage_baseline.json`；
  - 必要时可加只在准备阶段编译的显式实例化文件，放在 `hidden/coverage_instantiation/*.cc`，评分时不编译；
  - 产物的 C1 和 C3 只在冻结集合上计算。冻结集合之外的行不计入，只记数量供诊断；
  - 每个被测头文件至少要有一行冻结代码。
- C2：头文件分支在各实例之间没有稳定的对应关系，纯头文件题的 C2 记为不适用（⊥）。
- 题目指纹：`coverage_baseline.json` 与 `mutation_baseline.json` 一样只取实质内容（各头文件的哈希、冻结行和冻结函数），时间、run-id 等元数据不进指纹。重建题目时与 `mutation_baseline.json` 一样保留。
- 没有 `target_headers` 的题，覆盖率语义、插桩范围和编译命令全部保持不变。

实现说明：gcov 文本与 JSON 按编译单元核对。Docker 实测发现，同一编译单元的模板分支在文本输出中也可能省略部分实例；纯头文件题逐行核对原始执行计数，C2 仍为不适用。旧源码题继续核对行、全部分支和非异常分支三项统计。

**D018-3 M1 适用性**
- 两种情况下 M1 不适用，原因记为：
  - `header_only`：`target_sources` 为空；
  - `zero_mutants`：准备阶段 Mull 输出 “No mutants found”，且没有报告，证据保存 stdout。
- 题目的状态由冻结分母 `mutation_baseline.json` 记录：`"mutation": {"applicable": false, "reason": ...}`，`mutants` 为空。分母的实质内容只在存在这个键时才加入它，旧题的指纹计算结果不变。
- 结果的表示：
  - M1 不适用的题，无论产物状态如何（包括 invalid），`M1_e2e` 和 `M1_valid` 都为 ⊥；
  - 结果中记 `not_applicable: {"M1": 原因}`，纯头文件题另记 `"C2": "header_only"`；
  - 评分时不运行 Mull。
- 汇总与比较：
  - 汇总照常跳过 ⊥，但把“不适用”和“缺失”分别计数；
  - 比较时，M1 不适用的题不进入 M1 配对集合，在结论中写明排除了多少题；
  - 主指标的定义和守护指标规则都不变。
- 适用 M1 的题，如果评分时 Mull 没有出报告，仍按 `infra_error` 处理。

**D018-4 不适用 M1 的题，用手写变异衡量缺陷检出**
- 数量：每题至少 5 个手写变异。被测代码有效行数不超过 30 的小题（leap、two-fer、hello-world、reverse-string）至少 3 个。
- 每个变异的要求：
  - `kind: handwritten`，`expect: fail`；
  - 只改一处语义，模拟常见缺陷，例如边界、比较、遗漏分支、错误常量、状态没有更新；
  - 能和参考测试一起编译，由测试失败检出，不能靠编译失败检出；
  - 差异必须出现在有定义的行为上，只在未定义行为下不同的变异不能用（D015）。
- 存放：源文件是 `benchmark/tools/handwritten_variants/<题目 ID>/` 下的 patch 和说明，由导入脚本生成到 `hidden/variants/`，保证重建时逐字节一致。
- 这类题的缺陷检出看 M2；有真实缺陷时另看 M4。产物无效的情况由 V2 反映，不新增指标。

**D018-5 准入**
- M1 适用的题：准入条件不变。
- M1 不适用的题，需要同时满足：

  - 参考测试的 C1 达到 `reference_min_c1`。纯头文件题按冻结分母计算，零变异题按普通行覆盖计算；
  - 手写变异数量达标，并且全部被参考测试检出；
  - 真实缺陷版本全部被检出，等价版本全部通过；
  - 没有标为 pending 的结论。
- `reference_min_c1` 的缺省值为 0.8，只在 M1 不适用时读取，不写进旧题的 `task.json`。
- 没有变异分母可用的题，探针不是必需的。

**D018-6 R-07 替换头文件**
- 可替换的文件：
  - 被测源文件、被测头文件和可见头文件；
  - 依赖源文件仍不能替换（D017），不可见的文件也不能替换。

- 不采用“覆盖目录放在 -I 最前面”的做法。同目录用引号包含的头文件会先在包含它的文件所在目录查找，已核实 103 题中有 97 题是这种写法。

**D018-7 步骤 A 遗留项**

## D019 Clang 测试编译失败只影响 M1

- **日期**：2026-10-29
- **状态**：已实现并通过 assessment 0.4.1 完整 Docker 校准与冻结产物补评；按用户建议先独立提交决定，再实施。
- **背景**：Emitter 的首次冻结测试包含越界十六进制转义，GCC 警告后构建成功，Clang 将同一位置判为错误。旧实现把全部 Clang 构建失败记为 `infra_error`，无意义重试后触发 D012，阻止后续题目。Clang 仅负责 Mull，不决定 GCC 下的有效性与覆盖率。
- **决定**：
  1. GCC 已通过有效性门槛，Clang 编译失败的全部错误诊断均明确定位到 `/product/tests/` 内已冻结测试文件时，记为产物的 M1 评测失败。错误来源使用完整编译日志判断，不能只检查截断后的诊断摘要。
  2. 结果保留 GCC 的有效性、覆盖率及替换版本评测，`M1_valid` 为 `null`（⊥），`M1_e2e` 为 0；在 `metric_failures.M1` 记录 `clang_test_compile_failed`、诊断及证据位置。该字段不同于题目级 `not_applicable.M1`，不缩小变异分母，也不把题目改为不适用。
  3. 此类结果不记 `infra_error`，不重试，也不触发 D012；现有 runner 按状态处理即可。配置失败、超时、链接失败、业务源码/依赖错误、混合来源或不能可靠归因的失败仍为基础设施错误。准备阶段的参考测试发生此类失败仍阻止分母准备。
  4. 纯头文件和零变异题继续按 D018 跳过 Clang/Mull，两项 M1 均为 `null`。旧源码题正常构建和评分的规则不变。
- **验证**：增加 CAL-29，以越界转义锁定 GCC 成功、Clang 测试编译失败时的指标和原因；同轮重新校准后，用 `--rescore` 补评 Emitter 首次冻结产物，保留旧评分和失败运行记录，不重新生成。


## D020 第三方构建环境与代码生成（步骤 C）

- **日期**：2026-10-29
- **状态**：用户已批准定稿并实施；按[步骤 C 执行计划](步骤C执行计划.md)执行，实际验证另记。
- **理由**：一份锁定依赖配方同时供独立产品与评测使用，在保留固定基础工具链、旧题语义及禁网执行边界的前提下，支持第三方库、moc、protoc 和预生成配置头。
- **规则调整**：AGENTS.md 已按用户确认允许镜像安装配方锁定版本的依赖，业务项目源码仍只在运行时只读挂载。

**D020-1 构建环境**
- 构建环境由配方定义，一份配方生成两个派生镜像：
  - GCC 版：以固定 GCC 镜像（按 ID）为基础；
  - Clang 版：以固定 Clang/Mull 镜像（按 ID）为基础。
- 配方的内容：
  - 只能使用基础镜像已配置的同一快照 `20261021T000000Z`；
  - 顶层包写精确版本，安装时带 `--no-install-recommends`，传递依赖由快照固定；
  - 不允许执行脚本、下载源码或改动已安装的包。
- 存放与构建：
  - 配方放在 `agents/toolchains/environments/<名称>.json`，产品是独立交付物，需要持有这份配方；
  - 评测侧的 `evaluator/toolchains/toolchains.py` 读取同一个文件，与它读取 `agents/toolchains/images.json` 的做法相同；
  - 两个构建上下文各有一个只放行自身 Dockerfile 的 `Dockerfile.environment`：GCC 版在 `agents/toolchains/docker/`，Clang 版在 `evaluator/toolchains/docker/`。基础镜像和包列表通过构建参数传入。
- 镜像命名：`docker.io/library/qualtor-env-<名称>-gcc:<配方 sha256 前 12 位>`，Clang 版把 `-gcc` 换成 `-clang`。
- 每种架构都要保存：完整包清单（`dpkg-query`）、镜像 ID、冒烟测试输出。

**D020-2 题目字段（两份契约同步修改，保持逐字节相同）**
- `build.environment`：环境名，必须有对应的配方。
- `build.link_libraries`：CMake 导入目标的列表，例如 `OpenSSL::Crypto`、`ZLIB::ZLIB`、`protobuf::libprotobuf`、`Qt5::Core`、`Boost::headers`。只能取配方中声明的目标。只用 Boost 头文件时写 `Boost::headers`。
- `build.codegen`：对象列表，每项的写法如下：
  - `{"tool": "moc"}`：对整个测试可执行文件开启 AUTOMOC，被测、依赖和测试编译单元都会生效；
  - `{"tool": "protoc", "inputs": [".proto 路径"], "import_dirs": [目录]}`。
  - 写了 `codegen` 的题，必须同时声明环境，并链接对应的库。
- 不提供自由的头文件目录、链接参数或 CMake 片段。第三方头文件只能来自系统路径或导入目标。
- 有构建环境的题，不允许使用 `-fsigned-char`、`-funsigned-char`：预编译库按平台默认的 char 符号编译，改了会不一致。
- `.proto` 等生成器输入必须可见，并在 `source.files` 中登记。后缀白名单只为生成器输入增加 `.proto`，它不作为编译单元。
- 没有这几个字段的题，语义和编译命令完全不变。

**D020-3 生成单元与预生成文件**
- 生成器的输出只写到构建目录。
- 编译命令核对新增一类“生成单元”，按题目声明推出期望集合：
  - moc：AUTOMOC 的产物；
  - protoc：每个输入对应的 `<名称>.pb.cc`。
- 生成单元必须与其他单元一致的项：语言标准、断言头、宏、选项。
- 生成单元不能有的项：
  - 不加载 Mull 插件，不进入覆盖率统计或变异范围；
  - 不加覆盖率插桩。纯头文件题按 D018-2 给全部单元插桩时例外，但统计时仍会被过滤掉。
- 导入目标会自动带来一些编译选项，例如 `QT_CORE_LIB`、`QT_NO_DEBUG`、系统头文件目录，AMD64 上的 Qt 还会带来 `-fPIC`。核对时接受这些选项，但要和配方中登记的一致。
- 预生成配置头：
  - 用途：构建前只需生成一次的配置头，例如 ORC 的 `orc-config.hh`、libtiff 的 `tif_config.h`；
  - 生成：出题时在环境的 GCC 镜像中，用记录下来的命令生成，然后入库到 `source/`；
  - 登记：在 `SOURCE.json` 的 `generated` 中写明命令、工具版本、输入哈希和输出哈希；
  - 对 Agent 而言，它们就是普通的可见头文件。它们不属于修改业务源码。

**D020-4 镜像与记录**
- `executor.images` 仍只记录两个基础镜像，旧题的结果、补评判断和校准比较都不变。
- 环境镜像按题按需加载。评分时所有阶段都使用该题环境的派生镜像，包括构建、运行、Mull 和替换版本；运行阶段也必须用派生镜像，因为动态库只在派生镜像里。
- 记录与核对：
  - **结果**：新增 `environment: {name, recipe_sha256, images: {gcc, clang}}`。
  - **补评**：判断是否跳过时，要同时比较环境记录。
  - **校准状态**：新增 `environments`，记录校准题用到的环境。配方哈希或环境镜像 ID 变化时，校准变为 stale。
  - **题目指纹**：有环境的题，分母实质内容加入配方哈希；配方升级后准入自动失效。没有环境的题，指纹不变。
  - **变异分母**：记录环境；评分时如果环境不一致，判为分母过期。
- runner 对产品与评测侧的 GCC 镜像 ID 一致性检查，改为比较该题环境的 GCC 派生镜像。
- Mull：Debian 的库都在 `/usr/lib/<multiarch>`，现有的 `--ld-search-path` 够用。将来配方把库装到其他目录时，要由配方声明附加路径。

**D020-5 产品**
- 产品按公开任务里的 `build.environment` 选择本机的环境镜像，并在 `toolchain.json` 中记录环境名、配方哈希和镜像 ID。

- 用户自己的构建环境：按同一配方格式编写（同一快照、精确版本），产品负责构建和验证，不支持任意 Dockerfile。

**D020-6 与 D019 的关系**
- 下面两种 Clang 失败，判定时仍按基础设施错误处理：
  - moc 或 protoc 的生成单元编译失败；
  - 错误位置在库头文件里的失败。

  这是保守做法，D019 的归因规则不变。

  - 原因不能确定：按**阻塞**处理。
- 还有未处理的 `infra_error` 时，步骤 C 不能完成。

## D021 构建环境身份、Mull 预热上限与建题审计（步骤 C 收尾）

- **日期**：2026-10-30

**D021-1 环境身份（修订 D020-4 的“变异分母”“题目指纹”“校准状态”三项）**
- 环境身份指环境名与配方 sha256，与基础镜像的口径一致：可复现的输入进入分母和指纹，不可复现的镜像 ID 只做记录和校准比较。
- 变异分母：评分时只比较分母记录的环境身份与本次环境身份，不比较镜像 ID；不一致仍判为 `mutation_baseline_environment_changed`。
- 准入：题目指纹中的分母实质内容只取环境身份；准入状态只看题目指纹，以及分母的环境身份是否与题目当前配方一致，不解析本机镜像。
- 校准状态：
  - 记录每个校准环境的配方哈希和两个派生镜像 ID（与 `images` 记录基础镜像相同）；
  - 任何查询都核对每个已记录环境的配方哈希，配方变化时 stale；
  - 查询的题有 `build.environment` 时，比较该环境本机派生镜像的 ID，变化或镜像不可用时 stale；
  - 查询的题没有 `build.environment`（以及不指定题目）时，只比较基础镜像与校准记录，不要求本机存在环境镜像。
- 校准样本的冻结期望只核对环境身份及两个镜像记录是否齐全；当次校准的结果与当次校准环境的镜像 ID 仍逐项比较。
- 结果文件、分母、预生成登记和校准状态继续记录完整的环境记录（含镜像 ID），补评判断是否跳过时仍比较完整环境记录。
- 影响：分母实质内容的计算方式改变，11 道环境题的题目指纹全部变化，需要重新签署准入；旧 115 题的指纹不变。

**D021-2 `params.mull_test_timeout_ms`**
- 用途：映射为 `mull-runner --timeout=<毫秒>`，即 Mull 用原始（未变异）全套测试做预热运行的时间上限。它不改变 `--minimum-timeout`，也不改变单个测试的有效性超时 `test_timeout_seconds`。
- 默认：不设时 Mull 命令保持原样，旧题的命令与分母不变。
- 取值：整数毫秒，闭区间 1000–60000；`validate_task` 校验类型与范围，布尔值和浮点数都拒绝。
- 使用条件：只在参考测试的原始全套预热实测超出 mull-runner `--timeout` 的默认值时设置，并在该题 `hidden/README.md` 写明原因、实测时长和证据 run-id。不能用它把未检出的变异变成检出。
- 现有用法：只有 qt-aes 设为 30000，依据是 `runs/step-c-aes-diagnosis-20261029-01` 实测的 16.32 秒原始全套运行，已写在该题 README 中。
