## D001 断言以被测代码的实际运行结果为准

- **日期**：2026-10-22
- **决定**：Agent 全自动读取已有 C++ 代码并生成单元测试，断言的预期值以被测代码的实际运行结果为准。代码是否符合需求，由后续的功能测试负责，不属于本阶段。
- **理由**：
  - Agent 是全自动的，用在生产环境。
  - 需求文档难以维护，从需求文档自动拆解出断言效果不可靠。
  - 以实际行为为准时，测试在被测代码上失败就能直接判定为测试写错，评分可以全自动完成。
- **放弃的选项**：以需求文档为准生成断言，用来发现已有缺陷。
- **代价**：被测代码本身的缺陷会被测试一起锁定，留给后续功能测试发现。
- **前提（制定时待确认）**：生产环境里，Agent 能拿到目标项目的构建环境，在沙箱中编译、运行代码。
- **现状（2026-10-26）**：D013 产品已提供可独立交付的 GCC/Docker 编译反馈；任意项目的构建适配仍需按项目验证，当前支持范围见[产品 README](../agents/README.md)。

## D002 评分范围收窄，替换版本统一执行

> 第 2 条的规模由 D017 修订：开发集真实缺陷题至少 20 道、等价版本题至少 10 道；验收集真实缺陷 3–5 道保留。

- **日期**：2026-10-23
- **决定**：
  1. 不做 sanitizer、极端变异和静态扫描（断言密度、无断言测试、脆弱写法），对应指标 M3、F2、A1、A2 从评测规格中删除。
  2. 保留真实缺陷和等价版本，小规模实施：真实缺陷 3–5 道验收题，等价版本 2–3 道开发题。
  3. 优先级：先打通主链路（构建、执行核对、稳定性、gcov、Mull），然后是真实缺陷，最后是等价版本。
  4. 手写变异、真实缺陷、等价版本在评分器中统一为“替换版本执行”步骤，第一版就实现接口，题目格式始终保留替换版本列表，列表可以为空。
- **理由**：
  - 只调用不断言、断言无效的测试，Mull 的检出率本来就接近 0；断言密度和脆弱写法这些信号，变异测试和等价版本覆盖得更直接。
  - sanitizer 抓的测试自身未定义行为，在当前阶段意义很小，重复运行也能暴露其中一部分。
  - 真实缺陷是验证“变异检出率高等于测试有用”的唯一真实世界证据；等价版本是唯一检查误报的手段，防止评分被“写死实现细节”的测试钻空子。
  - 两者在评分器里是同一个动作，先留好接口，以后补的是题目数据，不需要改评分器。
- **放弃的选项**：把 sanitizer、极端变异、静态扫描排在后面实施；给每道题都配真实缺陷和等价版本。
- **代价**：测试自身的未定义行为（例如悬垂引用）不会被专门检查，可能出现“碰巧通过”的测试。
- **重新评估的条件**：错误分析中发现这类问题频繁出现，或者这类问题影响了版本比较的结论。

## D003 被评测的 Agent 只接 pi，源码全量入库

- **日期**：2026-10-24
- **决定**：
  1. 生成入口直接调用 pi，不做通用 Agent 适配器层。
  2. pi 源码全量复制进本仓库，不带原 `.git`，以后在本仓库修改和提交；Agent 版本用 Qualtor 提交号表示。`node_modules/`、`dist/` 不入库，`package-lock.json` 入库；另存 `UPSTREAM.json` 记录复制时的上游与提交号。
  3. 被评测配置（模型设置等）放在仓库的 `agents/` 下，由用户填写；本阶段不加 skill。
- **理由**：当前只需要 pi；源码在本仓库内，改 Agent、跑评测、比较结果在同一处完成，版本可直接追溯。
- **放弃的选项**：适配器层先接 Claude Code；pi 作为 git submodule；只在配置中记录外部路径和提交号。
- **代价**：与上游同步需要手工对照 `UPSTREAM.json`。
- 当前安装与配置见[产品 README](../agents/README.md)，工具与运行边界见[接口说明](接口与运行边界.md)。

## D004 生成在容器中运行：只读挂载、无 bash、直接联网

> **部分已被 D013 替代。** 下文保留 2026-10-24 的决定；现行 pi 在宿主机运行，生成 C++ 在禁网 Docker 中编译执行。工具白名单和 Agent 驱动修复的约束仍保留。

- **日期**：2026-10-24
- **决定**：
  1. 生成 Agent 在 Docker 容器中运行；生成镜像以 `qualtor-gcc` 为基础加装 node 24，由 `toolchains.py` 构建。pi 目录只读挂载进容器。
  2. 只挂载本 trial 需要的材料；被测代码只读挂载、不复制；隐藏材料不进入生成容器。
  3. Agent 只有 `read`、`write`、`edit`、`grep`、`find`、`ls`、`build_and_test` 七个工具，不提供 bash。
  4. `build_and_test`、路径门卫、轮次计数与快照以框架自己的 pi 扩展实现，与被评测配置分开。
  5. 生成容器直接联网，API 地址和密钥由环境变量传入；评分容器保持禁网。测试进程暂不断网。
- **理由**：pi 自身不构成安全边界，隔离要靠容器；有 bash 就能绕过修复轮次计数；没有 bash，Agent 没有可联网的工具，不需要出口代理；API 地址会变化。
- **放弃的选项**：宿主机上靠权限配置运行；按域名白名单的出口代理；不限次数的探针工具。
- **代价**：Agent 了解代码实际行为只能通过 `build_and_test`，会消耗修复轮次；修复阶段可联网而评分阶段禁网，依赖真实网络的测试会在评分时失败。
- **重新评估的条件**：出现需要联网的被测代码（届时让测试进程断网运行）。

## D005 修复由 Agent 驱动，只限制修复轮次

- **日期**：2026-10-24
- **决定**：
  1. Agent 自己决定何时调用 `build_and_test`；它只返回编译错误和每个测试的通过/失败及失败信息，不返回覆盖率、变异结果，也不运行替换版本和参考测试。
  2. 修复包括编译失败和在被测代码上运行失败（按 D001 属于测试写错）。
  3. 首次产物为第一次调用 `build_and_test` 时的工作区，这次不算修复；之后每次调用算 1 轮；用满 N 轮后拒绝执行。N 写进 `task.json`，初始值 3。
  4. 预算只限制修复轮次，token 与时间只记录。另设无响应看门狗：pi 连续 15 分钟无任何事件即终止，记为 `generation_stalled`。
  5. trial 结束状态分为 `finished`、`budget_exhausted`、`never_built`、`generation_stalled`、`agent_error`；`agent_error` 用全新工作区重跑，最多 2 次。
- **实现细化（2026-10-26）**：首次产物在首次编译前保存为测试快照；看门狗默认 900 秒无进展，编译时暂停、心跳不算进展；新增用户取消状态 `cancelled`，清理并保留产物、不重试。详见[接口与运行边界](接口与运行边界.md#结束与重试)。
- **修订**：2026-10-25 的 [D012](#d012-基础设施重试耗尽即停止生成整轮修订-d005) 补充第 5 条：`agent_error` / `infra_error` 耗尽重试后，取消未开始的 trial，生成整轮记为 `failed`；替代此前“单个 trial 记缺失、其余继续”的处理口径。
- **理由**：修复策略由 Agent 决定，才能评出 Agent 与 skill 的差异；评分信息一旦反馈给 Agent，Agent 就会针对指标优化；大代码库所需时间无法事先确定，只能检测卡死。
- **放弃的选项**：编排器驱动的固定修复循环；token 和墙钟预算；60 分钟总时长上限。
- **代价**：Agent 若一直读文件不结束，看门狗抓不到；暂不设模型调用次数上限，出现后再加。

## D006 run 是一次执行，补评写进原 run

- **日期**：2026-10-24
- **决定**：
  1. run 是一次实际执行的记录。同一配置执行两次就是两个 run，互不干扰。一个 run 包含所选题目的 K 个 trial（K = 5）。
  2. 一个 run 的全部内容（配置快照、工作区、每轮快照、冻结产物、日志、成本、评分）放在同一个 run 目录。
  3. 评分器升级后的补评写进原 run，按评分器版本分子目录，旧结果原样保留、不覆盖；汇总时指定评分器版本。
  4. 生成入口一条命令完成“生成 → 修复 → 冻结 → 评分 → 汇总”；评分器校准状态不是 passed 时拒绝运行。
- **理由**：一次执行的证据集中一处，便于追溯；补评属于原执行，按版本分目录同样满足“不覆盖旧结果”。
- **放弃的选项**：run 等同于一份配置；补评另开 run。
- **代价**：评分器版本多了以后，run 目录里会积累多份评分结果。

## D011 等价版本必须在全部输入上等价

- **日期**：2026-10-25
- **决定**：
  1. 等价版本须在被测代码**全部无未定义行为的输入**上与被测代码行为一致，不再以评分输入域为界。评分输入域只约束参考强测试集和有界穷举探针。
  2. 删除 GildedRose 的 eq-01（把质量截断到 0–50），新增 eq-02：按商品种类拆成独立函数的重构，只在 `sellIn == INT_MIN` 时与原代码不同；原代码在该输入上执行 `sellIn - 1` 会发生有符号溢出，属于未定义行为。等价性用 `hidden/variants/differential_check.cc` 在大范围输入网格上与原代码逐一比对确认。
  3. 断言评分输入域之外真实行为的测试（例如质量 60 的商品）按正常测试计分，不算误报。CAL-16 改为同时包含一条这样的测试和一条依赖有符号溢出的测试：前者在 eq-02 上必须通过，只有后者应判为误报。
  4. 评分器升为 0.1.3，在 Docker 中重新校准；已有的真实运行结果在原 run 中按 0.1.3 补评。
- **理由**：
  - 按 D001，被测代码的实际运行结果就是标准答案。质量 60 时给出 59 还是 50 是一处真实的行为差异，eq-01 实际上是一个在边界外改了行为的变异，不是等价版本。
  - 评分输入域对 Agent 不可见，代码本身也不检查输入范围。Agent 照实际行为写出的正确测试被判为误报，F1 量到的是“测了多少域外输入”，而不是测试是否脆弱。2026-10-24 的真实 K=5 运行中，12 份产物在 eq-01 上全部判为误报，原因都是这一点。
  - 等价版本真正等价后，测试在它上面失败只可能是因为锁死了实现细节或依赖未定义行为，这才是 F1 要抓的脆弱测试。
- **放弃的选项**：
  - 把输入域写进 `TASK.md`：生产环境里没有人告诉 Agent 输入范围，评测会比实际使用偏好。
  - 只用评分域内的测试计算 F1：评分器要先自动提取每条测试的输入，对任意 C++ 测试难以做到可靠，会引入新的噪声。
- **代价**：GildedRose 这类纯计算代码很难写出既真等价、又能让“只断言输出”的测试失败的改写，F1 在这道题上大概会接近 0，区分度要靠以后更复杂的题目。CAL-16 依赖 `-O0` 下有符号溢出按补码回绕的固定行为，换编译器或优化级别时要重新确认。
- **修订**：CAL-16 原先“断言输入域外行为应判误报”的设计意图（见[评测实现与校准样本](评测模块与校准样本设计.md)第 10 节）作废。

## D012 基础设施重试耗尽即停止生成整轮（修订 D005）

- **日期**：2026-10-25
- **状态**：已接受，修订 D005 第 5 条的重试后处理口径。
- **决定**：生成入口中，`agent_error` 或评分的 `infra_error` 在首次尝试及最多两次重试后仍失败，按系统性故障处理。取消所有尚未开始的 trial；已启动的 trial 运行结束后保留结果；`run.json` 和 `summary.json` 均记为 `failed`，后者列出出错与被取消的 trial。基础设施异常直接抛出时采用相同处理。
- **理由**：连续三次失败后仍继续排队任务，容易在同一个 API 或环境故障上重复消耗时间和模型费用；停止派发便于先定位环境问题。这里是运行策略，不是对根因已经确定的判断。
- **放弃的选项**：失败 trial 仅记缺失，其余照跑，整轮记为 `incomplete`。
- **代价与边界**：即使故障只影响一个 trial，也会取消未开始项；已经启动的任务仍会产生后续成本，记录和结果全部保留。测试编译失败、断言失败及预算耗尽属于正常评测结果，不触发该策略。生成入口完整执行记为 `completed`；独立评分/补评的缺失结果及其 `incomplete`、汇总时跳过缺失结果的统计规则保持不变。

## D015 只在未定义行为或资源耗尽时才不同的变异不计入分母

- **日期**：2026-10-28
- **状态**：由开发 Agent 按“能定的直接定”提出并实施，用户可推翻；推翻时只需改 `confirmed.json` 的判定并重新落实，评测代码不受影响。
- **决定**：
  1. 变异与原代码的差异只在未定义行为（越界访问、整数除零、有符号溢出、无效迭代器等）下出现时，复核判定为 `undefined_only`，列为不稳定变异，不计入 M1 分母。原先“sanitizer 证实 UB 即移回分母”的 10 项一并改判。
  2. 差异只在资源耗尽时出现（分配失败、超过 `max_size`、泄漏）的变异，按等价处理，在 `equivalent.json` 写明理由。
  3. 准备工具发现参考测试检出、而包含全部参考测试的探针未检出时，不再列为等价候选，改列为不稳定：探针含有全部参考测试，两者结果不同只能来自二进制差异，多为未定义行为。
  4. 只在部分输入上越界、在其他有定义输入上有确定差异的变异（如把 `length()` 换成 42，长度超过 42 时会截断），仍按普通变异处理，应补测试检出。
- **理由**：
  - 评测不带 sanitizer（D002），同一个 UB 变异在不同二进制、不同执行条件下可能幸存或崩溃。实测中，第 18 组 `cpp_141.cc:27` 被参考测试两轮检出、探针两轮幸存；Rail Fence 第 14 行在正式 Mull 中幸存，单独回放时崩溃；第 16 组两项在一轮中归为不稳定，下一轮又成了等价候选。把这类变异放进分母，被评测测试能否“检出”取决于内存布局，是噪声而不是测试质量。
  - D011 已规定等价版本只在无未定义行为的输入上要求一致，依赖未定义行为的测试被视为脆弱测试；分母口径与此保持一致。
- **代价**：越界、除零这类真实缺陷不进入 M1；如以后评测引入 sanitizer 运行，需要重新讨论。资源类差异（如 `reserve` 参数变化）不计入，测不出内存效率问题。
- **版本**：第 3 点改变了 `prepare_task.py` 的分类，随 R-08 一起把评测模块升为 0.2.0，需在 Docker 中重新校准；第 1、2 点只改题库数据（`benchmark/tools/mutant_review/`）。

## D016 题目准入清单与多题校准（R-08）

- **理由**：此前校准只覆盖 GildedRose，门禁只看全局指纹，改动过材料的题或未复核的新题可以直接进入正式比较。题目指纹与准入记录绑定后，正式比较用的每道题都对应一份签过字的分母。

- **版本**：评测模块升为 0.2.0（含 D015 第 3 点），需在 Docker 中完整校准。
- **修订（2026-10-28，0.2.1）**：0.2.0 的 Docker 验收复现了两处与本决定不符的实现，按实现错误修正，没有改变口径：
  1. 校准状态必须核对记录中的每一道校准题。任何一道校准题的材料变化，查询任意题目（或不指定题目）都返回 `stale`；此前只核对被查询的题目本身。
  2. 正式比较要求题目当前的准入有效，即当前指纹与登记一致，且结果评分时的指纹也与登记一致。题目材料在准入后变化时，即使旧结果与登记一致也拒绝；冻结旧题库结果只作参考，需加 `--allow-unadmitted`。
