# C++11 固定版本 Docker 工具链

两套镜像分别负责覆盖率和变异测试，使用相同的 C++11 业务源码与 GoogleTest 测试，构建目录互不混用。入口是 [`toolchains.py`](../evaluator/toolchains/toolchains.py)，镜像定义是 [`Dockerfile.toolchains`](../evaluator/toolchains/docker/Dockerfile.toolchains)。

同一个 Dockerfile 的 `gcc`、`clang` 两个构建目标分别生成一个可直接编译和运行测试的镜像。`toolchains.py` 在宿主机启动这两个镜像的容器，执行容器内的 `evaluator/toolchains/check_toolchain.py`；另有 generator 目标，在 GCC 层加入固定 Node 24.10.0，运行只读挂载的 pi；用途与构建说明见[生成入口运行说明](生成入口运行说明.md)。

## 固定版本

| 组件 | GCC 体系 | Clang 体系 |
|---|---|---|
| 基础系统 | Debian 13（trixie-slim） | 同左 |
| 编译器 | GCC / G++ **14.2.0** | Clang / LLVM **19.1.7** |
| 分析工具 | gcov **14.2.0**，与 GCC 同一软件包系列 | Mull **0.34.2**，官方 LLVM **19.1.7** 构建 |
| 测试框架 | GoogleTest / GoogleMock **1.12.1**，用 GCC 构建 | GoogleTest / GoogleMock **1.12.1**，用 Clang 构建 |
| 语言标准 | ISO C++11，`-std=c++11` | ISO C++11，`-std=c++11` |
| CMake / Ninja | **3.31.6 / 1.12.1** | 同左 |

GoogleTest 1.12.1 是最后支持 C++11 的版本；1.13 起要求至少 C++14，因此不能使用 `main` 或发行版自带的新版本。[GoogleTest 官方发布说明](https://github.com/google/googletest/releases/tag/release-1.12.1)

语言标准和编译器版本是两件事：GCC 14、Clang 19 均可使用 C++11，无需退回早期编译器。Mull 是 LLVM 插件，必须与 Clang/LLVM 匹配，因此这里固定整个组合。Mull 自身构建时的语言标准不会改变被测项目的 C++11 设置。[GCC 标准支持](https://gcc.gnu.org/projects/cxx-status.html)、[Clang 标准支持](https://clang.llvm.org/cxx_status.html)、[Mull 安装说明](https://mull-project.com/getting-started/installation/)

版本锁定包括：

- 基础镜像固定多架构摘要 `sha256:62bd423aeee912639ca8ee681c2b762cb3e25137e0a92b20be455898a9f034ad`。
- APT 固定 `20261021T000000Z` 的 Debian 与 Debian Security 快照；GCC 包固定 `14.2.0-19`，LLVM 包固定 `1:19.1.7-3+b1`。传递依赖也来自同一个固定快照，保留软件源签名验证。
- GoogleTest 官方源码包与 Mull 官方 `.deb` 均验证写死的 SHA-256；ARM64 和 AMD64 的 Mull 包分别校验。下载链接、摘要都在 Dockerfile 中。
- 每个镜像内 `/opt/qualtor/packages.txt` 保存实际包清单；验收保存版本输出、输入文件哈希、镜像 ID 和容器配置，并用镜像 ID 启动容器。

这固定了依赖版本与下载内容；不承诺不同机器的 Docker 构建时间戳、镜像 ID 或最终二进制逐字节相同。

## 构建与验收

从项目根目录执行。前提是 Docker 已启动、宿主机 Python 3.9+；首次镜像构建需要联网。验收使用仓库已有的上游源码快照及 `SOURCE.json`，前后校验哈希。

```bash
python3 evaluator/toolchains/toolchains.py
```

命令默认构建 GCC、Clang、generator 三个镜像，构建 pi 并执行验收；每次创建新的运行目录，不覆盖历史记录。镜像和 pi 已经构建时：

```bash
python3 evaluator/toolchains/toolchains.py --skip-build
```

只构建、不验收，或者只选择一套：

```bash
python3 evaluator/toolchains/toolchains.py --build-only
python3 evaluator/toolchains/toolchains.py --toolchain gcc
python3 evaluator/toolchains/toolchains.py --toolchain clang --skip-build
```

默认使用 Docker 当前架构；可显式传 `--platform linux/arm64` 或 `--platform linux/amd64`。跨架构执行依赖 Docker 的仿真支持；架构属于实验条件，比较成绩时必须固定。

镜像标签：

- `qualtor-gcc:14.2.0-gtest1.12.1-cxx11`
- `qualtor-clang:19.1.7-mull0.34.2-gtest1.12.1-cxx11`
- `qualtor-generator:node24.10.0-gcc14.2.0`

构建上下文始终为 `evaluator/toolchains/docker/`，没有 `COPY` / `ADD` 项目文件。镜像只包含工具及其依赖。GCC/Clang 验收的项目源码和测试通过只读 bind mount 引入；容器禁网、根文件系统只读、非 root 运行，限制为 2 CPU、2 GiB 内存、256 个进程，丢弃全部 capabilities，只有独立输出目录和临时目录可写。生成容器的联网、分 UID 和写入边界见[生成入口运行说明](生成入口运行说明.md)。

## 项目接入方式

两套镜像分别设置 `CC` / `CXX`；GoogleTest 已离线安装到 `/opt/googletest`，`CMAKE_PREFIX_PATH` 已指向该目录。项目中使用：

```cmake
set(CMAKE_CXX_STANDARD 11)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)
find_package(GTest 1.12.1 EXACT CONFIG REQUIRED)

enable_testing()
include(GoogleTest)
add_executable(unit_tests tests.cc)
target_link_libraries(unit_tests PRIVATE your_library GTest::gtest_main)
gtest_discover_tests(unit_tests DISCOVERY_MODE PRE_TEST)
```

使用不同的构建目录，例如 `build/gcc`、`build/clang`。不要切换编译器后复用 CMake 缓存、对象文件或覆盖率数据。

GCC 体系对业务目标加入 `-O0 -g --coverage -fprofile-abs-path`，在测试可执行文件的链接选项中加入 `--coverage`；执行测试后使用 `gcov-14`。Clang 体系对需要变异的业务目标加入 `-O0 -g -grecord-command-line -fpass-plugin=/usr/lib/mull-ir-frontend-19`，然后运行 `mull-runner-19`。GoogleTest 和测试代码不加载 Mull 插件。

编译与执行 Mull 时使用同一个 `MULL_CONFIG`，固定算子和业务源码路径。幸存变异通过 `--allow-surviving` 保留为结果，未覆盖变异通过 `--include-not-covered` 保留；超时和工具错误单列。执行器用 `g++-14 -print-multiarch` 得到 Debian 库目录，传给 Mull 的 `--ld-search-path`，使系统动态库可以正常解析。完整示例见 [验收 CMake](../evaluator/toolchains/smoke/CMakeLists.txt) 和 [Mull 配置](../evaluator/toolchains/smoke/mull.yml)。[Mull 配置说明](https://mull-project.com/getting-started/setup/)

## 验收范围与证据

验收用同一份上游 `cpp/src/GildedRose.cc` 和 9 个手写 GoogleTest 测试函数，检查：

1. 编译器和工具版本匹配；业务源码与测试均以 `-std=c++11` 编译，并通过 `__cplusplus == 201103L` 静态断言。
2. GoogleTest 与 CTest 实际发现、执行全部 9 个测试；JSON 结果无失败、跳过或禁用。
3. GCC 体系生成业务源码的 gcov 文本、JSON 及 `.gcda/.gcno`，核对两种输出的计数。
4. Clang 体系实际加载 Mull 插件、生成和执行变异，产生机器可读报告，且至少检出一个行为变异。
5. 执行前后上游源码清单与哈希保持一致。

每次输出保存在 `runs/<run-id>/`：`gcc/`、`clang/` 保存构建、测试和分析结果，`evidence/` 保存输入哈希、宿主机命令、镜像和容器记录。`run.json` 标记 `kind: toolchain`，`summary.json` 给出结论。

2026-10-24 迁移后的 Linux ARM64 验收：GCC 和 Clang 各 9/9 个测试通过；gcov 为 29/29 行、38/38 分支，文本与 JSON 一致；Mull 生成并检出 8/8。源码哈希保持一致，见[本轮汇总](../runs/toolchain-layout-20261024-02/summary.json)及[容器证据](../runs/toolchain-layout-20261024-02/evidence/)。AMD64 尚未实测。

历史工具链经验：Docker Desktop 凭据助手可能阻塞拉取，所以入口为本轮建立空 `auths` 客户端配置，同时保留 `cliPluginsExtraDirs` 定位 Buildx；APT 和下载使用有限重试，仍校验签名与摘要。若镜像列表显示标签而 inspect 报不存在，可核对已验证镜像的 ID 后恢复本地标签；本轮最初两次失败的日志保留在 runs 中。

生成运行时使用 Node 24.10.0 官方 ARM64/AMD64 包，SHA-256 固定在 Dockerfile；来源为 [Node.js 官方发布目录](https://nodejs.org/dist/v24.10.0/)。pi 不进入镜像，模型目录使用其源码自带的内容摘要固定。
