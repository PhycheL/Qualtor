# C++11 固定版本 Docker 工具链

GCC 镜像用于产品普通编译验证，以及评测中的有效性、稳定性、覆盖率和替换版本执行；Clang/Mull 镜像用于变异评测。两类镜像处理同一份 C/C++ 业务源码与 C++11 GoogleTest 测试，执行时按阶段创建独立容器，构建目录互不混用。统一构建与验收入口是 [`toolchains.py`](../evaluator/toolchains/toolchains.py)。

GCC 定义位于 [产品 Dockerfile](../agents/toolchains/docker/Dockerfile.gcc)，Clang/Mull 定义位于[评测 Dockerfile](../evaluator/toolchains/docker/Dockerfile.toolchains)。统一入口在宿主机启动两套容器执行 `check_toolchain.py`。pi 按 D013 在宿主机运行，不再构建 generator 镜像；安装方法见[生成入口运行说明](生成入口运行说明.md)。

## 固定版本

| 组件 | GCC 体系 | Clang 体系 |
|---|---|---|
| 基础系统 | Debian 13（trixie-slim） | 同左 |
| 编译器 | GCC / G++ **14.2.0** | Clang / LLVM **19.1.7** |
| 分析工具 | gcov **14.2.0**，与 GCC 同一软件包系列 | Mull **0.34.2**，官方 LLVM **19.1.7** 构建 |
| 测试框架 | GoogleTest / GoogleMock **1.12.1**，用 GCC 构建 | GoogleTest / GoogleMock **1.12.1**，用 Clang 构建 |
| 语言标准 | 测试与 C++ 源码为 ISO C++11；C 源码按题选择 C99 或 C11 | 同左 |
| CMake / Ninja | **3.31.6 / 1.12.1** | 同左 |

GoogleTest 1.12.1 是最后支持 C++11 的版本；1.13 起要求至少 C++14，因此不能使用 `main` 或发行版自带的新版本。[GoogleTest 官方发布说明](https://github.com/google/googletest/releases/tag/release-1.12.1)

语言标准和编译器版本是两件事：GCC 14、Clang 19 均可使用 C++11，无需退回早期编译器。Mull 是 LLVM 插件，必须与 Clang/LLVM 匹配，因此这里固定整个组合。Mull 自身构建时的语言标准不会改变被测项目的 C++11 设置。[GCC 标准支持](https://gcc.gnu.org/projects/cxx-status.html)、[Clang 标准支持](https://clang.llvm.org/cxx_status.html)、[Mull 安装说明](https://mull-project.com/getting-started/installation/)

版本锁定包括：

- 基础镜像固定多架构摘要 `sha256:62bd423aeee912639ca8ee681c2b762cb3e25137e0a92b20be455898a9f034ad`。
- APT 固定 `20261021T000000Z` 的 Debian 与 Debian Security 快照；GCC 包固定 `14.2.0-19`，LLVM 包固定 `1:19.1.7-3+b1`。传递依赖也来自同一个固定快照，保留软件源签名验证。
- GoogleTest 官方源码包与 Mull 官方 `.deb` 均验证写死的 SHA-256；ARM64 和 AMD64 的 Mull 包分别校验。下载链接、摘要都在 Dockerfile 中。
- 每个镜像内 `/opt/qualtor/packages.txt` 保存实际包清单；验收保存版本输出、输入文件哈希、镜像 ID 和容器配置，并用镜像 ID 启动容器。

这固定了依赖版本与下载内容；不承诺不同机器的 Docker 构建时间戳、镜像 ID 或最终二进制逐字节相同。

## 构建与验收

从项目根目录执行。前提是 Docker 已启动、宿主机 Python 3.9+；首次镜像构建需要联网。验收使用仓库已有的上游源码快照及 `SOURCE.json`，前后校验哈希。

```bash
python3 evaluator/toolchains/toolchains.py
```

命令默认构建并验收 GCC、Clang 两个镜像；每次创建新的运行目录。已有镜像时：

```bash
python3 evaluator/toolchains/toolchains.py --skip-build
```

只构建、不验收，或者只选择一套：

```bash
python3 evaluator/toolchains/toolchains.py --build-only
python3 evaluator/toolchains/toolchains.py --toolchain gcc
python3 evaluator/toolchains/toolchains.py --toolchain clang --skip-build
```

默认使用 Docker 当前架构；可显式传 `--platform linux/arm64` 或 `--platform linux/amd64`。跨架构执行依赖 Docker 的仿真支持；架构属于实验条件，比较成绩时必须固定。

镜像引用使用完整名称，构建、安装、生成和评测查询保持一致；查询后保存 ID，并按 ID 创建容器：

- `docker.io/library/qualtor-gcc:14.2.0-gtest1.12.1-cxx11`
- `docker.io/library/qualtor-clang:19.1.7-mull0.34.2-gtest1.12.1-cxx11`

GCC 名称只维护在 `agents/toolchains/images.json`，评测入口复用此配置；Clang 名称维护在 `evaluator/toolchains/toolchains.py`。`docker.io/library/` 显式写出了 Docker 对省略仓库域名和命名空间时的缺省值，参见[官方镜像命名规则](https://docs.docker.com/reference/cli/docker/image/tag/)。本地已有短标签对应的镜像可以直接按完整名称查询，镜像 ID 和校准的内容标识不变。

GCC 构建上下文为 `agents/toolchains/docker/`，Clang 为 `evaluator/toolchains/docker/`；按题构建环境的派生镜像另用只含 `Dockerfile.environment` 的临时上下文（见下节）。没有 `COPY` / `ADD` 项目文件，镜像只安装工具链和配方锁定的依赖。验收时源码和测试只读挂载，容器禁网、根文件系统只读、非 root，限制 2 CPU、2 GiB、256 个进程并丢弃 capabilities。产品编译服务的监督程序、降权和日志保护见[产品边界](接口与运行边界.md)。

## 按题构建环境（D020）

配方由独立产品持有：[bank-20261021.json](../agents/toolchains/environments/bank-20261021.json)，评测读取同一文件。配方只放在 `agents/toolchains/environments/` 一处；两份构建契约按自身的固定位置定位配方目录（评测侧按仓库根，产品单独交付时按产品根），不搜索、不回退（[D021-3](决策记录.md#d021-构建环境身份mull-预热上限与建题审计步骤-c-收尾)）。两份基础镜像不重建；在其固定 ID 上分别增加 Boost 1.83、OpenSSL 3.5、zlib 1.3.1、protobuf 3.21.12、QtCore 5.15.15 的精确 Debian 包（8 个顶层包，快照 `20261021T000000Z`；配方不含 expat）。版本与完整字段以配方为准，安装只允许增包，检查原有每个包的版本未变。

```bash
python3 -B evaluator/toolchains/toolchains.py --environment bank-20261021 --run-id step-c-environment-YYYYMMDD-01
# 只核对已有镜像和冒烟：
python3 -B evaluator/toolchains/toolchains.py --environment bank-20261021 --skip-build --run-id step-c-environment-YYYYMMDD-02
```

环境名、配方 SHA-256、平台、基础镜像 ID、派生镜像 ID 和前后完整包清单均入运行证据。标签为 `docker.io/library/qualtor-env-<名称>-<gcc或clang>:<配方哈希前12位>`，执行按 ID。Docker 28 的 BuildKit 会把本地 `sha256:` 基础 ID 当作远程名称（`runs/step-c-environment-20261029-01/` 因此拉取失败），故当前实现显式使用 legacy builder（`DOCKER_BUILDKIT=0`）；此为已验证的实现限制，未验证其他 Docker 版本。禁止因镜像缺失自动改用基础镜像。

legacy builder 只读取上下文根目录的 `.dockerignore`，不识别 `Dockerfile.environment.dockerignore`。0.5.1 起两侧的环境构建都把 `Dockerfile.environment` 复制到临时目录，以只含该文件的目录为构建上下文，不再带上同目录的其他 Dockerfile；运行证据另存 `dockerfile.json`（源文件路径与 SHA-256）。2026-10-30 已在 Linux ARM64 执行构建并通过，两侧命中缓存，派生镜像 ID 与 0.5.0 相同，见 `runs/step-c-closeout-environment-20261030-01/`；这次未验证无缓存安装。

双编译器冒烟使用 C++11，检查 libstdc++ ABI、Qt 信号槽、Boost、MD5、压缩和 protobuf 的 map、oneof、嵌套消息、Arena、反射及序列化。GCC 只给冒烟业务单元插覆盖桩，Clang/Mull 仅在该单元插桩，并核对编译清单中的生成单元。Linux ARM64 已通过，见 `runs/step-c-environment-20261029-03/summary.json`：两种编译器各 6 个 GoogleTest 用例（`Environment.` 下的 Subject、Boost、OpenSSL、Zlib、Protobuf、Qt）全部通过，Clang 侧 Mull 4 个变异检出 3 个；GCC、Clang 侧分别新增 130、127 个包，基础包无修改。AMD64 未实测。该证据只证明工具链与构建能力，题库准入和真实模型结果另见题库验证说明。

0.5.1 修改了两处：protobuf 用例由 `protobuf_generate` 改为与两套构建模板相同的固定 `add_custom_command`（调用导入目标 `protobuf::protoc`，输出只写构建目录）；GCC 覆盖率断言改为针对未过滤的原始数据，要求只产生被测单元的一份 `.gcda`，且 gcov JSON 中带行或函数记录的文件只有被测单元。这两处已在 Linux ARM64 Docker 重新验证（`runs/step-c-closeout-environment-20261030-01/summary.json`）：GCC、Clang 各发现并执行 6 个测试且全部通过；原始覆盖数据只含 `subject.cc`；Clang 的 4 个变异检出 3 个。独立产品交付的 10 项检查也通过，见 `runs/step-c-closeout-delivery-20261030-01/summary.json`。

题目用 `build.environment` 选配方，`build.link_libraries` 只能引用配方列出的导入目标，`build.codegen` 只接受 `{"tool": "moc"}` 与 `{"tool": "protoc", "inputs": [...], "import_dirs": [...]}`（protoc 两项均必填，不接受其他键）。AUTOMOC 与 protoc 输出均在构建目录；protoc 由模板中固定的 `add_custom_command` 调用导入目标 `protobuf::protoc`，`--cpp_out` 写构建目录，并按首个包含输入的 import 根保留子目录，避免 `protobuf_generate(APPEND_PATH)` 扁平输出破坏上游 include。生成单元单列核对且不加载 Mull，通常不插桩；纯头文件题按 D018 给全部编译单元插覆盖桩，统计仍只包含被测头文件。

`executor.images` 保持只有基础 GCC/Clang。按题结果与变异分母另存 `environment`，校准保存 `environments`，均含派生镜像 ID。按 [D021-1](决策记录.md#d021-构建环境身份mull-预热上限与建题审计步骤-c-收尾)，环境身份为环境名与配方 SHA-256：变异分母与准入只绑定环境身份，配方变化才使其失效，重建镜像导致的 ID 变化不影响；校准状态仍比较镜像 ID，有 `build.environment` 的题比较该环境本机派生镜像的 ID，没有环境的题只比较基础镜像，不要求本机存在环境镜像。旧题不写环境字段，继续走基础镜像。

## 项目接入方式

两套镜像分别设置 `CC` / `CXX`；GoogleTest 已离线安装到 `/opt/googletest`，`CMAKE_PREFIX_PATH` 已指向该目录。项目中使用：

```cmake
set(CMAKE_CXX_STANDARD 11)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)
find_package(GTest 1.12.1 EXACT CONFIG REQUIRED)

enable_testing()
include(GoogleTest)
add_executable(unit_tests tests.cc)
target_link_libraries(unit_tests PRIVATE your_library GTest::gtest_main)
gtest_discover_tests(unit_tests DISCOVERY_MODE PRE_TEST)
```

题目通过 D017 的可选 `build` 声明依赖源文件、宏、白名单编译选项和 C 标准。两套模板启用 `LANGUAGES C CXX`，仅 C++ 编译单元强制包含 `cxx11_guard.h`；宏和选项作用于被测、依赖、测试三类单元。每次配置后检查 `compile_commands.json`，标准、宏、选项或插桩范围不符即停止。依赖源文件只参与链接，不进入 gcov 分母，也不加载 Mull 插件；镜像定义未改。

使用不同的构建目录，例如 `build/gcc`、`build/clang`。不要切换编译器后复用 CMake 缓存、对象文件或覆盖率数据。

GCC 体系对业务目标加入 `-O0 -g --coverage -fprofile-abs-path`，在测试可执行文件的链接选项中加入 `--coverage`；执行测试后使用 `gcov-14`。Clang 体系对需要变异的业务目标加入 `-O0 -g -grecord-command-line -fpass-plugin=/usr/lib/mull-ir-frontend-19`，然后运行 `mull-runner-19`。GoogleTest 和测试代码不加载 Mull 插件。

编译与执行 Mull 时使用同一个 `MULL_CONFIG`，固定算子和业务源码路径。幸存变异通过 `--allow-surviving` 保留为结果，未覆盖变异通过 `--include-not-covered` 保留；超时和工具错误单列。执行器用 `g++-14 -print-multiarch` 得到 Debian 库目录，传给 Mull 的 `--ld-search-path`，使系统动态库可以正常解析。完整示例见 [验收 CMake](../evaluator/toolchains/smoke/CMakeLists.txt) 和 [Mull 配置](../evaluator/toolchains/smoke/mull.yml)。[Mull 配置说明](https://mull-project.com/getting-started/setup/)

Mull 0.34.2 的 `--minimum-timeout` 是变异运行的最低超时，不能改变原始测试预热上限。按 [D021-2](决策记录.md#d021-构建环境身份mull-预热上限与建题审计步骤-c-收尾)，整套参考测试较慢的题可显式声明 `params.mull_test_timeout_ms`（整数毫秒，1000–60000），映射到 `mull-runner --timeout=<毫秒>`，即原始（未变异）全套测试预热运行的上限；它不改变 `--minimum-timeout` 和单测有效性超时 `test_timeout_seconds`。未声明的旧题保持命令原样。该值须依据原始测试实测时长设定，并在该题 `hidden/README.md` 写明原因、实测时长和证据 run-id，不能靠修改超时把未检出的变异计为检出。目前只有 qt-aes 设为 30000，依据是 `runs/step-c-aes-diagnosis-20261029-01/` 实测的 16.32 秒原始全套运行；诊断证据另见 `-02/`。

## 验收范围与证据

验收用同一份上游 `cpp/src/GildedRose.cc` 和 9 个手写 GoogleTest 测试函数，检查：

1. 编译器和工具版本匹配；业务源码与测试均以 `-std=c++11` 编译，并通过 `__cplusplus == 201103L` 静态断言。
2. GoogleTest 与 CTest 实际发现、执行全部 9 个测试；JSON 结果无失败、跳过或禁用。
3. GCC 体系生成业务源码的 gcov 文本、JSON 及 `.gcda/.gcno`，核对两种输出的计数。
4. Clang 体系实际加载 Mull 插件、生成和执行变异，产生机器可读报告，且至少检出一个行为变异。
5. 执行前后上游源码清单与哈希保持一致。

每次输出保存在 `runs/<run-id>/`：`gcc/`、`clang/` 保存构建、测试和分析结果，`evidence/` 保存输入哈希、宿主机命令、镜像和容器记录。`run.json` 标记 `kind: toolchain`，`summary.json` 给出结论。

2026-10-24 迁移后的 Linux ARM64 验收：GCC 和 Clang 各 9/9 个测试通过；gcov 为 29/29 行、38/38 分支，文本与 JSON 一致；Mull 生成并检出 8/8。源码哈希保持一致，见本轮汇总（`runs/toolchain-layout-20261024-02/summary.json`）及容器证据（`runs/toolchain-layout-20261024-02/evidence/`）。AMD64 尚未实测。

运行排障经验：Docker Desktop 凭据助手可能阻塞拉取，所以入口为本轮建立空 `auths` 客户端配置，同时保留 `cliPluginsExtraDirs` 定位 Buildx；APT 和下载使用有限重试，仍校验签名与摘要。若镜像列表存在但短名称 inspect 报不存在，先用上面的完整名称查询并核对 ID，不据此判断镜像丢失或重新打标签；完整名称也失败时再检查当前 Docker endpoint 和本地镜像是否存在。

2026-10-28 的排查在 Docker Desktop 4.40.0 / Engine 28.0.4 复现：Linux VM 休眠时，宿主机 `apicache` 对 GCC 短名称直接返回 404；完整名称走 `apiproxy`、唤醒 VM 后成功，后续短名称也恢复。第三次历史失败（08:46 UTC）及本轮复现均有直接日志；更早两次的 Desktop 日志已轮换，不能逐次确证。该行为与 [Resource Saver 的缓存与唤醒机制](https://docs.docker.com/desktop/use-desktop/resource-saver/)相关；具体缓存键或规范化实现尚未证实。修正引用名称后，两套工具链、真实冻结测试的产品编译和独立评测均通过，并记录了两次休眠后的完整名称查询成功；详见[诊断与验收报告](../runs/docker-image-resolution-20261028-01/summary.md)。
