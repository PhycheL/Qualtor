# 评分器运行说明

评分器、题目包和校准样本怎么用：在装有 Docker 的机器上标定变异分母、校准评分器、给测试产物打分、汇总比较。设计见[评分器与校准样本设计](评分器与校准样本设计.md)，计算规则见[评分算法](评分算法.md)。

> 状态（2026-10-24）：评分器 **0.1.1 已在 Linux ARM64 Docker 中通过完整校准**。变异分母为 47；16 个样本各评分两次，判定与指标符合原期望，重复结果一致。59 个单元测试通过；宿主机集成测试本轮未配置，跳过 1 项。证据和本轮修复见第 9 节。

## 前提

- Docker 已启动，两个固定版本的工具链镜像已经构建并通过验收（见 [C++11 固定工具链](C++11固定工具链.md)）。可以用下面的命令确认：

  ```bash
  python3 gildedrose-lab/toolchains.py --skip-build
  ```

- 宿主机 Python 3.9+，只用标准库。所有命令都从项目根目录执行。
- 每次运行都会新建 `gildedrose-lab/runs/<run-id>/` 和 `gildedrose-lab/artifacts/scorer/<run-id>/`；`run-id` 不能重复，旧结果不会被覆盖。

## 1. 单元测试（不需要 Docker）

```bash
python3 -B -m unittest discover -s gildedrose-lab/scorer/tests -p "test_*.py"
```

包括解析器（用 gcov、Mull 的真实输出）、判定逻辑、汇总与比较、校准检查、题目包与产物校验、准备工具，以及 Docker 模式的接线检查。宿主机集成测试没有设置环境变量时会跳过，见第 7 节。

## 2. 标定变异分母（首次，或者题目、Mull 算子、工具链变化后）

```bash
python3 gildedrose-lab/scorer/prepare_task.py baseline --task gildedrose-update-quality --write
```

- 用参考强测试集和有界穷举探针各评分 2 次，每次都跑全部步骤（包括 Mull 和替换版本）。
- 输出：`runs/<run-id>/prepare_report.json` 和分母草稿 `runs/<run-id>/mutation_baseline.json`。
- 检查全部通过时，`--write` 才会写入 `gildedrose-lab/tasks/gildedrose-update-quality/hidden/mutation_baseline.json`；已存在时需要再加 `--force`。
- 命令打印变异总数、等价候选数、不稳定数、需复核数，以及参考强测试集的 M1（要求不低于 0.8）。

出现以下情况时命令失败，并写出问题清单：参考测试或探针本身有无效、不稳定的测试；各次 Mull 的变异集合不一致；参考强测试集强度不够；替换版本准入不通过（应失败的版本没被检出，或等价版本上出现误报）。

## 3. 人工复核等价变异

打开 `hidden/mutation_baseline.json`，逐个看 `equivalent` 里的候选：根据 `id` 中的算子和位置，判断它是真正的等价改动，还是引入了未表现出来的问题。复核完把 `review` 改为：

```json
"review": {"status": "reviewed", "by": "<复核人>", "at": "<日期>", "note": "<结论>"}
```

不是等价的变异，从 `equivalent` 移回分母（删除该条目）。复核之前，每份评分结果都会带一条 `mutation_baseline_review: pending` 警告。改动 `equivalent` 或 `unstable` 清单会让校准状态过期，需要重新校准；只改 `review` 字段不会。

## 4. 校准评分器

```bash
python3 gildedrose-lab/scorer/calibrate.py --jobs 2
```

- 16 个样本各评 2 次，每次都在全新的容器里执行。
- 输出：`runs/<run-id>/calibration_report.md`（可读的结果表）和 `calibration_report.json`。
- 全部通过时，`artifacts/scorer/calibration-status.json` 记为通过，并写入评分器代码、样本、题目和镜像的指纹。之后这四样中任何一个变化，校准状态都会自动变为过期。
- 每轮还核对输出中的 `cost` 和 `metrics.K1` 与输入 `cost.json` 一致，包括被判无效的样本。
- 只想先排查某几个样本时，可以运行 `--samples CAL-01,CAL-07`。这样只写报告，不更新校准状态。
- 第一次校准时，CAL-12、CAL-15 的数值阈值可以按参考强测试集的实际分数调整一次，但要在报告旁写明调整前后的值和理由。

首次执行时重点看：
- CAL-12、CAL-15 的 C1 有值，说明容器内的 gcov 采集正常；
- CAL-07 不是评分器故障，说明 Mull 的测试过滤生效了；
- 所有样本都没有“重复评分结果不一致”。

## 5. 给一份测试产物打分

产物目录的结构为 `<产物目录>/tests/*.cc`。先冻结，再评分：

```bash
python3 gildedrose-lab/scorer/freeze_product.py <产物目录>
python3 gildedrose-lab/scorer/score.py --task gildedrose-update-quality --product <产物目录> \
    --cost <cost.json> --agent-version <版本> --trial 1 --phase final
```

- `cost.json` 的格式：`{"tokens": {"input": 0, "output": 0}, "seconds": 0, "model_calls": 0, "repair_rounds": 0}`。
- 无效产物也保留生成成本并参与 K1 汇总；未传入成本文件时记录 `cost_missing`。
- 结果写在 `runs/<run-id>/tasks/<task-id>/<版本>-trial-<k>-<阶段>/result.json`。
- 校准状态不是 passed 时，命令会打印警告，结果里也会记录这个状态。
- 评分器修改后，可以补评历史结果，不需要重新生成测试：

  ```bash
  python3 gildedrose-lab/scorer/score.py --rescore <旧 run-id>
  ```

## 6. 汇总与比较

```bash
python3 gildedrose-lab/scorer/aggregate.py summarize --runs <run-id> [<run-id> ...]
python3 gildedrose-lab/scorer/aggregate.py compare --runs <run-id> ... --baseline <版本A> --candidate <版本B> \
    --delta 0.05 --tolerance V2=0.05 --tolerance S1=0.05 --tolerance K1.seconds=60
```

- 默认只看开发集（`--set dev`）的修复后阶段（`--phase final`）。
- 结果来自未通过校准的评分器，或者来自不同版本的评分器时，命令会拒绝执行。只做参考时加 `--allow-uncalibrated`。
- `--delta` 和各项容忍值必须在比较之前写定（评测规格第 7 节），不要看了结果再改。

## 7. 宿主机辅助检查（可选，不能替代第 2–4 步）

在没有 Docker 的机器上，可以用本机编译器和 GoogleTest 1.12.1，把校准样本中不依赖 gcov 和 Mull 的部分走一遍：

```bash
export QUALTOR_HOST_CMAKE=<cmake> QUALTOR_HOST_NINJA=<ninja> QUALTOR_HOST_GTEST=<GoogleTest 1.12.1 安装前缀> QUALTOR_HOST_CXX=<C++ 编译器>
python3 -B -m unittest discover -s gildedrose-lab/scorer/tests -p "test_host_integration.py" -v
```

2026-10-24 的做法：在 `/tmp` 中用 venv 安装 CMake 和 Ninja，用官方源码包构建 GoogleTest 1.12.1（SHA-256 与 Dockerfile 一致），编译器为 Apple clang 21。16 个样本各评两次，全部通过，用时约 3.5 分钟。

## 8. 出错时看哪里

| 现象 | 位置 |
|---|---|
| 某份产物的结论 | `result.json` 的 `status`、`invalid_reason`、`infra_detail`、`warnings` |
| 构建失败的原因 | `result.json` 的 `build.diagnostics`；完整日志在 `gcc-build/logs/` |
| 某个测试为什么被判为无效或不稳定 | `gcc-run/step.json` 的 `record`：`full_run`、`isolation`、`stability`；每次运行的 GoogleTest JSON 在 `gcc-run/results/` |
| Mull 的问题 | `mull/logs/` 中 mull-runner 的标准输出和错误输出；报告在 `mull/mull/mutations.json` |
| 容器启动或隔离检查失败 | 产物目录下的 `*-host/` 命令日志；`artifacts/scorer/<run-id>/` 中的镜像与容器记录 |

常见的评分器故障（`infra_error`）：

| 原因 | 含义 |
|---|---|
| `missing_mutation_baseline` | 还没有执行第 2 步 |
| `mull_config_changed`、`mutant_set_mismatch` | 题目的 Mull 算子、被测源码或工具链变了，需要重新标定分母 |
| `clang_build_failed` | 测试在 GCC 下能编译、在 Clang 下不能，需要人工排查 |
| `judge_mismatch` | 宿主机复核与容器内的判定不一致，说明评分器有缺陷 |
| `phase_timeout`、`phase_no_output` | 阶段容器超时或没有写出结果 |

## 9. 2026-10-24 Docker 验证结果

本轮按以上入口在 macOS ARM64 的 Docker Linux ARM64 容器执行，保持禁网、只读源码和资源限制。两套镜像从固定 Dockerfile 构建（复用缓存）并通过验收。

| 检查 | 结果与证据 |
|---|---|
| 工具链验收 | 两套镜像各 9/9 测试通过；[工具链结果](../gildedrose-lab/runs/scorer-docker-build-20261024/summary.json) |
| 分母标定：参考强测试、穷举探针各 2 次 | 47 个变异，参考集检出 47/47；等价候选、不稳定、需复核均为 0；[准入报告](../gildedrose-lab/runs/scorer-docker-prepare-20261024-01/prepare_report.json) |
| 0.1.1 完整校准 | 16/16 样本通过，共 32 次评分，重复结果一致；[校准报告](../gildedrose-lab/runs/scorer-docker-calibration-20261024-02/calibration_report.md) |
| 测试强度区分 | CAL-12/13 为 3/47，CAL-14 为 8/47，CAL-15 为 47/47；四者行覆盖均为 29/29，分支覆盖均为 38/38 |
| 冻结、单份评分、补评、汇总和比较 | 使用校准样本副本及非零合成成本，包含产物篡改、重复运行与未校准结果的拒绝检查；[命令行验收结果](../gildedrose-lab/artifacts/scorer/docker-validation-20261024/cli-checks.json) |

发现并修复了一处成本统计问题：0.1.0 只在评分流程末尾读取 `cost.json`，无效产物提前返回时会丢失成本，导致 K1 汇总漏计失败生成的消耗。0.1.1 提前读取成本，并增加回归测试和校准检查。旧轮次保留原样；用新检查复核旧结果，CAL-01 至 CAL-06 的两轮成本均不一致，见[复核记录](../gildedrose-lab/artifacts/scorer/docker-validation-20261024/old-results-with-cost-check.json)。本轮未调整样本或指标阈值。

全部命令审计见[验证日志](../gildedrose-lab/artifacts/scorer/docker-validation-20261024/)，单份评分的原始构建、gcov、Mull 与容器记录保留在对应运行目录。本轮没有等价候选需要逐个复核，但自动生成的 `review.status` 仍为 `pending`，评分结果保留该提示；没有将代理操作标为人工复核。

本次证明了 GildedRose 开发题的评分链路可用。AMD64、真实缺陷题、模型生成与预算内修复未验证；命令行比较只验证功能，不代表 Agent 质量提升，合成成本也不代表模型实际消耗。
