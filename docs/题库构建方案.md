> **v0.6，2026-10-29。** 本文说明题库（开发集与验收集）的目标、必须补齐的构建与评测能力、题目包组成、准入规则、材料来源、已建成的题目、分阶段计划和已知问题。题目包格式见[评测模块与校准样本设计](评测模块与校准样本设计.md)第 3 节；批量验证与重建步骤见[题库验证说明](题库验证说明.md)。
>
> 状态（2026-10-29）：**阶段 0–1、步骤 A 及步骤 B 的实现、校准、建题与准入已完成**。开发集 115 道，全部在 Linux ARM64 Docker 标定并签署准入（Codex，AI 复核）；assessment 0.4.0 的 8 题 27 样本各两轮通过。步骤 B 新增 12 题、47 个手写变异和 3 个真实缺陷，正式 runner 验收及旧产物补评进度见[题库验证说明](题库验证说明.md)第 15 节。长期层级/数量目标、步骤 C 与验收集仍未完成。

## 1. 目标与现状

### 1.1 目标

- 被评测的模型能力不预设。题库要覆盖从易到难的梯度，GildedRose 这类入门题同样参与比较。
- 生产环境的代码会链接第三方库、混有 C 源文件、依赖编译宏和代码生成步骤，也会用 header-only 库。这些能力必须补齐（第 2 节），题库要有覆盖它们的题目。
- 题目是否被模型见过，不作为准入条件。

### 1.2 规模与现状

| 项 | 开发集（`dev`） | 验收集（`acceptance`） |
|---|---|---|
| 目标题数 | ≥ 100 | 20 |
| 现有题数 | 115（原 100 题 + 步骤 A 三题 + 步骤 B 十二题），均已准入 | 0 |
| 被测代码来源 | 公开代码与公开数据集 | 内部生产代码 |
| 真实缺陷题 | 目标 ≥ 20，现有 4（yaml-cpp 三题、cpp-peglib 一题） | 目标 3–5（D002），现有 0 |
| 等价版本题 | 目标 ≥ 10（D017 修订 D002），现有 1（GildedRose） | 按需 |

- **快速子集**：开发集达到目标层级配比后，按难度层和能力标签分层抽取 30 道，用于日常迭代；全量开发集用于阶段性比较。子集确定后保持固定。
- 开发集与验收集分别汇总，永不合并（[评分算法](评分算法.md)第 5.3 节）。题数少于 10 时，比较结论会标注“题数不足”（同上第 6.1 节）。

### 1.3 难度分层

| 层 | 特征 | 目标 | 现有 |
|---|---|---|---|
| 入门（`easy`） | 单个函数或小类，几十到一两百行 | 约 30 道 | 100 道（含 GildedRose） |
| 中等（`medium`） | 真实库的模块，数百行，常为多文件、有状态 | 约 40 道 | 10 道 |
| 困难（`hard`） | 真实缺陷；依赖第三方库或代码生成；模板；遗留代码 | 约 30 道 | 5 道 |

层级是出题时的预估，写在 `task.json` 的 `tier` 字段。GildedRose 是当前的校准题，改动它的 `task.json` 会使校准过期，所以没有补写 `tier`，按入门层统计。现有题目集中在入门层，中等层与困难层按第 7 节步骤 A–C 补充。

### 1.4 能力覆盖

| 能力 | 开发集最少题数 | 现有题目 | 依赖的改造 |
|---|---|---|---|
| 多文件模块 | 5 | 至少 26（步骤 B 又增加两道含依赖源码的 yaml-cpp 题） | 已可行 |
| header-only 第三方库（随源码入库） | 3 | 1（Theatrical Players 的 nlohmann/json） | 已可行 |
| 链接替身（遗留代码常见测法） | 2 | 1（TirePressureMonitoring） | 已可行 |
| 文件读写、全局状态、随机数 | 各 3 | 各 1 | 已可行 |
| C 源文件 | 5 | 2（md4c、TinyExpr） | R-02 已完成 |
| 链接第三方库 | 5 | 0（HumanEval-X 的 CPP/22、137、162 待接入） | R-01 |
| 按题设置编译宏 | 3 | 1（TinyExpr） | R-03 已完成 |

### 1.5 使用规则

- 验收集只用于最终验证，不用来调试 Agent。skill 和提示词里的示例不取自验收题。
- 结果按全题集和各难度层分别报告：各层题数相差大，只看总平均会被题数最多的层主导。

## 2. 必须补齐的构建与评测能力

这些能力来自生产环境的要求，不是选题的否决条件。改造完成之前，需要某项能力的候选题登记为“待能力”并注明 R 编号，改造完成后再出题。

| 编号 | 能力 | 现状（证据） | 要求 | 步骤（第 7 节） |
|---|---|---|---|---|
| R-01 | 链接第三方库 | 产品与评测的 CMake 模板只链接 GoogleTest/gmock；镜像只装工具链 | 能声明并链接第三方库，库在离线容器中可用 | 步骤 C |
| R-02 | C 源文件 | **已完成**：两套模板启用 C/CXX；显式 C99/C11，guard 只用于 CXX；CAL-19/20 及真实生成通过 | 被测与依赖文件可以是 `.c`；被测 `.c` 同样统计覆盖、做变异 | 步骤 A |
| R-03 | 按题设置编译宏与选项 | **已完成**：build 宏及白名单选项作用于三类编译单元，compile_commands 核对通过 | 题目可声明宏和白名单内的编译选项 | 步骤 A |
| R-04 | 代码生成步骤与生成的配置头 | 没有生成步骤 | 支持 moc、protoc 等生成器；构建时生成的配置头有固定处理方式 | 步骤 C |
| R-05 | 依赖源文件（support_sources） | **已完成**：support 编译链接；只统计 target；纯头文件题覆盖率构建给所有单元插桩，防止链接丢计数 | 依赖文件参与编译链接，但不变异、不统计其自身覆盖 | 步骤 A/B |
| R-06 | header-only 与以模板为主的代码 | **已实现并校准**（D018，0.4.0）：顶层 target_headers、冻结 C1/C3，C2/M1 不适用；零变异同样有显式状态 | 纯头文件或源码二选一，缺陷检出由手写变异及真实缺陷衡量 | 步骤 B |
| R-07 | 替换版本替换头文件 | **已实现并校准**（D018，0.4.0）：复制并核对完整源码树，在副本原位替换，记录树哈希 | 支持被测源码、被测头文件和可见头文件；不替换依赖源文件 | 步骤 B |
| R-08 | 多题校准与新题准入门禁 | **已完成**（D016，0.2.1 Docker 校准与两处失效边界回归通过）：校准覆盖所有带样本的题目，任何校准题变化都使校准过期；`benchmark/admission.json` 按题目指纹登记准入，runner 与汇总据此拦截 | 能校准所有题目的样本；未准入的题不能进入正式评测 | 第一批（已完成） |
| R-09 | 规模化工具 | 已有建题、批量标定、复核结论落实、准入签署与固定工具链取证工具（第 6 节），已支撑 115 道题；缺分层汇总和变异计数命令 | 支撑 100 道以上题目的建设与汇总 | 部分完成 |

**各项方案要点：**

- **R-01**：在固定工具链镜像上叠加“构建环境”层，同一份依赖配方分别生成 GCC 版和 Clang 版镜像，版本锁定、运行时离线。题库配一个公共环境，产品支持用户指定自己的构建环境。小型依赖也可以随题入库，作依赖源文件编译。`task.json` 增加链接库与第三方头文件目录。涉及两套 Dockerfile 和 CMake 模板、`agents/generator/task.py`、`evaluator/runner/host.py`、`evaluator/assessment/common.py`。
- **R-02**：模板启用 C 语言，题目声明 C 标准。被测 `.c` 插桩并加载 Mull 插件（Mull 支持 C）。C++11 断言头只加给 C++ 编译单元。测试仍用 C++ 和 GoogleTest 编写。
- **R-03**：`task.json` 增加宏与白名单内的编译选项，作用于被测、依赖和测试编译单元，两套构建一致，并用 `compile_commands.json` 核对。
- **R-04**：构建前一次性生成的配置头，出题时生成并随源码入库，在 `SOURCE.json` 注明来源，现在即可执行。必须在构建中运行的生成器（moc、uic、rcc、protoc）由模板按白名单支持，同时作用于测试编译单元。版本约束：Qt 6 要求 C++17，只能用 Qt 5；protobuf 22 起要求 C++14（待核实）。
- **R-05**：`support_sources` 参与编译链接，不加载 Mull 插件。源码题不对它插桩；纯头文件题给全部编译单元插桩，避免 COMDAT 保留未插桩实例而丢计数，统计仍只含被测头文件。
- **R-06**：顶层 `target_headers` 与非空 `target_sources` 互斥。覆盖率构建给全部编译单元插桩，以参考测试和准备阶段的显式实例化文件冻结行、函数集合，写入 `hidden/coverage_baseline.json`；C1/C3 仅在冻结集合上计算，C2 不适用。M1 为 `header_only`，无效产物也不记 0。准入要求参考 C1≥0.8、有效稳定，至少 5 个手写变异（四个小题至少 3 个）全部检出，真实缺陷全检出、等价版本全通过且无 pending。
- **零变异题**（已实现）：只在准备阶段依据正常退出、stdout 含 `No mutants found`、无报告三个条件认定 `zero_mutants`，保存两轮原始证据。M1 始终不适用（含 invalid），其余准入要求与纯头文件题相同；评分时不运行 Mull。M1 适用题评分缺报告仍判 `infra_error`。hello-world、reverse-string 和 linked-list 已重新导入。
- **R-07**：替换版本可以包含被测头文件，按 D018 在源码树副本中原位替换，再只读挂载；同目录引号包含不能由 -I 覆盖。
- **R-08**（已完成，0.2.1 Docker 校准与失效边界回归通过）：校准运行所有题目的样本并记录全部题目指纹；门禁增加“已准入题目”清单 `benchmark/admission.json`，由 `benchmark/tools/admit.py` 在复核人签署后写入。0.2.0 校准通过后，可以在 `calibration/<题目 ID>/` 下给新题添加样本（样本 ID 全局唯一）。

**共同要求**：每一批改造都要升评测模块版本并完整校准；公开任务保留 9 个必填字段，可选字段为 `build`（D017）和 `target_headers`（D018），同步修改 runner 投影；补充对应能力的校准样本与验证题；新增决策记录，更新产品 README。

## 3. 一道题包含什么

```text
benchmark/<task-id>/
  task.json                               # 题目卡，见附录 A
  source/                                 # 被测项目源码（按需截取），含 SOURCE.json 与许可证
  hidden/
    README.md                             # 本题隐藏材料的来源与生成方式
    reference_tests/*.cc                  # 参考强测试集（必备）
    equivalence_probe/tests/*.cc          # 探针（M1 不适用时可省略）
    equivalence_probe/generate_probe.cc   # 探针生成器（生成型探针随题保存）
    mutation_baseline.json                # 变异分母：prepare_task.py 生成，复核后签署
    coverage_baseline.json                # 纯头文件题冻结行/函数集合
    coverage_instantiation/*.cc           # 可选，只在准备阶段补齐模板实例
    variants/<variant-id>/<被替换文件>     # 替换版本（按需）
```

| 材料 | 用途 | 对 Agent | 完成标准 |
|---|---|---|---|
| 被测源码与 `SOURCE.json` | 题目本体，来源追溯 | 只投影 `visible.files` | 仓库地址、提交号、文件哈希齐全；保留许可证；Qualtor 添加的文件列在 `added_by_qualtor` |
| `task.json` | 题目卡 | 只投影公开字段 | `prepare_task.py` 能加载；`title` 中立 |
| 参考强测试集 | 证明可解；确定冻结分母；替换版本准入 | 不可见 | 有效、稳定；M1 适用时 ≥ `reference_min_m1`（0.8），不适用时按 D018 检查 C1 与手写变异 |
| 探针 | 识别等价变异 | 不可见 | 有效、稳定；包含全部参考测试 |
| 变异分母 | M1 的冻结分母 | 不可见 | 准备通过并写入；每个等价候选有复核结论，经复核人用 `admit.py` 签署 |
| 替换版本 | M2、M4、F1 | 不可见 | 准入通过；等价版本附差分检查 |

**探针模式**（`task.json` 的 `preparation.probe_mode`）：
- `generated`：生成器在原代码上运行大量输入，记录实际结果，并包含全部参考测试。探针也区分不出的变异列为等价候选。
- `reference_copy`：探针就是参考测试的副本。等价候选即参考测试没杀死的变异，变异分母为参考测试能检出的变异。准备工具算出的参考 M1 必然为 1，要看批量标定汇总里的“原始检出率”判断参考测试强弱；复核时把不等价的变异移回分母（`mutant_review/`）。

**题目卡注意事项**：
- `title` 会写进 Agent 看到的 TASK.md，只写中性描述；`description`、`tier`、`tags`、`preparation` 不会投影给 Agent。
- `visible.files` 要包含编译所需的全部头文件，包括随源码入库的 header-only 第三方库。参考测试、探针和替换版本绝不能列入。

## 4. 准入与难度标定

**准入条件**：只针对题目本身的质量，与构建方式无关。
1. 能编译：按题目声明的标准（C++ 部分为 C++11）被 GCC 14.2.0 和 Clang 19.1.7 编译。所需能力未实现时登记为“待能力”。
2. 能确定性运行：在禁网、2 CPU / 2 GiB / 256 进程的容器中运行，结果不依赖时间、网络或外部状态；单个测试在 `test_timeout_seconds` 内完成。
3. 参考强测试集达到强度：M1 适用时 ≥ 0.8；`reference_copy` 题结合原始检出率与逐项复核判断；纯头文件、零变异题按 R-06。
4. 隐藏材料不出现在可见文件中，来源可追溯。

**难度标定**：
- 不按难度淘汰题目。
- 用基线配置（最简单的提示词）每题试跑 3 次，按最终阶段端到端 M1 修正 `tier`；没有 M1 的题用覆盖率。
- 全部 trial 都无效时，先排查题目本身的构建配置和可见文件，确认无误后保留为困难题。

**规模控制**：
- 变异数上限按人力定，即参考测试达标和等价候选复核的工作量，不按运行时间定（GildedRose 47 个变异的 Mull 只用 35 毫秒）。
- 提议值：每题 100–500 个变异，入门题可以更少。
- 控制手段：只列要考的文件、拆题；R-05 完成后移出依赖文件；必要时全题库统一收窄变异算子，并重新标定。不删改源码。

- HumanEval-X、Tennis 与 Parrot 的生成输入，都由生成器在原代码上执行：每个输入在子进程中运行，用 ASan、UBSan 与 libc++ 断言过滤掉触发未定义行为、崩溃、超时或超过 20 毫秒的输入；再用带 ASan 与不带 ASan 两种构建、不同的栈与堆填充共跑 4 遍，只保留每遍都正常结束且结果相同的输入（读未初始化变量的输入在不同栈布局下结果不同而被淘汰；2026-10-27 第 17 组的 `minPath` 崩溃后由原来的两遍改为 4 遍）；最后用 GCC 14 + libstdc++ 回放，删去与 libc++ 结果不一致的断言。
- 未纳入的来源及原因：
  - HumanEval-X 的 CPP/22、CPP/137 需要 Boost，CPP/162 需要 OpenSSL，等 R-01；
  - Exercism 有 15 个练习未纳入：12 个参考解需要 C++14 以上（含使用 C++17 语法的 list-ops），meetup 依赖 Boost（R-01，归步骤 C），2 个测试需要人工转换。步骤 B 的 7 个练习已全部接入。

### 5.2 后续题目的来源

| `apply_review.py` | 把复核结论落到已有分母上（移回分母，或按 D015 列为不稳定），或核对是否都已落实 |
| `admit.py` | 核对准入条件（分母达标、复核结论已落实、每个等价候选都有结论且没有待补证据的标记），由复核人签署并登记到 `benchmark/admission.json` |
| `tests/` | 复核结论相关逻辑的单元测试（`python3 -B -m unittest discover -s benchmark/tools/tests`） |
| `mutant_ir.py` | 在固定 Clang/Mull 镜像中导出带变异的 IR，列出每个变异生效副本删改的调用（如“删除调用”实际删的是哪个析构）；`--resolve` 在证据与结论一致时清除 pending |
| `ub_sweep.py`、`ub_drivers/` | 在固定 GCC 镜像中用 libstdc++ 断言加 ASan/UBSan 复核变异的源码副本，区分等价与只在未定义行为下不同（D015）；`--resolve` 同上 |

**单题流程**：
1. 登记候选（附录 B），对照第 4 节检查；需要未实现的能力时登记为“待能力”。
2. 源码入库到 `source/`，写 `SOURCE.json`。
3. 写 `task.json`。
4. 编写参考测试和探针。
5. 在 Docker 中检查 C++11 构建、参考测试与替换版本；宿主机仅编排容器。
6. Docker 标定（`--write`）。
7. 复核等价候选：能区分的写成反例放进 `mutant_review/<题目 ID>/review_tests.cc`，已证明不等价的记入 `confirmed.json`，等价的在 `equivalent.json` 写明理由；需要固定工具链证据的先标记 `pending`，用 `mutant_ir.py`、`ub_sweep.py` 补证。材料有变化时重建题目，回到第 5 步。
8. 难度标定。
9. 登记证据 run-id，由复核人用 `admit.py` 签署准入。

**runner 保护（已实现）**：`evaluator/run.py` 选题时：
- 点名一道还没有 `mutation_baseline.json` 的题，会在生成前报错；用 `all` 或 `--set` 批量选题时，跳过这类题并打印提示；
- 未准入或准入已失效的题同样处理：点名报错，批量跳过（R-08）；冒烟和新题试跑加 `--allow-unadmitted`，结果不能用于正式比较。
