# 测试评测运行说明

评测模块、题目包和校准样本怎么用：在装有 Docker 的机器上标定变异分母、校准评测模块、给测试产物打分、汇总比较。整体职责、执行流程与样本见[评测模块与校准样本设计](评测模块与校准样本设计.md)，计算规则见[评分算法](评分算法.md)。

> 当前版本 **0.4.0**，已通过 Linux ARM64 Docker 完整校准：8 题 27 个样本各两次全部通过，见[本轮校准报告](../runs/step-b-calibration-20261029-01/calibration_report.md)。新增纯头文件、零变异和原位替换头文件；步骤 B 的标定、补评与正式 runner 证据见第 16 节及[题库验证说明](题库验证说明.md)第 15 节。

第 1–8 节为现行用法；第 9–16 节为按版本保存的验证记录，历史命令不能直接作为当前入口。

## 前提

- Docker 已启动，两个固定版本的工具链镜像已经构建并通过验收（见 [C++11 固定工具链](C++11固定工具链.md)）。可以用下面的命令确认：

  ```bash
  python3 evaluator/toolchains/toolchains.py --skip-build
  ```

- 宿主机 Python 3.9+，只用标准库。所有命令都从项目根目录执行。
- 分母标定、校准和独立单份评测各创建新的 `runs/<run-id>/`，`run-id` 不能重复；补评写入原 run 的新版本目录。`aggregate.py` 默认只输出 JSON，指定 `--out` 才写文件，不自动新建 run。

## 1. 单元测试

下面是测试命令。按本轮用户要求，四组单元测试、导入预检与材料核对均在 Docker 中执行；维护容器提供 Python、Node、Git，不改变正式评分镜像和宿主机环境。宿主机只编排 Docker；生成用的 pi 仍按 D013 运行。

```bash
python3 -B -m unittest discover -s evaluator/assessment/tests -p "test_*.py"
```

包括解析器（用 gcov、Mull 的真实输出）、判定逻辑、汇总与比较、校准检查、题目包与产物校验、准备工具，以及 Docker 模式的接线检查。宿主机集成测试没有设置环境变量时会跳过，见第 7 节。

## 2. 标定变异分母（首次，或者题目、Mull 算子、工具链变化后）

```bash
python3 evaluator/assessment/prepare_task.py baseline --task gildedrose-update-quality --write
```

- 用参考强测试集和有界穷举探针各评分 2 次，每次都跑全部步骤（包括 Mull 和替换版本）。
- 输出：`runs/<run-id>/prepare_report.json` 和分母草稿 `runs/<run-id>/mutation_baseline.json`。
- 检查全部通过时，`--write` 才会写入 `benchmark/gildedrose-update-quality/hidden/mutation_baseline.json`；已存在时需要再加 `--force`。
- 命令打印变异总数、等价候选数、不稳定数、需复核数，以及参考强测试集的 M1（要求不低于 0.8）。

纯头文件题用 `target_sources: []` 和非空 `target_headers`，准备阶段给全部单元插桩，生成 `coverage_baseline.json`。没有被测源文件时 M1 为 `header_only`；Mull 正常退出、stdout 含 “No mutants found” 且没有报告时，准备阶段才认定 `zero_mutants` 并保存 stdout。两类题的 M1 在评分时均为 null（含 invalid），纯头文件 C2 也为 null；M1 适用题评分时缺报告仍是基础设施错误。M1 不适用题按冻结/普通 C1≥0.8、手写变异至少 5 个（四个小题至少 3 个）且全部检出等条件准入，探针可省略。

出现以下情况时命令失败，并写出问题清单：参考测试或探针本身有无效、不稳定的测试；各次 Mull 的变异集合不一致；参考强测试集强度不够；替换版本准入不通过（应失败的版本没被检出，或等价版本上出现误报）。

参考测试检出、而探针未检出的变异列为不稳定（D015）。题库题目用 `benchmark/tools/prepare_new_tasks.py` 批量标定：它在写入前落实 `benchmark/tools/mutant_review/` 的复核结论，命令见[题库验证说明](题库验证说明.md)。

新增校准题时，先准备校准所必需的种子分母并收敛参考材料，再完整校准新版本，然后正式标定、复核、签署。若正式标定改变了校准题分母的等价或不稳定清单，校准会 stale，须再次完整校准；只改签署元数据不影响状态（D017）。

## 3. 人工复核等价变异

打开 `hidden/mutation_baseline.json`，逐个看 `equivalent` 里的候选：根据 `id` 中的算子和位置，判断它是真正的等价改动，还是引入了未表现出来的问题。复核完把 `review` 改为：

```json
"review": {"status": "reviewed", "by": "<复核人>", "at": "<日期>", "note": "<结论>"}
```

不是等价的变异，从 `equivalent` 移回分母（删除该条目），并重算参考强度。复核之前，每份评分结果都会带一条 `mutation_baseline_review: pending` 警告。改动校准记录所含题目的 `equivalent` 或 `unstable` 清单会让校准状态过期，需要重新校准；只改 `review` 字段不会。当前校准覆盖 GildedRose、步骤 A 三题和步骤 B 的 circular-buffer、hello-world、yaml-cpp-node-impl、yaml-cpp-emitter-utils；其他题目的分母修订仍须独立核验和重新评分，不能凭全局校准通过视为已验收。

2026-10-27 的 [逐项复核](../runs/bank-review-20261027-03/index.md)覆盖当前 100 题的 689 个条目，另有 [37 题分母修订草稿](../runs/bank-review-20261027-03/baseline-proposals/changes.json)。已验证不等价的 121 项记入 `benchmark/tools/mutant_review/<题目 ID>/confirmed.json`，对应反例作为复核补充测试并入参考测试与探针。题库批量标定（`benchmark/tools/prepare_new_tasks.py`）写入分母前，会把仍被探针判为等价候选的已确认项移回分母并重算参考强度；不需重新标定的题用 `benchmark/tools/apply_review.py` 修订和核对。补强后的 40 题已在 Linux ARM64 全部重标定通过，37 题确认项核对退出码 0；最新清单为 [2026-10-28 清单](../runs/bank-review-20261028-04/index.md)。进度见[题库验证说明](题库验证说明.md)第 9 节。仍有未决项的题不能批量标为 `reviewed`。源码层的变异写法只是示意，应核对实际 Mull IR；固定随机种子、小样本幸存或一次 sanitizer 未报错均不能证明等价。按 D011 审查原程序所有有定义输入。

## 4. 校准评测模块

```bash
python3 evaluator/assessment/calibrate.py --jobs 2
```

- 默认校准 `calibration/` 下所有带样本的题目（CAL-01–16、CAL-18–28，共 8 题 27 个样本），每个样本评 2 次，每次都在全新的容器里执行。样本 ID 在全部题目中唯一。
- 输出：`runs/<run-id>/calibration_report.md`（可读的结果表，按题目列出样本）和 `calibration_report.json`。
- 全部通过时，`evaluator/assessment/calibration-status.json` 记为通过，并写入版本、代码、样本、每道校准题目和镜像的指纹。入口读取时核对这些条件；变化后状态过期，需重新校准。题目能否进入正式比较另看准入（第 6 节、D016），不能凭其他题目的校准认定其已验收。
- 每轮还核对输出中的 `cost` 和 `metrics.K1` 与输入 `cost.json` 一致，包括被判无效的样本。
- 只想先排查某几个样本或某道题时，可以运行 `--samples CAL-01,CAL-07` 或 `--task <题目 ID>`。这样只写报告，不更新校准状态。
- CAL-12、CAL-15 的数值阈值已固定。后续调整须记录理由、升评测模块版本并重新校准。
- 正式评测前由入口检查校准状态；版本和相关指纹未变时复用 passed 记录，不必每轮重新校准。纯文档整理不触发代码指纹变化。

检查报告时重点看：

- CAL-12、CAL-15 的 C1 有值，说明容器内的 gcov 采集正常；
- CAL-07 不是评测模块故障，说明 Mull 的测试过滤生效了；
- CAL-18–20 与 0.3.0 的精确值一致；CAL-23 的 C1 为 20/25；CAL-24 的 M1 不适用；CAL-21/27 的 M4 为 0；
- 所有样本都没有“重复评分结果不一致”。

## 5. 给一份测试产物打分

外部准备的测试先复制到独立产物目录 `<产物目录>/tests/*.cc`，作为待评测快照，再记录文件清单和哈希，最后评分。`freeze_product.py` 只生成清单，不复制测试；生成产品输出的 `first/`、`final/` 已包含快照和清单，可直接进入评分。

```bash
python3 evaluator/assessment/freeze_product.py <产物目录>
python3 evaluator/assessment/evaluate.py --task gildedrose-update-quality --product <产物目录> \
    --cost <cost.json> --agent-version <版本> --trial 1 --phase final
```

- `cost.json` 的格式：`{"tokens": {"input": 0, "output": 0, "cache_read": 0, "cache_write": 0}, "seconds": 0, "model_calls": 0, "repair_rounds": 0, "usd": null}`。
- 无效产物也保留生成成本并参与 K1 汇总；未传入成本文件时记录 `cost_missing`。
- 结果写在 `runs/<run-id>/trials/<task-id>/trial-<k>/score/<评测模块版本>/<阶段>/result.json`。
- 校准状态不是 passed 时，命令拒绝评分并退出；只做参考时加 `--allow-uncalibrated`，结果里会记录校准状态，汇总和比较时仍会被拦下。
- 评测模块修改后，可以补评历史结果，不需要重新生成测试：

  ```bash
  python3 evaluator/assessment/evaluate.py --rescore <旧 run-id>
  # 中断后直接重跑同一命令：指纹匹配的有效结果跳过；未完成或失效结果移入同级 incomplete/ 后重评
  ```

## 6. 汇总与比较

```bash
python3 evaluator/assessment/aggregate.py summarize --runs <run-id> [<run-id> ...]
python3 evaluator/assessment/aggregate.py compare --runs <run-id> ... --baseline <版本A> --candidate <版本B> \
    --delta 0.05 --tolerance V2=0.05 --tolerance S1=0.05 --tolerance K1.seconds=60
```

- 补评写入原 run，保留旧评分版本。仅复用同版本且评测模块代码、校准、题目、产物和镜像指纹匹配的有效结果；JSON 半写、基础设施错误、旧指纹或未校准参考结果移入 `incomplete/` 后重评。每次补评的 `rescore.json` 独立记录，异常或中断记为 `failed`；原 `run.json` 保持不变。用 `--assessment-version <版本>` 选择评测模块版本，当前版本号见 `evaluator/assessment/VERSION`（旧 `--scorer-version` 仍可用），被移开的 `incomplete/`、`infra-retries/` 结果不参与汇总。
- 默认只看开发集（`--set dev`）的修复后阶段（`--phase final`）。
- 结果来自未通过校准的评测模块，或者来自不同版本的评测模块时，命令会拒绝执行。只做参考时加 `--allow-uncalibrated`。
- 结果所属题目未准入，或评分时记录的题目指纹（`task.sha256`）与准入登记不一致时，命令也会拒绝执行（D016）。0.2.0 之前的结果没有题目指纹，需要先补评。只做参考时加 `--allow-unadmitted`。
- 准入：`python3 benchmark/tools/admit.py` 列出每道题能否签署；复核人确认后用 `--tasks <题目 ID>... --by <复核人> --write`（或 `--ready --by <复核人> --write`）签署分母并登记到 `benchmark/admission.json`。题目材料或分母之后任何变化都会使准入失效。
- `--delta` 是必填参数；`--tolerance` 没有默认值，程序只检查传入的项。正式比较需事先确定全部适用守护指标并显式传入；上面数值只是命令示例，不是项目已定标准。M2、M4、F1 有数据时也应按规格纳入。
- `compare` 默认使用最终阶段的 `M1_e2e`，两层 bootstrap 默认 10000 次、种子 20261024。加 `--out <文件>` 保存比较结果；生成 run 的汇总不会自动得出两个 Agent 版本的比较结论。

## 8. 出错时看哪里

| 现象 | 位置 |
|---|---|
| 某份产物的结论 | `result.json` 的 `status`、`invalid_reason`、`infra_detail`、`warnings` |
| 构建失败的原因 | `result.json` 的 `build.diagnostics`；完整日志在 `gcc-build/logs/` |
| 某个测试为什么被判为无效或不稳定 | `gcc-run/step.json` 的 `record`：`full_run`、`isolation`、`stability`；每次运行的 GoogleTest JSON 在 `gcc-run/results/` |
| Mull 的问题 | `mull/logs/` 中 mull-runner 的标准输出和错误输出；报告在 `mull/mull/mutations.json` |
| 容器启动或隔离检查失败 | 产物目录下的 `*-host/` 命令日志；`runs/<run-id>/evidence/` 中的镜像与容器记录 |

Docker Desktop 休眠时可能由宿主机 API 缓存对短镜像名误报 `No such image`。当前镜像配置已使用 `docker.io/library/…` 完整名称查询，再按镜像 ID 创建容器；不需要修改题目、分母或恢复标签。排查步骤及 2026-10-28 的直接日志证据见 [C++11 固定工具链](C++11固定工具链.md)。此次只修改引用名称，原镜像 ID、assessment 代码和校准样本指纹未变，0.3.0 校准保持有效。

常见的评测模块故障（`infra_error`）：

| 原因 | 含义 |
|---|---|
| `missing_mutation_baseline` | 还没有执行第 2 步 |
| `mull_config_changed`、`mutant_set_mismatch` | 题目的 Mull 算子、被测源码或工具链变了，需要重新标定分母 |
| `compile_commands_mismatch` | 真实编译单元、语言标准、公开宏/选项或插桩范围与任务不一致 |
| `clang_build_failed` | 测试在 GCC 下能编译、在 Clang 下不能，需要人工排查 |
| `judge_mismatch` | 宿主机复核与容器内的判定不一致，说明评测模块有缺陷 |
| `phase_timeout`、`phase_no_output` | 阶段容器超时或没有写出结果 |
