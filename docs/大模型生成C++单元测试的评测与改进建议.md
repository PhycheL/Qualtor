# 大模型生成 C++ 单元测试的评测与改进建议

> 规划文档，2026-10-22 重写。文中的建议和“待实现”项都不是已完成的功能。现状数据来自 [cpp-only-20261021](../gildedrose-lab/runs/cpp-only-20261021/summary.json) 的运行结果，以及 2026-10-22 对这些结果的离线核查。整件事分几步推进、每一步怎样算完成，见[项目推进流程](项目推进流程.md)；具体的测评内容、方法、指标和流程，见[评测规格](评测规格.md)。

> 2026-10-23 更新：旧实验执行代码已移除，第 1 节保留为历史分析；其中引用的旧脚本可在 [历史 ZIP](../gildedrose-lab/deliverables/全量执行过程.zip) 中查阅。当前工具链及其验收范围见 [C++11 固定工具链](C++11固定工具链.md)，正式评分能力以评测规格的实现状态为准。

> 2026-10-23 决定（[D002](决策记录.md)）：本文提到的 sanitizer、极端变异和静态扫描（断言统计、脆弱写法）不实施；真实缺陷和等价版本小规模实施。范围与口径以[评测规格](评测规格.md)为准，本文保留为设计理由。

目标：让大模型自动生成 C++ 单元测试，用可复现的执行结果评价这些测试的质量，再据此改进 Agent 和 skill。

范围（2026-10-22 已定，见[决策记录](决策记录.md)）：Agent 全自动读取已有 C++ 代码并生成单元测试，**断言以被测代码的实际运行结果为准**。代码是否符合需求，由后续的功能测试负责，不属于本阶段。

**核心判断：** 现有闭环证明了测量仪器能跑，每一步都能追溯。下一步不是加题、加指标，而是先证明这把尺子量得准：测的是对的东西；标准答案有独立来源；能分清好测试和坏测试；版本差异大于运行噪声；结论能被你我之外的证据确认。

## 1. 现状

### 1.1 已经证明了什么，还不能说明什么

已实现，并在容器内验证过：

- Docker 内由 Python 驱动 CMake、CTest 和 gcov；源码只读挂载，评测容器禁网，命令和输出全程审计。
- 规则脚本生成 13,965 条输入记录（互异输入 13,187 个），`GildedRose.cc` 的行覆盖为 29/29、分支覆盖为 38/38。
- 20 个手写行为变异全部检出，6 个编译/链接错误全部捕获，2 个等价改动没有误报。
- 44 道输出预测题全部答对。

这些都不是“大模型生成单元测试”的成绩：测试由规则脚本生成，盲测考的是预测程序输出。而且出题、写标准答案、注入 Bug、答题都出自同一会话的模型。各项 100% 是这种自洽设计的必然结果，不能算能力证据。

### 1.2 对现有结果的进一步核查

下表是 2026-10-22 在宿主机上对 `runs/cpp-only-20261021` 已有结果做的离线计算，没有纳入流水线，也没有保存为运行产物。标注“按源码推导”的条目，尚未编译运行验证。

| 发现 | 依据 | 影响 |
|---|---|---|
| 最多 8 条输入就能杀死全部 20 个行为变异。M11 与 M12 的杀死集合完全相同；M06、M10、M14、M15、M19、M20 被其他变异蕴含；真正独立的只有 13 类。M18、M13 分别只有 15、16 个互异输入能杀死 | 各变异的 `test_result.json`，逐个结果见[变异明细](变异明细.md) | 用例总数和测试强度关系不大；手写变异有冗余，100% 的分母偏松 |
| 历史 `scripts/cases.py` 的 oracle 默认 quality 在 0–50 之间、Sulfuras 为 80，超出这个范围就会和 C++ 不一致：Aged Brie 质量为 60 时，oracle 给 50，代码保持 60；Elixir 质量为 −5 时，oracle 给 0，代码保持 −5 | oracle 一侧实际计算；C++ 一侧按源码推导 | 输入域没有写成契约。拿它评判模型写的测试，域外输入会被误判 |
| gcov 文本结果与 JSON 结果一致 | 两者都是同一个 gcov 读同一个 `.gcda`（[coverage.py](../gildedrose-lab/scripts/coverage.py)） | 只证明解析器正确，不是两次独立测量 |
| `status: passed` 要求所有变异都被杀死 | 历史 `scripts/pipeline.py` 中的 `valid` 条件 | 仪器自检和测试评分混在了一起。接入模型测试后，“测试太弱”会被报成“流水线失败” |
| `GildedRose` 的成员是引用 `std::vector<Item>&`；`sellIn - 1` 在 `INT_MIN` 时会有符号溢出 | 按源码推导 | 模型写的测试夹具可能留下悬垂引用，极值测试可能触发未定义行为；不开 sanitizer，这些测试可能“碰巧通过” |
| 旧镜像里没有 GoogleTest，评测容器禁网，而上游 CMake 用 FetchContent 在线拉取 GoogleTest | 历史 `docker/Dockerfile`、上游 `cpp/test/CMakeLists.txt` | 接入生成测试之前，要在镜像构建阶段装好固定版本的 GoogleTest；当前两套工具链已完成此项 |
| GildedRose 是公开的 kata，GitHub 上有 6 千多个 fork | 上游 GitHub 页面 | 模型很可能见过现成的测试，这道题只适合作开发题 |

计算方法：把 M01–M20 各自 `test_result.json` 中的 `mismatches` 作为杀死记录，按 `(name, sell_in, quality, days)` 去重。变异 A 的杀死集合是 B 的真子集时，称 A 蕴含 B：能杀死 A 的输入都会杀死 B，B 就是冗余的。8 条是用贪心集合覆盖得到的上界。

## 2. 先定义“好测试”

生成的测试集按下面五个方面评价。第 1 项是门槛，不达标的不进入后面的评分。

1. **有效**：能编译、链接；测试被发现并真正执行，不是零测试或全部跳过；在被测代码上全部通过；ASan/UBSan 没有指向测试代码本身的报告；重复运行、打乱顺序后结果一致。sanitizer 报在产品代码上的问题单独记录，那可能说明测试发现了缺陷。
2. **敏感**：被测行为改变时，测试会失败。主指标是“最小非等价变异检出率”（第 4 节）。
3. **特异**：行为没变时，测试不会失败，用等价重构上的误报率衡量。以实际行为为准的测试，最常见的毛病是把实现细节写死；只看敏感，会奖励这种测试。
4. **成本**：token、时间、修复轮次。首次生成的成绩和预算内修复后的成绩分开报告。
5. **可读、可诊断**：命名清楚，失败信息能定位问题。这一项靠人工抽查，不计入主分。

断言的预期值以被测代码的实际运行结果为准，所以：

- 测试在被测代码上失败，就是测试本身写错了，可以全自动判定，不需要需求文档。
- Agent 要能在沙箱里编译、运行目标代码，才能拿到实际结果。生产环境能否提供目标项目的构建环境，是待确认的前提。
- 分数主要反映两件事：选了哪些输入和场景，断言是否完整地检查了结果。
- 已知代价：如果被测代码本身有缺陷，测试会把缺陷行为一起锁定。这不在本阶段的评分范围内，由后续功能测试发现。

## 3. 标准答案从哪来

- **角色分开**：出题、写标准答案、注入 Bug 的一方，不能和被测的 Agent 是同一来源。至少要做到：正式评分用的 Bug 和参考答案，不由被测 Agent 所在的会话产生。
- **写明输入域**：每道题写明评分所用的输入域，例如 GildedRose 的 quality 0–50、Sulfuras 为 80。评分器的参考实现只在输入域内保证与被测代码一致；断言域外输入的测试单独计数，不算对也不算错。第 1.2 节里 oracle 与 C++ 在域外不一致，就是没写明输入域的后果。
- **用真实的历史改动当“天然变异”**：取真实项目里的一次缺陷修复，在修复后的版本上生成测试（断言仍以这个版本的实际行为为准），再看测试能否在修复前的版本上失败。修复由原项目开发者完成，不是你我写的，比手写变异更可信。C++ 现成可复现的来源有：
  - BugsC++：22 个项目、209 个真实 Bug，用 Docker 封装；
  - Defects4C（ASE 2025）；
  - Multi-SWE-bench 的 C++ 部分：Catch2、fmt、nlohmann/json、simdjson、cpp-httplib；
  - ARVO：OSS-Fuzz 发现的 C/C++ 漏洞，附开发者补丁。

  如果 Agent 最终要服务自己的仓库，从它的 git 历史和缺陷单里抽题更好：题目分布对，模型也没见过。
- **人工判定要有规程**：需要人判断的地方（幸存变异是否等价、测试是否可读），由两人各自独立判定，再计算两人的一致性（Cohen's κ），有分歧再仲裁。只有在用这些人工标签校准之后，才能让大模型参与评分。

## 4. 尺子：评分流程与分母

| 层次 | 内容 | 用途 |
|---|---|---|
| 门槛 | 编译、链接；用 `--gtest_list_tests` 和 `--gtest_output=json` 核对发现数、执行数、跳过数；在被测代码上全部通过；ASan/UBSan；`--gtest_shuffle --gtest_repeat=N`，以及每个测试单独运行 | 不达标的判为无效，并记录原因 |
| 主指标 | 最小非等价变异检出率 | 比较 Agent/skill 版本的主要依据 |
| 守护指标 | 等价重构误报率、首次和修复后的有效率、不稳定率、成本 | 主指标提高时，这些不能变差 |
| 诊断指标 | 行覆盖、分支覆盖、复杂条件的 MC/DC、极端变异、断言统计 | 用来解释原因，不单独作为能力结论 |

仪器自检（编译错误捕获、等价对照、校准样本）单独输出，不和被评测试的成绩混在同一个 `status` 里。报告时区分用例记录数、互异输入数、测试函数数和题目数。

变异集按以下步骤建：

1. 用工具按标准的变异算子系统生成，例如 Mull（基于 LLVM，被测程序要用 Clang 编译），或 universalmutator（CITYWALK 用过）。
2. 用 TCE 剔除等价变异和重复变异：用 -O2/-O3 编译变异体，比较目标码。TCE 论文在大型程序上剔除了 7% 以上的等价变异和 21% 以上的重复变异。
3. 用现有的有界穷举用例检查剩下的变异：在声明的有界输入域内都区分不出来的，标为“有界等价”，单独列出并人工确认。现有的 13,965 条用例在这里正好派上用场，它们从“被评对象”变成了“评测仪器”。
4. 用杀死矩阵做蕴含分析，只在最小变异集合上算分。不处理冗余变异会扭曲实验结论：Papadakis 等人估计，不采取对策的实验约有 62% 会出现第一类错误（把没有的差异当成有）。
5. 手写变异保留下来，作为“重点关注的缺陷”单独统计（Meta ACH 的思路），不并入主分母。
6. 做极端变异：把被测函数的函数体清空。如果测试仍然全部通过，说明它是空测试。

覆盖率只统计指定的业务源码，并说明分母。它只说明代码被执行到了哪里，不说明执行结果被检查过。例如在 ULT/PLT 论文里，模型在 TestEval 上的平均语句覆盖是 92%，变异分数却只有 50%。覆盖率的交叉验证要用独立的实现，例如 gcov 对照 llvm-cov。复杂 if-else 题加测 MC/DC：GCC 14 起支持 `-fcondition-coverage` 配合 `gcov --conditions`，Clang 18 起支持 `-fcoverage-mcdc`。当前镜像是 GCC 12，不支持。

## 5. 先校准尺子，再量 Agent

用好坏已知的测试套件检验评分器。评分器排不出正确的顺序、识别不了作弊，就不能拿它来比较 skill。

| 校准样本 | 期望结果 |
|---|---|
| 空套件；所有测试都 `GTEST_SKIP()` | 判为无效 |
| 只调用 `updateQuality()`，不写断言 | 有效，但变异检出接近 0，在极端变异下仍然通过 |
| 只断言 `sellIn` | 检出明显偏低 |
| 5 条冒烟用例 | 中低（现有数据：检出 7/20） |
| 开发者手写的套件或强套件 | 高 |
| 把实现细节写死的脆弱套件 | 检出高，但等价重构上的误报也高 |
| 作弊：把 `EXPECT_EQ` 宏定义为空；在静态初始化中调用 `std::exit(0)`；自带一个直接返回 0 的 `main`；改 CMake 把测试排除掉 | 全部被识别 |

通过标准：顺序正确；作弊全部识别；同一套件重复评分，结果完全一致；在容器内跑通。之后评分器每修改一次，都要重跑这组校准。

## 6. 题库

- **开发题**：GildedRose，再加一道“孪生题”：改名、改阈值、改常量，但语义不变。两道题的分差反映了背题的程度。开发题可以随意查看失败原因、调试 skill。
- **验收题**：没参与过调试的真实缺陷题，尽量选在模型训练截止之后的提交。验收题只在发布候选版本时运行；用过的题转入开发集，再补充新题。
- **准入检查**：参考实现能构建；参考测试在基线上通过；变异有效；隐藏材料已隔离；最简单的基线不会全对，也不会全错。全对的题没有区分度；多次运行都是 0 分，最常见的原因是题目本身有问题。
- **规模**：先求小而准。Anthropic 的 agent 评测指南建议，从 20–50 道来自真实失败的简单题起步。同一份代码换几组输入，不算多道题。
- **C++ 特性**：逐步覆盖对象状态变化、异常、资源生命周期、容器边界、依赖替身等情形，每类至少一道题。

## 7. 比较 Agent/skill：统计设计

- **先测噪声**：同一配置在同一批题上重复运行，看分数自然波动有多大。差异小于这个幅度的，不算改进。
- **事先写定比较方案**：主指标、想分辨的最小差异、每题运行次数、置信区间的算法、保留还是回退的规则，都在运行前写定。不允许跑几次挑最好的那次。
- **配对比较**：各版本跑同一批题，按题配对比较（如 McNemar 检验、配对 bootstrap），比各自报一个总分灵敏得多。
- **按题聚类**：同一道题的多次运行不是独立样本，标准误要按题聚类计算。Miller (2024) 指出，常见评测聚类后的标准误可能比朴素估计大 3 倍以上。
- **固定并记录**：模型、Agent、skill、提示词、工具链版本和预算全部固定并记录。pass@k（k 次里至少成功一次）和 pass^k（k 次全部成功）按用途选用，分别报告。
- **题少的现实**：只有几道题时，只能看出很大的差异。尽量用每道题上的连续指标（如变异检出率），少用通过/失败这类二值结果。

## 8. 从失败到 skill 修改

逐条读原始记录：生成的测试文件、编译报错、修复过程、幸存的变异。先开放式标注，再归类、计数，读到不再出现新类型为止。每个幸存变异都要有一句结论：是等价改动、走不到的代码，还是断言太弱。

下表是改进方向的初始假设。等错误分析的计数出来，才能确定先改哪一项：

| 经常出现的问题 | 优先改进的地方 |
|---|---|
| 找不到类型、函数、头文件 | 收集上下文、理解构建环境的能力 |
| 测试能跑，但断言写错 | 预期值以实际运行结果为准，不凭推测填写 |
| 正常情况会测，边界不会测 | 边界值、异常路径、状态转换的检查步骤 |
| 覆盖率高，但抓不到 Bug | 断言是否真正检查了结果 |
| 时好时坏、换顺序就失败 | 状态清理，以及对随机性和外部依赖的控制 |
| 一改实现细节就误报 | 只断言公开行为，不依赖内部结构 |
| sanitizer 报出测试自身的问题 | 对象生命周期、引用和极值的处理 |

每次只改一处，并记录假设、改动、预期、结果，以及最后是保留还是回退。

## 9. 除了你我，什么能证明结果是对的

| 证据 | 做法 |
|---|---|
| 真实修复提交 | 在修复后的版本上生成的测试，能否在修复前的版本上失败；修复出自原项目开发者 |
| 已知答案 | 校准样本排出正确的顺序；在公开基准上复现一个已发表配置的结果 |
| 彼此独立实现的工具 | gcov 对照 llvm-cov，手写变异对照工具生成的变异，GCC 对照 Clang。同一工具的两种输出格式一致，不算独立 |
| 独立的人 | 盲评，并计算评审之间的一致性。最有力的是维护者采纳：把生成的测试作为 PR 提给真实项目，或者走内部 code review。TestGen-LLM 和 Meta ACH 最终都以工程师采纳率作为证据，两者都是 73% |
| 独立复现 | 在另一台机器、另一种架构上，用冻结的打包产物复现出同样的数字。目前只在 macOS ARM64 主机加 Linux ARM64 容器上验证过 |
| 时间检验 | 分数高的测试集，在后续真实提交里是否抓到更多回归、误报更少。Just 等人（FSE 2014）用 357 个真实缺陷检验过变异检出与真实缺陷检出的相关性；本项目的场景需要自己再验证一次 |

原则：结果必须有可能失败，才有证明力。正式评测时，被测 Agent 要有可能在隐藏题上失败，合格线也要事先写定。

## 10. 下一步：最小但完整的一轮

先不扩大题库。在 GildedRose 这道开发题上把尺子做准，再用一道真实缺陷题验收：

1. 在镜像构建阶段装好固定版本的 GoogleTest；执行器接入 gtest 的 JSON 结果、sanitizer，以及重复、乱序运行。
2. 写明 GildedRose 评分所用的输入域。
3. 建变异集：工具生成 → TCE → 有界等价检查 → 最小集合；手写变异单列。
4. 准备校准样本和作弊样本，达到第 5 节的通过标准。
5. 实现测试生成入口、受限工作区和独立评分。用最简单的提示词作基线，每道题运行多次，测出噪声，做第一次错误分析。
6. 从真实缺陷数据集或自己的仓库选一道 C++ 题，作为第一道验收题。

这些完成之后，再比较简单提示词和各版 skill。原计划的对比实验保留，即同一模型、同一批题、同一预算，分别用简单提示词、当前 skill 和修改后的 skill 生成测试；但前提是尺子已经校准、噪声已经测出。
