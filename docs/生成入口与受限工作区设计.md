# 生成入口与受限工作区设计

> **讨论结论，2026-10-24，尚未实现。** 本文记录“测试生成入口 + 受限工作区”的设计讨论结果，目标是全自动跑完“生成 → 修复 → 冻结 → 评分”一整轮。已定的决定摘要见[决策记录](决策记录.md) D003–D009，规格层面的改动见[评测规格](评测规格.md) v0.4 草案。**仓库目录结构（含工作区内部布局、各类材料的存放位置）另行专门讨论**，本文出现的路径只表达“放什么”，不代表最终目录名，见第 12 节。

## 1. 目标与本阶段范围

- **目标**：一条命令完成一个 run：为每道题建立全新的受限工作区，运行被评测的 Agent 生成并修复测试，冻结首次与最终产物，用已校准的评分器分别评分，汇总结果。
- **本阶段只接 pi**，直接调用，不加 skill。skill 是否加、怎么写，与本阶段无关（Q45）。
- **顺序**：先完成仓库目录重构（单独一步、单独提交，Docker 中重新校准与 0.1.1 结果一致），再实现生成入口（Q1）。目录方案尚待专门讨论。

## 2. 术语

| 术语 | 含义 |
|---|---|
| **run** | 一次实际执行，是动态的记录，不是一份配置。同一配置（Agent + 配置 + 题目集 + K）执行两次，就是两个 run，互不干扰（Q7、Q8） |
| **trial** | 同一道题从全新的空工作区开始，完整跑一遍“生成 → 修复 → 冻结”。每题跑 K 个 trial（K = 5），全部属于同一个 run。评测规格中的“一次运行”即一个 trial |
| **首次产物** | Agent **第一次调用** `build_and_test` 时工作区中的测试 |
| **最终产物** | Agent 结束时（含预算用尽、看门狗终止）工作区中的测试 |
| **修复轮次** | 第一次之后每调用一次 `build_and_test` 记 1 轮 |

## 3. 被评测对象：pi

- **来源**：用户 fork 的 pi（TypeScript/Node，要求 node ≥ 22.19；上游 earendil-works/pi，即原 badlogic/pi-mono）。本机位置 `/Volumes/ProjectCode/AI_Coding_Agent/pi`。
- **入库方式**（Q30、Q36）：源码**全量复制**进本仓库，不带原 `.git`，以后直接在本仓库修改，Agent 版本用 Qualtor 的提交号表示。
  - 不入库 `node_modules/`、`dist/`；入库 `package-lock.json` 固定依赖。在 Docker 机器上用 `npm ci && npm run build` 构建。
  - 另存 `UPSTREAM.json`，记录复制时对应的上游地址和提交号，便于对照上游修复。
- **不做适配器层**（Q2）：生成入口直接面向 pi，不抽象成通用 Agent 接口。
- **被评测配置**放在仓库的 `agents/` 下（Q19），本阶段只需一份配置文件，**模型、provider、thinking 级别等由用户自行填写**（Q51），框架只留出配置位置。一份 pi 可以搭配多套配置。
- pi 的调用方式（调研结果，实现时核实）：`--mode json` 输出 JSONL 事件流；`--tools` 白名单；`-e` 加载扩展；`-nc` 不加载 AGENTS.md/CLAUDE.md；`--session-dir` 指定会话目录；状态目录由 `PI_CODING_AGENT_DIR` 指定且运行时需要可写；完成信号为 `agent_settled` 事件；json 模式失败时退出码不一定非 0，需检查事件。pi 官方声明自身不构成安全边界，隔离必须靠容器。

## 4. 生成容器与隔离

- **生成 Agent 在 Docker 容器中运行**（Q3、Q16）。新增生成镜像：以 `qualtor-gcc` 为基础，加装 node 24 运行时，不在镜像里安装 pi；由 `toolchains.py` 一并构建（Q43）。
- **pi 目录以挂载方式加入容器**，只读；每个 trial 新建一个空的、可写的 pi 状态目录（`PI_CODING_AGENT_DIR`），会话记录落在本 trial 的目录内。
- **只挂载本 trial 需要的东西**：被测项目（只读）、本 trial 的可写测试目录、任务说明、pi 与配置（只读）、框架扩展（只读）。隐藏材料（参考测试、替换版本、变异分母、校准样本、历史 runs）根本不进入生成容器，这是第一道隔离。
- **被测代码只读挂载、不复制**（Q33 说明）：容器内看到的是宿主机上的同一份文件，任何写入都被操作系统拒绝。这既防止 Agent 修改被测代码迎合测试，也避免大代码库每个 trial 复制一份。run 目录不另存源码，靠提交号与哈希追溯。工作区内部的具体布局属于目录讨论（Q37）。
- **网络**（Q20、Q26、Q32）：生成容器**直接联网**，不设出口代理。理由是 Agent 没有 bash（第 5 节），手里没有可联网的工具。API 地址和密钥由 Docker 机器的环境变量传入（地址可变，改环境变量即可）；`run.json` 记录 API 地址，不记录密钥。评分容器保持禁网。
- **已知差异**：`build_and_test` 运行测试时可以联网，评分时禁网。依赖真实网络的测试会在修复阶段通过、评分阶段失败。当前题目不涉及网络，暂不处理；出现需要联网的被测代码时，再让测试进程断网运行（Q32）。

## 5. 工具与 build_and_test

- **Agent 可用的工具**（Q17、Q38）：`read`、`write`、`edit`、`grep`、`find`、`ls`、`build_and_test`。**不提供 bash**，否则 Agent 可以自行编译运行，绕过修复轮次的限制。由此，skill 不能依赖 shell 脚本。
- **Agent 只能通过 `build_and_test` 了解代码的实际行为**（Q24 选 A）：想知道实际返回值，就写测试、看失败信息，这会消耗修复轮次。不提供单独的探针工具。
- **`build_and_test` 做什么**（Q39）：
  1. 用评分器的同一份 CMake 模板和 GCC 编译 `tests/` 下的文件，不开覆盖率；
  2. 编译失败时返回编译器错误，截断到前 8000 字符；
  3. 编译成功后运行一遍测试，不打乱、不重复，单测超时用题目的 `test_timeout_seconds`；
  4. 返回每个测试的通过/失败及 GoogleTest 失败信息，截断到 8000 字符；
  5. 告知剩余修复轮次。
- **只返回编译与运行结果，绝不返回评分信息**（Q5、Q12）：不给覆盖率、变异结果，不运行替换版本和参考测试。修复的含义是：编译失败，或在被测代码上运行失败（按 D001 属于测试写错），Agent 据此修正测试。
- **裁判机制属于评测框架，与被评测配置分开**（Q18）。以一个 pi 扩展实现，只读挂载、用 `-e` 加载，包含三样：
  - `build_and_test` 工具本身，负责编译、运行、计数和拍快照；
  - 门卫：通过 `tool_call` 钩子，写入只允许 `tests/` 下符合 `allowed_test_files` 的文件，读取只允许工作区内，越权操作拒绝并记录；
  - 计数器和每轮快照存放在 Agent 写不到的位置，Agent 无法篡改已用轮次。

  换 skill 或提示词时，这部分保持不变。容器挂载是第一道隔离，钩子是第二道。

## 6. 预算、冻结与结束状态

- **只限制修复轮次**（Q6）。token、墙钟时间只记录，不设上限。N 写进 `task.json` 的 `budget.repair_rounds`，初始值 **N = 3**（Q13）。
- **计数**：第 1 次调用 `build_and_test` 不算修复，同时冻结首次产物；之后每次调用记 1 轮；用满 N 轮后 `build_and_test` 拒绝执行，并告知预算已用完。
- **无响应看门狗**（Q14、Q25）：不设总时长上限，因为大代码库所需时间无法事先确定。pi 连续 **15 分钟**没有任何事件（模型调用、工具调用均无）即判为卡死并终止。模型调用次数暂不设上限，出现“只读不停”的情况再加。
- **任务说明**：框架根据 `task.json` 生成任务说明（被测文件、允许写的测试文件、修复预算 N、`build_and_test` 用法）。这几项事实固定，不随配置改变（Q27，存放位置属于目录讨论）。

**trial 的结束状态**（Q15、Q41）：

| 状态 | 含义 | 处理 |
|---|---|---|
| `finished` | Agent 自己结束 | 冻结最终产物，首次、最终分别评分 |
| `budget_exhausted` | 修复轮次用完 | 同上 |
| `never_built` | 从未调用 `build_and_test` | 以结束时的工作区同时作为首次和最终产物，照常评分并记录；用于比较配置是否引导 Agent 自行验证 |
| `generation_stalled` | 看门狗终止 | 冻结当时的工作区，照常评分，单独列出 |
| `agent_error` | pi 崩溃或模型 API 出错 | 属于基础设施问题，用全新工作区重跑该 trial，最多 2 次；失败那次的记录保留 |

## 7. 一次 run 的流程与入口

- **入口**（Q40）：`run.py --config <配置名> --tasks <题目集> --trials 5 [--jobs N]`。依次完成：建工作区 → 运行 pi → 冻结首次与最终产物 → 两份产物各评一次分 → 汇总。trial 默认串行，`--jobs` 并行。
- **评分器校准状态不是 passed 时拒绝运行**，避免白花生成成本。
- **配置快照**（Q8）：`run.json` 记录 Qualtor 提交号与未提交改动的哈希、pi 源码与配置的哈希、模型设置、API 地址（不含密钥）、题目指纹、工具链镜像 ID、评分器版本与校准状态、开始与结束时间、状态。
- **run 目录的内容**（Q10，目录名待定）：

```
runs/<run-id>/
  run.json                     # 配置快照、时间、状态
  trials/<task>/trial-<k>/
    workspace/                 # Agent 写的测试（结束后保留）
    attempts/attempt-<n>/      # 每次 build_and_test 的快照及完整编译、运行输出
    first/  final/             # 冻结产物（manifest + 哈希）
    logs/                      # 全量执行日志，见第 8 节
    cost.json                  # 由日志派生
    score/<评分器版本>/first/  final/
  summary.json
```

  一个 run 的全部证据集中在这个目录；`artifacts/` 只保留工具链验收和校准状态。
- **补评写进原 run**（Q22、Q28）：评分器升级后，在同一个 run 的 `score/<新版本>/` 下新增结果，旧结果原样保留、不覆盖；汇总与比较时指定评分器版本。不另开 run。

## 8. 执行日志与成本

- **可观测性优先，全量保存原始日志**（Q42、Q47），每个 trial 的 `logs/` 下原样保存：
  - pi 的会话 JSONL 原文；
  - pi `--mode json` 的完整事件流（stdout、stderr）；
  - 编排器日志：每次 `build_and_test` 的调用参数、完整编译与运行输出（给 Agent 的是截断版，这里是完整版）、修复轮次计数、看门狗事件、越权写入被拒记录；
  - 容器启动命令、镜像 ID、退出码（沿用 `audit.py` 的记录机制）。

  日志中不写入任何凭证。
- **`cost.json` 由抽取脚本从原始会话日志派生**（Q48），不在运行时随手记录。改统计口径时用原始日志重新抽取，不需要重跑生成。抽取脚本版本写进 `cost.json`。字段：
  - `tokens`：输入、输出、缓存读、缓存写；
  - `model_calls`：assistant 消息条数；
  - `repair_rounds`：实际用掉的修复轮次；
  - `seconds`：墙钟时间，只记录；
  - `usd`：pi 计算的费用。

  首次产物的成本取第一次调用 `build_and_test` 时的累计值。
- **不生成给人看的时间线视图**（Q49），以原始日志为准。

## 9. 生成镜像与框架自测

- **生成镜像冒烟验收**（Q43）：在镜像中构建 pi，用一个不调用模型的命令确认 pi 能启动、扩展能加载、`build_and_test` 能编译并通过现有 9 个手写测试。
- **剧本模型**（Q44）：用 pi 的自定义 provider 接一个本地“剧本模型”，按脚本依次发出工具调用，确定性地触发失败路径：越权写入被拒、修复轮次用尽、`never_built`、卡死（看门狗）、API 出错（`agent_error` 重跑）。它只用于框架自测，不是被评测的 Agent。

## 10. 本阶段完成标准

- 用 pi（不加 skill，用户填写模型配置）在 GildedRose 上跑 **一个 run、K = 5**，全自动完成、无人工干预，首次与最终产物都得到评分（Q46、Q50）；
- 用剧本模型覆盖第 6 节的每种结束状态和越权写入；
- 生成镜像冒烟验收通过；
- 不包含 skill 版本，也不比较 skill 效果。

## 11. 讨论中否决的方案

| 方案 | 否决理由 |
|---|---|
| 通用 Agent 适配器层，先接 Claude Code | 只需要 pi，直接调用（Q2） |
| 编排器驱动修复（编排器编译并回传错误，固定 N 轮） | 修复策略应由 Agent 决定，才能评出 Agent 与 skill 的差异（Q4） |
| token、墙钟时间也设预算上限 | 只限制修复轮次（Q6） |
| 60 分钟总时长保护 | 大代码库所需时间无法事先确定；改为无响应看门狗（Q14） |
| 给 Agent bash | 可绕过修复轮次计数 |
| 不限次数的 `run_probe` 探针工具 | 可把整套测试塞进探针预先调好，使轮次限制失效；且不是核心（Q24） |
| 出口代理按域名白名单放行 | 过于复杂，API 地址会变化；Agent 无 bash，直接联网即可（Q20） |
| 测试进程断网运行 | 当前题目不涉及网络，暂无意义（Q32） |
| 补评另开 run | 补评属于原 run，按评分器版本分目录（Q22、Q28） |
| pi 作为 git submodule，或只记录外部路径 | 源码全量入库，在本项目中提交（Q30） |
| 被测源码只记录地址和提交号、不入库 | 被测源码是核心资产，必须完全放在本仓库（Q31） |
| 可读时间线 `timeline.md` | 专门给人做视图浪费，以原始日志为准（Q49） |
| 本阶段做 baseline 与 skill 两套配置对比 | skill 与本阶段无关（Q45、Q46） |
