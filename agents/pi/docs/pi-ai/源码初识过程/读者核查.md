# 读者核查

核查方式：一个未参与撰写的子 Agent，只拿到报告正文、研究对象名称、正文写作原则和章节分工，没有读源码、来源和查证材料。它逐句回答“删除这一句，读者会失去什么”。

## 第一轮结果

- **结论**：共 11 条候选。主线（定位、能力、交互、边界）读者能顺利读懂。问题集中在三处：
  - 背景与核心能力重复；
  - 系统交互与定位重复；
  - 责任边界中“重试”“兼容接口”两条含义不清，或混入了编码代理的内部细节。

  处理后报告更短，关键认识不会丢失。
- **候选句**：
  1. 「可持久化的对话运行时 pi-durable 也通过它访问模型。」（定位）**删除**。
     - pi-durable 此后不再出现，“可持久化的对话运行时”也没有解释。
     - 前两句已说明 pi-ai 是 pi 模型请求的底层，删去不影响对定位的理解。
  2. 「有的服务商在回复中夹带只有本家能识别的签名数据……请求中途取消就算不准费用。」（背景）**合并**。
     - 签名数据一事与能力“换模型后接着同一段对话”重复。
     - 取消后用量不准与责任边界“中途取消的请求用量也可能不完整”重复；它是 pi-ai 没有解决的限制，放在背景里容易被读成已解决的问题。
  3. 「认证方式同样各不相同……拿到的令牌过期后还要刷新。」（背景）**合并**。这些内容在能力“找到凭证并完成订阅登录”中逐项再次出现，且写得更完整。
  4. 「pi-agent-core 的每一轮请求和编码代理生成对话摘要都走这条路径。」（能力）**合并**。与定位“……发出的每一次模型请求都经过它”重复。
  5. 「应用交出模型、对话和选项；pi-ai 找到模型所属的服务商，取得凭证……」（系统交互）**合并**。交出与拿回已在定位首句和第一项能力中讲过，取凭证已在凭证能力中讲过，本句没有新的交接信息。
  6. 「调用方要检查结束原因，不能只靠捕获异常。」（责任边界）**合并**。标题和前一句已足以让读者得出这个要求。
  7. 「……调用方不设重试次数时，它也不会自动重发失败的请求。」（责任边界）**改写**。
     - 这个条件暗示 pi-ai 自带可配置的重试，与标题“压缩和重试由调用方执行”冲突。
     - 这项设置别处没有解释，读者判断不了 pi-ai 到底会不会重试。
  8. 「编码代理的自动重试默认最多 3 次，间隔逐次加倍。」（责任边界）**删除**。这是编码代理的默认参数，超出研究范围；编码代理会自动重试一事已在能力中给出。
  9. 「推荐的用法是应用先创建自己的模型集合……兼容导入路径……」（责任边界）**改写**。
     - 旧方式写成“按环境变量自动取密钥”，而新方式也会读环境变量，读者分不清新旧差在哪里。
     - “模型集合”在此处尚未解释。
  10. 「编码代理仍在使用它：models.json 新增的服务商靠它的全局登记表……」（责任边界）**改写**。
      - “全局登记表”“接口格式的实现”“扩展”“被自动导向”都没有解释，属于应放在证据里的调用链线索。
      - 这句看似与核心组成“组装成同样的形式，放进同一个集合”矛盾。
      - 读者只需知道：编码代理及其扩展仍依赖旧接口，过渡尚未完成。
  11. 「每种实现负责一种接口格式的请求转换……SDK 在第一次用到时才加载。」（核心组成）**合并**。
      - 多家服务商共用接口格式，已在系统交互中给出。
      - SDK 首次用到时才加载，是不影响使用方式的实现细节。

## 主 Agent 的处理

主 Agent 同意全部 11 条，处理如下：

- **删除**：第 1、4、6、8、11 条。
- **合并**：
  - 第 2、3 条：背景只保留接口差异的总述，删去签名数据、取消后用量、认证方式三处细节。
  - 第 5 条：系统交互第一项只保留新信息，即编码代理经 pi-agent-core 发请求，事件经 pi-agent-core 转给界面。
- **改写**：
  - 第 7 条改为“默认也不会重发失败的请求”。
  - 第 9、10 条合并改写：
    - 新旧差异改用行为说明：旧函数一导入就对整个进程生效，也不读取应用保存的凭证。
    - 当场说明“模型集合”的含义。
    - 编码代理的依赖只写“部分请求经由旧函数发出、扩展拿到的也是兼容入口”。

## 第二轮复核

- **结论**：仍有剩余候选。原第 1–6、8–11 条已解决，第 7 条部分解决；另因修订新增两条合并候选。
- **仍有的问题**：
  - 第 7 条：“默认也不会重发失败的请求”里的“默认”，仍暗示 pi-ai 可以自己重发，与标题冲突。复核意见有两种改法：
    - 写明“可设置让 pi-ai 重发有限次数，默认关闭”，标题改为“由调用方决定”；
    - 若这点不重要，删去“默认”。
  - 新增合并候选：
    - 核心组成“模型集合”一项：“应用创建并持有”“多个互不影响”“也是解析凭证的地方”，已由责任边界“旧的全局调用方式仍在过渡”一条及凭证能力给出。
    - 核心组成整节：去掉“模型集合”后只剩“服务商”一项。它独有的认识只有一点：自定义服务商和扩展注册的服务商与内置服务商形式相同、平等接入。这一点可并入系统交互“pi-ai 与模型服务”，并把“扩展（用户编写的插件）”的括注移到系统交互，这一节随后删除。
  - 复核认为“服务商”一项与兼容入口一条不重复：前者讲扩展注册的服务商以同样形式接入，后者讲扩展导入 pi-ai 时拿到旧入口。

## 第二轮处理

主 Agent 同意，处理如下：

- **第 7 条**：pi-ai 确有有限的请求级重试，调用方可设定次数，只在服务尚未开始返回内容时重发，默认 0 次。删去“默认”会把“默认不重发”写成“从不重发”，与事实不符，所以采用第一种改法：
  - 标题改为“压缩和重试策略由调用方决定”；
  - 正文写明“调用方可以设定次数，让它在服务还没开始返回内容时重发请求，默认不重发”。
- **核心组成**：
  - 删除整节。
  - “自定义服务商和扩展注册的服务商与内置服务商一样自带模型清单、凭证规则和请求入口”并入系统交互“pi-ai 与模型服务”，并在那里首次解释“扩展（用户编写的插件）”。
  - “同一进程里的多个集合互不影响”补进兼容入口一条的前半句。

## 最终复核

- **结论**：从读者理解的角度看，没有剩余候选；读者核查完成。
- **复核意见**：
  - 第 7 条已解决：读者能分清哪些由 pi-ai 做、哪些由调用方决定。
  - 删去核心组成没有丢失结构认识。“扩展”的括注放在首次出现处，“模型集合”只在兼容入口一条出现并就地解释。
  - 没有新候选。
- **可选措辞**：复核指出，重试一项“pi-ai 只判断失败属于哪一类”与后文“可以重发请求”字面略有出入，建议去掉“只”。这一处不列为候选，主 Agent 仍已采纳，改为“pi-ai 判断失败属于哪一类，但不会替调用方压缩对话”。
