# 源码初识：pi-ai

> 研究对象：pi 仓库的 `packages/ai`，即 npm 包 `@earendil-works/pi-ai` 1.2.0（源码提交 2d147a114）。范围只含这个包；pi-agent-core、pi-coding-agent 等包作为它的使用方出现。

## 定位

pi-ai 让程序用同一种方式调用几十家服务商的大模型：调用方交出模型和一段对话，拿回逐段到达的回复、模型要调用的工具，以及这次请求的用量和费用；各家接口格式、密钥和登录方式的差异由 pi-ai 消化。[1][2]

它是 pi 最底层的模型接入层。pi 的智能体循环（pi-agent-core）和命令行编码代理（pi-coding-agent）发出的每一次模型请求都经过它：前者负责“请求模型、执行工具、再请求”的循环，后者让用户选模型、登录，并保存会话和凭证。[3][4]

## 背景与问题

编码代理在一次会话里要反复请求模型，用户还会中途换模型、中止生成，并想知道花了多少钱。这些需求都受制于各家接口的差异：Anthropic、OpenAI、Google 的接口对工具调用、思考内容、流式返回和用量统计各有一套表示；即使同样兼容 OpenAI 的 Chat Completions 格式，有的服务商也会拒绝某些字段，或把思考内容放在别的字段里。[5]

作者 Mario Zechner 在 2025 年 11 月的文章中说明，他没有采用 Vercel AI SDK 这类现成的多服务商封装，而是在各家官方 SDK 之上自建这一层，以便完全掌控接口设计并保持精简；跨服务商延续对话、请求可中止并保留已生成的部分，是这一层从一开始就设定的目标。[5]

## 核心能力

- **用同一种对话格式请求不同服务商**：对话用统一的消息结构表示（系统指令、用户输入、模型回复、工具结果），pi-ai 负责转成各家的请求，并把返回内容整理成同一套逐段到达的事件，结束时给出带结束原因、用量和费用的完整回复。[2]
- **换模型后接着同一段对话**：对话记录不绑定服务商，下一次请求可以直接交给另一家的模型；发送前，pi-ai 把历史改写成新模型能接受的形式，例如把上一个模型的思考内容改成普通文字、丢掉只有原模型认得的签名数据。编码代理切换模型时只替换模型，对话原样保留。[6]
- **用一个档位控制各家的思考强度**：调用方从“关闭”到“最高”的统一档位中选一档，pi-ai 换算成各家的参数，例如思考预算的 token 数或强度等级；它还能列出某个模型支持的档位，并把不受支持的档位换成相邻的可用档位。编码代理据此为每个模型提供可选档位和切换。[7]
- **提供可选模型及其参数**：pi-ai 内置 42 个服务商配置（含同一厂商的地区或套餐变体），目录中的对话模型都支持工具调用，并带有上下文窗口、最大输出、价格、能否读图和思考等参数，数据在构建时由 models.dev、OpenRouter 等公开来源生成。编码代理用这些参数列出可选模型、判断对话是否快超出上下文窗口，并利用 pi-ai 的清单刷新机制，从 pi.dev 获取发版之后的目录更新。[8]
- **找到凭证并完成订阅登录**：每次请求前，pi-ai 按服务商的规则找凭证：调用方明确传入的密钥优先，其次是已保存的凭证，都没有时才读环境变量或 AWS、Google Cloud 的本机凭证。对 Claude Pro/Max、ChatGPT、GitHub Copilot 等订阅，它提供登录流程，令牌快过期时在请求前自动刷新并存回，同时到来的多个请求只刷新一次；编码代理的 /login 和 /logout 命令都通过它完成登录和注销。[9]
- **在对话中途调整系统指令和工具**：调用方可以在对话中途插入系统消息来改动提示段落或增删可用工具，不必改写之前的历史。支持这种写法的模型原地收到提示变更，服务商为不变的对话开头保留的缓存仍然有效，其他模型则在发送前把变更合并进开头的系统指令；工具增删只有部分模型能原地表达，其余情况下 pi-ai 会在请求开头换上完整的当前工具列表，开头的缓存因此失效。pi-agent-core 用它声明可用工具的增删，编码代理在系统指令变化时只追加有变化的段落。[10]
- **判断失败该压缩还是重试**：pi-ai 能从各家措辞不同的报错里认出“对话超出上下文窗口”，也能发现部分服务商不报错、悄悄截断的情况；它还区分服务繁忙、网络中断这类值得重试的错误和额度耗尽这类重试无用的错误。编码代理据此决定先压缩对话再重发，还是等一段时间后自动重试。[11]

## 系统交互

- **编码代理、pi-agent-core 与 pi-ai**：在 pi 中，编码代理经由 pi-agent-core 发出请求；pi-ai 返回的逐段事件由 pi-agent-core 转给界面实时显示。[3][4]
- **pi-ai 与模型服务**：pi-ai 用 Anthropic、OpenAI、Google、AWS 的官方 SDK 或直接的 HTTP 请求访问各家服务，按服务商采用的接口格式转换请求、解析返回。多数服务商沿用少数几种主流格式，例如 Groq 用 OpenAI 的 Chat Completions 格式，Kimi For Coding 用 Anthropic 的 Messages 格式；用户在编码代理中配置的 Ollama、vLLM 等自建服务，也是选一种已有格式接入；这类自定义服务商和扩展（用户编写的插件）注册的服务商，都和内置服务商一样自带模型清单、凭证规则和请求入口。[12]
- **pi-ai 与应用的存储**：凭证和运行时刷新得到的模型清单放在哪里由应用决定：pi-ai 在请求前从应用提供的存储读取凭证，登录或刷新令牌后写回，刷新清单后存下结果供下次启动先用；应用不提供存储时，这些数据只在内存中。编码代理把它们存为 ~/.pi/agent 下的 auth.json 和 models-store.json。[13]
- **pi-ai 与用户（登录时）**：订阅登录由 pi-ai 推进流程，与用户的交互交给应用：应用显示授权链接或设备码、收集用户粘贴的授权码；部分流程会在本机临时开启回调服务，接收浏览器跳转回来的授权结果。[9]

## 责任边界

- **工具由调用方执行**：pi-ai 只告诉调用方模型要调用哪个工具、参数是什么，并提供按工具的参数结构校验参数的功能；执行工具、把结果加回对话、决定是否继续请求，由 pi-agent-core 这样的调用方负责。[3]
- **对话由调用方保存**：pi-ai 不保存对话，每次请求都要交出完整的对话记录；会话的保存和恢复由编码代理负责。[2]
- **出错不抛异常**：请求一旦开始，出错或被中止都不会以异常形式抛出，而是以一个错误事件结束；最终回复的结束原因标为“出错”或“已中止”，已生成的部分内容仍保留。[14]
- **压缩和重试策略由调用方决定**：pi-ai 判断失败属于哪一类，但不会替调用方压缩对话；调用方可以设定次数，让它在服务还没开始返回内容时重试，默认不重试。经 AWS Bedrock 的请求例外：它沿用 AWS SDK 自带的重试（默认最多尝试 3 次），不受这个设定控制。[11]
- **费用是估算值**：费用通常由 pi-ai 按服务商报告的 token 数乘以模型目录中的单价算出，而不是取自服务商的账单；部分计价方式（如 OpenRouter 按时段计价）没有建模，中途取消的请求用量也可能不完整。[15]
- **旧的全局调用方式仍在过渡**：现在的用法是应用自己创建模型集合、只登记需要的服务商，同一进程里的多个集合互不影响；早期的全局函数一导入就对整个进程生效、默认带上全部内置服务商，也不读取应用保存的凭证。旧函数保留在兼容导入路径（`@earendil-works/pi-ai/compat`）中并标明将被删除，但编码代理仍有部分请求经由它们发出，它加载的扩展导入 pi-ai 时拿到的也是这一入口。[16]
